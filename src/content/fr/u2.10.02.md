# u2.10.02 Notice d’utilisation de MFront avec code_aster

**Résumé:**

On décrit ici l’utilisation du couplage entre **code_aster** et le module d’intégration de lois de comportement [MFront](https://thelfer.github.io/tfel/web/index.html), qui est diffusé en Open Source sous licence GPL et CECILL-A.

MFront permet de définir une loi de comportement de façon simple, proche des équations physiques, sans avoir à se soucier des méthodes de résolution. Il offre des classes de manipulation de données (tenseurs, par exemple) de façon conviviale et met à disposition des algorithmes de résolution des équations non-linéaires associées efficaces en termes de performances. MFront est adapté aussi bien aux schémas temporels implicites qu’explicites.

Ces comportements sont utilisables dans **code_aster** pour les modélisations 3D et 2D, coques, THM et pour les éléments de joints. Les grandes déformations peuvent être utilisées avec GDEF_LOG. De plus, MFront produit un code efficace, car les opérations tensorielles sont optimisées comme le montrent les *benchmarks* réalisés avec des comportements équivalents de **code_aster**.

Il faut bien noter que l'utilisation de ces lois de comportement *à façon* (mot-clé RELATION='MFRONT' sous [COMPORTEMENT](doc:u4.51.11)) implique une validation spécifique pour l'étude envisagée, car on se place hors du domaine qualifié de **code_aster**.

Ce document décrit la façon d'utiliser un comportement défini par l'utilisateur à l'aide de MFront dans un fichier de commandes de **code_aster**.

## 1 Définition d'une loi de comportement avec MFront

### 1.1 Écriture d'un comportement MFront

On écrit la loi de comportement dans le fichier MFront, suivant les conseils fournis dans le tutoriel [bib1]_, ou en s'inspirant d'un comportement déjà disponible dans les tests de **code_aster** (*cf.* U2.10.02-exemples-d-utilisation).

Nous prendrons ici pour exemple le comportement visco-plastique de Lemaître écrit sous forme implicite. Le fichier `Lemaitre.mfront` s'écrit:

```
@DSL Implicit;
@Behaviour Lemaitre;
@Author EDF R&D ERMES;
@Date 25/03/2024;
@Description{
    Lemaitre viscoelastic behaviour law (cf. code_aster documentation r5-03-08 for details):
    eto=eel+dp_dt*nv,
    sig=D:eel,
    nv=1.5*dev(sig)/seq,
    dot(p)=((1/K)*seq/p^(1/M))^Np;
}

@Algorithm NewtonRaphson_NumericalJacobian;
@Theta 0.5;
@Epsilon 1.0e-12;
@MaximumNumberOfIterations 100;

@UseQt true;
@MaterialProperty stress young;
@MaterialProperty real poisson;
@MaterialProperty real Np;
@MaterialProperty result_type<real,stress,OpDiv> UN_SUR_K;
@MaterialProperty real UN_SUR_M;

@StateVariable real p;

@LocalVariable StiffnessTensor Dv;

@InitLocalVariables{
    const auto lambda=computeLambda(young,poisson);
    const auto mu=computeMu(young,poisson);
    Dv=lambda*Stensor4::IxI()+real(2.0)*mu*Stensor4::Id();
}

@ComputeStress{
    sig=Dv*eel;
}

@Integrator{
    const auto seq=sigmaeq(sig);
    const auto p_mts=max(p+theta*dp,real(1.0e-8));
    const auto slem=seq*UN_SUR_K/pow(p_mts,UN_SUR_M);
    const auto vp=frequency(1.0)*pow(slem,Np);
    const auto iseq=real(1.0)/max(seq,young*real(1.e-14));
    const auto n=real(1.5)*deviator(sig)*iseq;
    feel+=vp*dt*n;
    feel-=deto;
    fp-=vp*dt;
}

@TangentOperator{
    Stensor4 Je;
    getPartialJacobianInvert(Je);
    Dt=Dv*Je;
}
```

Cette loi est équivalente à la loi LEMAITRE, disponible dans **code_aster**.

### 1.2 Création de la bibliothèque dynamique à partir d'un comportement MFront

Pour être utilisable dans **code_aster**, le comportement MFront ainsi programmé doit être transformé en bibliothèque dynamique. Pour cela, il faut le *compiler*. Cela peut être fait de deux manières différentes.

1. **Solution recommandée: utilisation de CREA_LIB_MFRONT**
  La macro-commande CREA_LIB_MFRONT permet de construire la bibliothèque automatiquement. Il suffit de fournir le fichier MFront en entrée sur une unité logique ainsi que le nom du comportement décrit dans ce fichier (derrière la directive `@Behaviour`):

```
behav_mfront=CREA_LIB_MFRONT(UNITE_MFRONT=10, NOM_COMPOR="Lemaitre", )
```
  Ce mode de fonctionnement est à privilégier, notamment car il facilite l'utilisation dans AsterStudy. Pour plus d'informations, voir la documentation de [CREA_LIB_MFRONT](doc:u7.03.04). Il est notamment possible d'ajouter `DEBUG="OUI"` à la fin de la macro-commande CREA_LIB_MFRONT si l'utilisateur souhaite construire la bibliothèque en mode DEBUG.
2. **Pour les experts: construction de la bibliothèque à la main**
  Dans un terminal, il faut d'abord *compiler* le fichier MFront:

```
mfront --obuild --interface=generic Lemaitre.mfront
```
  Cela crée deux répertoires: `include` et `src`. Ce dernier contient en particulier la bibliothèque dynamique `libBehaviour.so`.
  Celle-ci doit ensuite être fournie en entrée sur une unité logique dans le macro-commande CREA_LIB_MFRONT, comme expliqué précédemment:

```
behav_mfront=CREA_LIB_MFRONT(UNITE_LIBRAIRIE=11, NOM_COMPOR="Lemaitre", )
```
  Enfin, notons qu'il est possible d'ajouter l'option `--debug` dans la ligne de commande `mfront` précédente si l'utilisateur souhaite construire la bibliothèque en mode DEBUG.

**Remarque:**

Les deux méthodes décrites précédemment sont exactement identiques d'un point de vue informatique, la première cachant à l'utilisateur la compilation du fichier MFront, réalisée *à la volée*. Dans les deux cas, la macro-commande [CREA_LIB_MFRONT](doc:u7.03.04) produit une structure de données `compor_mgis` qui pourra être utilisée plus tard dans le fichier de commandes.

### 1.3 Utilisation du comportement dans le fichier de commandes

L'utilisation du comportement MFront dans le fichier de commandes s'effectue de la façon suivante:

1. Les données matériaux sont fournies dans [DEFI_MATERIAU](doc:u4.43.01), sous le mot-clé MFRONT / MFRONT_FO. Par exemple, pour la loi de Lemaître (les unités sont ici en MPa pour `young` et `K`):

```
young=210000.0
poisson=0.3
Np=11.0
UN_SUR_K=0.00032840723
UN_SUR_M=0.178571429
mat_mfront=DEFI_MATERIAU(
    ELAS=_F(E=young, NU=poisson, ),
    MFRONT=_F(LISTE_COEF=(young, poisson, Np, UN_SUR_K, UN_SUR_M, ), ),
)
```
  Il est ici très important de noter que les valeurs de `LISTE_COEF(young, poisson, ...)` sont à donner **dans l'ordre** des directives `@MaterialProperties` du fichier MFront.

```
mfront-query --material-properties Lemaitre.mfront
```

**Remarque:**

Pour des utilisateurs avancés de MFront, il est possible de lister les propriétés matériaux d'un fichier MFront dans le bon ordre à l'aide de l'exécutable `mfront-query` via la commande:

2. Sous le mot-clé COMPORTEMENT des commandes de calcul non-linéaire [STAT_NON_LINE](doc:u4.51.03), [DYNA_NON_LINE](doc:u4.53.01), ou [SIMU_POINT_MAT](doc:u4.51.12):

```
sol_mfront=STAT_NON_LINE(
    MODELE=MO,
    CHAM_MATER=CMF,
    INCREMENT=_F(LIST_INST=L_INST, NUME_INST_FIN=5, ),
    NEWTON=_F(REAC_ITER=1),
    EXCIT=(_F(CHARGE=CH1), _F(CHARGE=CH2), ),
    ####################################
    COMPORTEMENT=_F(                   #
        RELATION="MFRONT",             #
        COMPOR_MFRONT=behav_mfront,    #
        RESI_INTE=1.0E-12,             #
        ITER_INTE_MAXI=100,            #
    ####################################
    ),
)
```
  Dans le cas où `RELATION="MFRONT"`, notons que seul le mot-clé COMPOR_MFRONT est obligatoire et que le nom prescrit (ici `behav_mfront`) doit être cohérent avec le nom utilisé en sortie de CREA_LIB_MFRONT pour construire la bibliothèque. Les deux autres mot-clés RESI_INTE et ITER_INTE_MAXI sont optionnels et leurs valeurs par défaut sont celles contenues dans le fichier MFront (respectivement via les directives `@Epsilon` et `@MaximumNumberOfIterations`). Les valeurs du fichier MFront ne sont surchargées que si le mot-clé correspondant est présent côté Aster.
  Ainsi, soit RESI_INTE est renseigné sous COMPORTEMENT et c'est alors la valeur prescrite qui est utilisée, soit c'est la valeur du paramètre `epsilon` du fichier MFront qui est utilisée. Cette dernière est automatiquement initialisée à `1.0e-8` lorsque qu'une méthode implicite est invoquée, et modifiable via la directive `@Epsilon` dans le fichier MFront. Mentionnons que l'utilisateur est informé si la valeur de RESI_INTE est plus grande que celle du paramètre `epsilon` de MFront.
  De manière similaire, la valeur fournie côté Aster pour ITER_INTE_MAXI vient écraser celle du paramètre `iterMax` dans le fichier MFront, sinon c'est cette dernière qui est utilisée par défaut. Côté MFront, elle est automatiquement initialisée à `100` lorsqu'une méthode implicite est invoquée et modifiable via la directive `@MaximumNumberOfIterations` (ou `@IterMax` bien qu'obsolète) dans le fichier MFront. L'utilisateur est informé si la valeur de ITER_INTE_MAXI est différente du paramètre `iterMax` de MFront.
  Dans le cas où RELATION='MFRONT', il est également possible d'ajouter sous [COMPORTEMENT](doc:u4.51.11) les autres mots-clés suivants:

  - VERI_BORNE ('ARRET' par défaut, sinon 'SANS' ou 'MESSAGE') permet de piloter le comportement de MFront dans le cas où la valeur d'un des paramètres matériaux dépasse des bornes spécifiées **à l'avance** dans le fichier MFront (via la directive `@Bounds`). Par défaut, l'intégration de la loi échoue, sinon l'erreur est passée sous silence, l'impression d'un message étant généré ou non côté MFront. Dans tous les cas, le code retour et le message d'erreur de MFront sont récupérés par **code_aster**.

**Remarque:**

Contrairement à la directive `@Bound` piloté par VERI_BORNE côté Aster, on mentionne que la directive `@PhysicalBounds` dans un fichier MFront entraîne automatiquement une erreur si le paramètre matériau associé dépasse les bornes prescrites (échec automatique de la loi de comportement).

  - SYME_MATR_TANG ('OUI' par défaut, sinon 'NON') permet de spécifier si la matrice de comportement est symétrique ou non.
  - ALGO_CPLAN ('DEBORST' par défaut, sinon 'ANALYTIQUE') permet de définir la modélisation dans le cas des contraintes planes (*cf.* U2.10.02-modelisations-disponibles).
  - DEFORMATION ('PETIT' par défaut, sinon GDEF_LOG) permet de préciser le type de petites déformations utilisées. Malheureusement, les U2.10.02-modeles-de-grandes-deformations ne sont actuellement plus accessibles pour les comportements issus d'un fichier MFront.
  - TOUT='OUI' (mot-clé par défaut) ou l'autre mot-clé habituel GROUP_MA pour prescrire un ou plusieurs groupes de mailles.
  - TYPE_MATR_TANG permet de vérifier la matrice tangente, calculée dans ce cas par MFront. La valeur 'PERTURBATION' permet de la remplacer par une matrice tangente perturbée tandis que 'VERIFICATION' va les comparer. On mentionne que VALE_PERT_RELA (`1.0e-5` par défaut) permet de préciser la valeur de la perturbation relative utilisée. On rappelle aussi qu'on peut utiliser RESI_RADI_RELA à la place de TYPE_MATR_TANG.
  Enfin, sous [COMPORTEMENT](doc:u4.51.11) dans le cas où RELATION='MFRONT', mentionnons que les mots-clés suivants sont ignorés:

  - ITER_INTE_PAS
  - ALGO_INTE
  - RIGI_GEOM
  - PARM_THETA
  - REGU_VISC
  ou exclu

  - POST_ITER
  - POST_INCR
  - COMPOR
  - NB_VARI
  - LIBRAIRIE
  - NOM_ROUTINE

Le reste du fichier de commandes est inchangé. Par exemple, si on utilise la loi de Lemaître définie dans `Lemaitre.mfront` pour le test ssna01a, on peut comparer les résultats avec ceux obtenus par la loi de LEMAITRE dans **code_aster**.

**Remarque:**

Lorsque la loi de comportement échoue côté MFront, un message d'erreur est généré et celui-ci est affiché par **code_aster**. En particulier, il se peut que la loi de comportement échoue pour une raison différente que la non-convergence de l'algorithme (division par zéro, racine d'un nombre négative ou paramètre matériau en dehors de ses bornes de validité par exemple). On se renvoit à l'aide à l'utilisation de MFront avec **code_aster** pour la gestion des arrêt anormaux de **code_aster** suite à un échec de l'intégration d'une loi de comportement MFront.

### 1.4 Modélisations disponibles

Les lois de comportement MFront sont utilisables nativement en 3D (et ses dérivés comme 3D_SI et 3D_INCO_* ), en déformations planes (D_PLAN_* ) et en axisymétrique (AXIS_* ). Pour le cas des contraintes planes (C_PLAN), il y a deux situations:

- soit on utilise le mode *contraintes planes* natif de MFront en sélectionnant ALGO_CPLAN='ANALYTIQUE' dans le mot-clef facteur COMPORTEMENT. Dans ce cas, le fichier MFront devra utiliser, suivant la valeur de la directive `@ModellingHypothesis`, l'intégrateur adéquat;
- soit on utilise [l'algorithme de De Borst](doc:r5.03.03) avec ALGO_CPLAN='DEBORST' dans le mot-clef facteur COMPORTEMENT. Dans ce cas, cela suppose que le fichier MFront est capable utiliser une modélisation de type axisymétrique.

**Remarque:**

Côté Aster, on rappelle que la convergence concernant la vérification de l'état des contraintes planes peut être dissociée de la convergence de l'algorithme de Newton grâce au mot-clé RESI_CPLAN_RELA (`1.0e-6` par défaut) ou RESI_CPLAN_MAXI pour le critère d'arrêt relative ou absolu respectivement, ainsi que ITER_CPLAN_MAXI (`10` par défaut) pour le nombre maximal d'itérations laissé à l'algorithme de De Borst au sein de chaque itération de l'algorithme de résolution des équations d'équilibre (schémas emboîtés).

Pour les comportements unidimensionnels (TUYAU_*, POU_D_EM et POU_D_TGM), il faut nécessairement utiliser l'algorithme de De Borst car MFront ne supporte pas ces modélisations.

### 1.6 Modèles de grandes déformations

Les modèles de grandes déformations GDEF_LOG et GREEN_LAGRANGE sont utilisables avec MFront. Le modèle SIMO_MIEHE ne l'est pas.

Le modèle GDEF_LOG de code_aster s'appuient nécessairement sur une loi écrite en petites déformations, il n'y a donc rien à faire de particulier dans le fichier MFront.

Le modèle GREEN_LAGRANGE est disponible avec MFront pour les modélisations 3D, D_PLAN, AXIS et leur équivalents sous-intégrés (3D_SI...).
Pour le modèle GREEN_LAGRANGE, il faudra choisir dans le fichier MFront le DSL `@DefaultFiniteStrain`.
Le fichier Mfront attendra alors le gradient de la transformation `F1` en entrée et devra produire la contrainte de Cauchy `sig` en sortie.
MFront fournit des routines utilitaires pour faire ces conversions au besoin.

### 1.7 Aide à l'utilisation de MFront avec code_aster

Souhaitant effectuer un calcul avec une loi de comportement issue d'un fichier MFront, il peut arriver qu'un utilisateur de **code_aster** soit confronté à un arrêt brutal et anormal de la simulation lors l'intégration de la loi de comportement avec un message d'erreur un peu désarmant de ce type:

```
╔══════════════════════════════════════════════════════════════╗
║ <EXCEPTION> <DVP_2>                                          ║
║                                                              ║
║ Erreur numérique (floating point exception).                 ║
║                                                              ║
║ --------------------------------------------                 ║
║ Contexte du message :                                        ║
║    Option         : FULL_MECA                                ║
║    Type d'élément : MECA_HEXA20                              ║
║    Maillage       : 00000001                                 ║
║    Maille         : M7425                                    ║
║    Type de maille : HEXA20                                   ║
║    Cette maille appartient aux groupes de mailles suivants : ║
║       VKCV                                                   ║
║    Position du centre de gravité de la maille :              ║
║       x=0.000035 y=0.000075 z=0.001500                       ║
║                                                              ║
║                                                              ║
║ Il y a probablement une erreur dans la programmation.        ║
║ Veuillez contacter votre assistance technique.               ║
╚══════════════════════════════════════════════════════════════╝
```

Face à ce type d'erreur DVP_2 côté Aster lors de l'intégration d'une loi MFront, plusieurs possibilités sont envisageables pour l'expliquer:

1. Le problème vient-il de l'écriture de la loi MFront et dans ce cas, faut-il se tourner vers son auteur ?
2. Est-ce un problème qui provient de la librarie MFront et dans ce cas, faut-il contacter les équipes de développement de MFront ?
3. Est-ce un problème dans l'interface entre **code_aster** et MFront et dans ce cas, faut-il ouvrir une fiche dans le REX de **code_aster** ?
4. Il y a-t-il des paramètres de [STAT_NON_LINE](doc:u4.51.03), [DYNA_NON_LINE](doc:u4.53.01), ou [SIMU_POINT_MAT](doc:u4.51.12) à adapter et dans ce cas, lesquels et comment?

Cependant, statistiquement, en regardant l'ensemble des fiches REX de **code_aster** ouvertes à ce sujet, une erreur en DVP_2 côté Aster lors de l'intégration d'une loi issue d'un fichier MFront provient presque sûrement de l'écriture de la loi de comportement, c'est à dire le problème (1) décrit ci-dessus. Autrement dit, il ne s'agit donc pas d'un problème d'interface, ni côté Aster, ni côté MFront mais très certainement d'un problème de rédaction de la loi.

Il semble ici opportun de rappeler qu'existe deux types d'erreurs informatiques:

- les arrêts normaux qui correspondent aux cas prévus par les développeurs, par exemple un échec de l'intégration de la loi de comportement MFront en un point de Gauss. Dans ce cas-là, **code_aster** récupère déjà le message d'erreur côté MFront, l'affiche et est capable de prendre des décisions (comme redécouper automatiquement le pas de temps) en fonction du code retour renvoyé par MFront. Les versions actuelles de **code_aster** tentent d'exploiter au maximum les informations *fines* de `mgis` renvoyées par MFront.
- les arrêts anormaux qui correspondent à des signaux spécifiques (`CTRL+C` ou floating point exception par exemple) qui peuvent certes être interceptés par le programme mais qui provoque généralement un arrêt soudain de celui-ci. On mentionne que des outils de *debug* intégré dans **code_aster** permettent de désigner la ligne où s'est produit ce type d'erreur (mode *debug* coché dans astk, ajout dans la commande DEBUT de l'option `ERREUR=_F(ERREUR_F='ABORT')` et/ou compilation séparée de la bibliothèque MFront avec l'option `CXXFLAGS="-g"`). Notons aussi au passage qu'il est tout à fait normal d'être désemparé devant un message d'erreur en arrêt anormal puisque justement, le programme ne s'arrête pas comme il devrait, même s'il concerne une opération algébrique basique comme une division par zéro.

De plus, si une étude est réalisée en utilisant à la fois **code_aster** et MFront, alors il semble nécessaire de maîtriser un minimum la syntaxe de **code_aster** et celle de MFront, tout en ayant un certain nombre d'informations sur la loi utilisée.

Nous détaillons maintenant un certain nombre de conseils et la démarche à adopter quand un utilisateur tombe sur une erreur DVP_2 dans **code_aster** suite à l'échec de l'intégration d'une loi de comportement MFront. Puisqu'il est quasiment certain que le problème vient de l'écriture de la loi de comportement MFront, on peut ainsi énoncer un certain nombre de vérifications de base à effectuer, en particulier si le calcul effectué avec **code_aster** échoue dès le début de l'intégration de la loi de comportement MFront:

- Si le fichier MFront utilise la directive [@Brick](https://thelfer.github.io/tfel/web/BehaviourBricks.html), alors il faut vérifier si les valeurs fournies sont correctes et cohérentes vis-à-vis du modèle considéré, comme en [élasto-visco-plasticité](https://thelfer.github.io/tfel/web/StandardElastoViscoPlasticityBrick.html).
- Vérifier que l'ordre des valeurs fournies dans **code_aster** pour les paramètres matériaux donnés dans [DEFI_MATERIAU](doc:u4.43.01) est le même que celui du fichier MFront. Par exemple, cela peut s'obtenir grâce à l'option `--material-properties` de l'outil `mfront-query`.
- Vérifier si les variables d'état externes réellement utilisées dans le fichier MFront via la directive `@ExternalStateVariable` (en particulier la température) sont bien définies dans le fichier de commande **code_aster**.
- Vérifier l'initialisation des variables dans le fichier MFront ainsi que l'ordre des variables d'état internes est correct (directives `@InternalStateVariable` et `@AuxiliaryStateVariable`). Il est également possible d'utiliser des `std::cout<<...<<std::endl;` pour afficher les variables. Afin de limiter la quantitié d'impressions dans le fichier de sortie, on peut ajouter des conditions ou se focaliser seulement sur la partie initialisation (directive `@InitLocalVariables`).

Si l'erreur DVP_2 persiste et/ou que le calcul échoue plus loin, il est alors très probable que le problème vienne de rédaction de la loi MFront et que la non-protection d'une opération algébrique soit en jeu (division par zéro, exponentielle d'un nombre positif trop élevé, racine d'un entier négatif, etc.). En général, la protection de telles opérations algébriques règlent le problème d'erreur en DVP_2.

Nous proposons maintenant une méthodologie pour effectuer un simulation d'étude avec **code_aster** interfacé avec une loi de comportement MFront. Cela pourra servir de base à un futur cahier des charges de tests des lois MFront utilisées dans **code_aster**. Il faut aussi bien comprendre qu'il s'agit d'une utilisation avancée qui nécessite un calcul compliqué avec deux outils interfacés différents. La stratégie consiste donc à aller du plus simple au plus compliqué dans de telles études.

#### 1.7.1 Est-il nécessaire d'utiliser MFront? Peut-on utiliser code_aster uniquement?

Ces deux questions peuvent paraître anodines mais il semble opportun de rappeler à l'utilisateur de regarder si la loi MFront qu'il souhaite utiliser n'est pas déjà disponible directement dans **code_aster**. En effet, il semble raisonnable de chercher à diminuer le nombre d'erreur potentielles et donc d'utiliser une loi sans interface, directement intégrée dans **code_aster**, sans passer par MFront, lorsque cela est possible bien sûr.

Et même si l'utilisateur souhaite absolument utiliser une loi de comportement MFront, avoir un fichier de commandes **code_aster** qui fonctionne avec une loi identique ou similaire permet de comparer les résultats avec celui utilisant MFront tout en s'assurant qu'une éventuelle non-convergence de l'algorithme provient bien de la non-linéarité de la loi et non d'autres phénomènes (contact, grandes déformations, etc.).

De plus, il est très probable que la documentation correspondante de **code_aster** fournissent des idées, des références et des cas-tests sur la meilleure façon de traiter numériquement la loi en question.

Et même dans le cas d'une étude utilisant uniquement **code_aster**, il faut y aller progressivement quand on travaille sur un calcul de structure, afin d'isoler les non-linéarités et les difficultés:

- tester la loi sur un point de Gauss en la *secouant* un peu;
- puis initier le calcul de structure en élastique sans contact, sans dépendance à thermique et en petites déformations;
- si cela se passe bien, on peut ajouter successivement et progressivement dans cet ordre la dépendance à la thermique, les grandes déformations puis le contact. On mentionne notamment la description des [bonnes pratiques](doc:u2.04.04) pour simuler le contact non-linéaire (avec ou sans friction).
- et si à la tout fin le calcul converge, alors on peut enfin ajouter la loi non-linéaire.

Enfin, si la structure est complexe géométriquement, il peut être également judicieux de commencer par des géométries plus simples.

Notons au passage que la désactivation de la singularité de la matrice est une mauvaise idée en général. Enfin, ne pas avoir travaillé avec MFront jusqu'ici permet d'isoler les problèmes et de se rendre compte déjà si la loi converge mal numériquement ou pas (i.e. si le résidu de la méthode de Newton ne décroît pas).

On rappelle que l'opérateur de prédiction durant le premier pas de temps est une élément central pour assurer la convergence quadratique de la méthode de Newton. Il peut être spécifié dans **code_aster** mais aussi directement dans MFront via la directive `@PredictionOperator`.

#### 1.7.2 Travailler le fichier MFront sur un point matériel avec mtest

Pour travailler avec MFront, il semble indispensable de créer un fichier `*.mtest` et d'effectuer plusieurs tentative de chargements ou déplacements pour voir et comprendre comment se comporte la loi non-linéaire que l'utilisateur souhaite utiliser sur un point matériel en premier lieu. Le fichier `Lemaitre.mtest` associé au fichier `Lemaitre.mfront` peut s'écrire de la manière suivante:

```
/* ************************************************************************** */
/* MTest case of Lemaitre behaviour law (cf. code_aster documentation         */
/*                                                      r5-03-08 for details) */
/*                                                                            */
/* To vizualize this MFront test on a material point (mtest):                 */
/*           mfront --obuild --interface=generic Lemaitre.mfront              */
/*           mtest Lemaitre.mtest                                             */
/*           gnuplot                                                          */
/*           plot "Lemaitre.res" using 2:8 with lines                         */
/*           exit                                                             */
/* ************************************************************************** */

@ModellingHypothesis "Tridimensional";

@Behaviour "src/libBehaviour.so" "Lemaitre";

@ExternalStateVariable "Temperature" 20.0;

@MaterialProperty<constant> "young" 210000.0; /* given in MPa here */
@MaterialProperty<constant> "poisson" 0.3;
@MaterialProperty<constant> "Np" 11.0;
@MaterialProperty<constant> "UN_SUR_K" 0.00032840723; /* given in MPa⁻1 here */
@MaterialProperty<constant> "UN_SUR_M" 0.178571429;

/*@Parameter "theta" 1.0;*/
/*@Parameter "epsilon" 1.0e-14;*/
/*@UnsignedIntegerParameter "iterMax" 200;*/

@ImposedStrain "EXX" {0:0.0, 1:1.0};
/*@ImposedStrain<function> "EXX" "1.e-3*t";*/
/*@ImposedStress "SXX" {0:0.0, 1:1.0e3};*/

@Times{0, 1 in 2000};
```

Ensuite, un certain nombre de recommandations pour écrire un fichier MFront peuvent être énoncée:

- Il est utile de lire un peu la [documentation MFront](https://thelfer.github.io/tfel/web/documentations.html) de base, notamment [celle](https://thelfer.github.io/tfel/web/documents/mfront/behaviours.pdf) sur l'écriture de loi de comportement.
- Il vaut mieux utiliser ce qui existe déjà pour minimiser les erreurs d'implémentations. Plus précisément, il s'agit de regarder si la loi ne rentre pas dans une [@Brick](https://thelfer.github.io/tfel/web/BehaviourBricks.html) déjà implémentée. Dans le cas des lois qui ne font intervenir que le tenseur des contraintes élastiques `eel` et un multiplicateur visco-plastique `p` comme variables d'états internes, il faut envisager d'utiliser la directive `@FlowRule` et:

- `@DSL IsotropicMisesCreep` pour des lois de type $\dot{p}=f(\Vert\sigma\Vert_{eq})$;
- `@DSL IsotropicPlasticMisesFlow` pour des lois de type $\dot{p}=f(\Vert\sigma\Vert_{eq},p)$;
- `@DSL IsotropicStrainHardeningMisesCreep` pour des lois de type $f(\Vert\sigma\Vert_{eq},p)<=0,~ \dot{p}>=0, ~ \dot{p}*f(\Vert\sigma\Vert_{eq},p)=0$;
- `@DSL MultipleIsotropicMisesFlows` pour des combinaisons des trois modèles de loi précédents.

> On est parfois obligé d'utiliser la directive `@DSL ImplicitII` (même chose que `@DSL Implicit` mais sans pré-définir `eel` comme variable d'état interne).

- Il est indispensable de documenter précisément sa loi dans le fichier MFront.
- L'ensemble des opérations algébriques doivent être protégées correctement. En particulier, un `if(a>0){b=1/a;}` ne protège rien du tout (par exemple si `a=1.0e-200`) et de même pour un `min(1,exp(x))` (par exemple si `x=1.0e10`). De plus, pour des puissances fractionnaires, on utilise plutôt le template `power<int,int>(real)` plutôt que la fonction `pow(real,real)`, comme cela est expliqué dans la [documentation associée](https://thelfer.github.io/tfel/web/tfel-math.html).
- Le calcul de la matrice jacobienne doit être calculé analytiquement. Son calcul par perturbations doit être réservé à des tests rapides sur un point matériel et pour vérifier que le calcul analytique est juste (directives `@CompareToNumericalJacobian`, `@JacobianComparisonCriterium` et `@PerturbationValueForNumericalJacobianComputation`). De même, le calcul de la matrice tangente cohérente doit être calculé le plus précisément possible, idéalement analytiquement (dans `mtest`, les directives `@CompareToNumericalTangentOperator`, `@TangentOperatorComparisonCriterium` et `@NumericalTangentOperatorPerturbationValue` permettent de vérifier que sa version analytique est correcte). On rappelle également que MFront offre une gestion conviviale des [tenseurs d'ordre deux et quatre](https://thelfer.github.io/tfel/web/tensors.html).
- Il est utile d'activer la vérification des dimensions physiques de grandeurs utilisées via la directive `@UseQt` true dans le fichier MFront. Cela impose de bien dimensionner les variables. On peut utiliser la [documentation](https://thelfer.github.io/tfel/web/mfront-types.html) pour s'aider.
- Il est nécessaire réfléchir aux bornes des paramètres physiques (directive `@PhysicalBounds`) et aux bornes du modèle (directive `@Bounds`) car ces variables vont communiquer avec l'extérieur du fichier MFront et les valeurs rentrées par un utilisateur peuvent être incohérentes.
- Ne pas mettre de constantes physiques en dur dans le code MFront mais plutôt utiliser la directive `@StaticVariable` (non modifiable), `@Parameter` (modifiable à l'execution) et `@IntegerConstant`, etc.
- Initialiser **toutes** les variables locales, faire attention aux variables inutilisées, et réduire au maximum le nombre d'inconnues implicites (directive `@StateVariable`), les autres grandeurs d'intérêt étant mis à jour explicitement via les directives `@AuxiliaryStateVariable` et `@UpdateAuxiliaryStateVariables`. On rappelle que le choix du point de départ pour la méthode de Newton détermine fortement la vitesse de convergence et la convergence de l'algorithme. Il peut donc être utile de comprendre s'il y a un meilleur point de départ que zéro. C'est d'ailleurs parfois un très mauvais point de départ et une initialisation correcte est nécessaitre durant la phase de prédiction (directive `@Predictor`).
- Quand un fichier MFront est voué à être utilisé avec **code_aster**, il est nécessaire de ne pas faire dépendre les paramètres matériaux des unités choisies. Un façon rapide consiste généralement à ajouter des paramètres matériaux `LengthUnit` et `StressUnit` puis de le tester sur un fichier mtest. Parfois, le changement d'unités (MPa au lieu de Pa par exemple) peut mieux conditionner la matrice et faire mieux converger l'algorithme de Newton global.

Si la simulation sur un point matériel d'une loi MFront ne se passe pas correctement avec `mtest`, par exemple un problème de convergence de la loi comme c'est être souvent le cas, alors il n'y a généralement aucune chance que l'interfaçage avec **code_aster** se passe mieux.

#### 1.7.3 Travailler le fichier MFront avec code_aster

Une fois que l'étape précédente fonctionne, il semble pertinent de continuer à y aller progressivement dans la mise en place de l'étude. On teste donc la loi MFront dans **code_aster** mais d'abord sur un point matériel avec la commande [SIMU_POINT_MAT](doc:u4.51.12) en la secouant un peu, puis en ajoutant progressivement des complexités.

Si cette étape plante ou ne converge pas, alors il repasser à l'étape précédente. En effet, il est facile de transposer l'étude SIMU_POINT_MAT dans `mtest`.

Enfin, dans le cas où le calcul **code_aster** converge sur un point matériel, on peut alors commencer à travailler sur un vrai calcul de structure, en y allant progressivement afin d'isoler les différents types de non-linéarités et les difficultés:

- Initier le calcul de structure en élastique sans contact, sans dépendance à thermique et en petites déformations.
- Si cela se passe bien, on peut ajouter successivement et progressivement dans cet ordre la dépendance à la thermique, les grandes déformations puis le contact. On mentionne notamment la description des [bonnes pratiques](doc:u2.04.04) pour simuler le contact non-linéaire (avec ou sans friction).
- Si à la tout fin le calcul converge, alors on peut enfin ajouter la loi non-linéaire issue de MFront grâce à la commande CREA_LIB_MFRONT.

Enfin, si la structure est complexe géométriquement, il peut être judicieux et commencer par des géométries plus simples.

Notons au passage que la désactivation de la singularité de la matrice est une mauvaise idéee en général. On rappelle aussi que l'opérateur de prédiction durant le premier pas de temps est un
élément central pour assurer la convergence quadratique de la méthode de Newton. Il peut être spécifié dans **code_aster** mais aussi directement dans MFront via la directive `@PredictionOperator`.

Pour conclure, il faut aussi être humble vis-à-vis des résultats numériques obtenus et bien se rappeler que certains phénomènes mécaniques sont très difficiles à simuler numériquement. Par conséquent, il est normal qu'une loi ait du mal à converger, a fortiori si on mélange plusieurs types de
non-linéarités. Cela nécessite donc de bien comprendre les mécanismes physiques et numériques sous-jacents. En particulier, y aller progressivement est donc nécessaire, ne serait-ce que pour se rendre compte que le problème de convergence ne vient peut être pas de la loi mais de la simulation de la
thermique, des grandes déformations ou du contact.

## 2 Exemples d'utilisation

D'autres exemples sont fournis dans la [galerie de MFront](https://thelfer.github.io/tfel/web/gallery.html).

Les cas-tests [mfron01](doc:v1.03.126), [mfron02](doc:v1.03.127), [mfron03](doc:v1.03.128), [mfron05](doc:v1.03.130) et [mfron06](doc:v1.03.132) permettent de vérifier le mot-clé RELATION='MFRONT', avec un fichier MFront fourni en donnée du test.

**Remarque:**

Les tutoriels et informations concernant l'interface entre **code_aster** et MFront issues du [nouveau site MFront](https://thelfer.github.io/tfel/web/index.html) et de [l'ancien](https://tfel.sourceforge.net) décrivent l'ancienne manière dont **code_aster** communiquait avec MFront. Depuis la version 16.3.13, **code_aster** n'utilise plus l'interface historique (option `--interface=aster` dans la ligne de commande MFront) mais l'interface générique (option `--interface=generic`) via son support appelé [MGIS](https://thelfer.github.io/mgis/web/index.html).

En particulier, l'option `--@AsterGenerateMtestFileOnFailure=true` n'est plus disponible durant la compilation du fichier Mfront. Elle permettait de récupérer automatiquement les données de simulation de **code_aster** sur un point matériel (fichier `*.mtest` ) lorsque l'intégration échouait sur celui-ci. L'interface actuelle dispose bien d'une directive équivalente (`--@GenerateMTestFileOnFailure=true`) mais son utilisation est inutile et à proscrire car d'une part, le calcul va prendre beaucoup plus de temps (écriture d'un fichier `*.mtest` différent en chaque point de Gauss à chaque calcul), d'espace mémoire (avec le risque d'erreur **code_aster** par saturation, impossible d'ouvrir ou écrire sur un fichier), et d'autre part, tous ces fichiers `*.mtest` seront supprimés du répertoire temporaire à la fin du calcul de **code_aster**.
