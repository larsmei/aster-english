# u4.11.02 Command FIN

## 1 Purpose

This command terminates the execution of an analysis cleanly. In this way, one tells the memory manager that the objects may be released and written to disk in the global database (and a restart, POURSUITE, made possible).

The call to this procedure is **mandatory** for the execution to finish correctly, which requires every command file to end with:

```python
FIN()
```

## 2 Syntax

```text
FIN(
    ◇ RETASSAGE = / "NON" (par défaut),
                  / "OUI",
    ◇ INFO_BASE = / "NON",
                  / "OUI",
    ◇ INFO_RESU = / "NON" (par défaut),
                  / "OUI",
)

◆ : obligatoire
◇ : optionnel
⟐ : présent par défaut
& : ensemble
/ : un seul parmi
| : plusieurs choix possibles
```

## 3 Operands

The command FIN saves all the concepts computed during the execution in the file `glob.1` (and possibly `glob.2`, ... if necessary), as well as all the Python objects of the execution context in *pickle* files. These objects will be available for a restart (POURSUITE) of the analysis.

If the user has not asked for the database to be copied after the analysis (there is no database in the `.export` file of the study), FIN will do nothing.

**Note**

Python objects of class, function and type kinds are not saved in the file :file:`pick.codeaster.objects`.

When FIN has finished its work, Python continues to analyse the instructions that follow, and these will certainly fail if they call code_aster objects.

The developer may use `FIN(exit=True)` to force an exit from the Python interpreter.

### 3.1 Keyword RETASSAGE

Causes the 'GLOBALE' database to be repacked before it is written to the associated file. This makes it possible to keep smaller databases (cleared of the objects associated with the concepts destroyed by the user).

This repacking is carried out by the command as follows:

- closure of the databases,
- opening of the 'GLOBALE' database,
- opening of a 'VOLATILE' database,
- copy, non-empty record by non-empty record, of the 'GLOBALE' database onto the 'VOLATILE' database,
- renaming by the code of this 'VOLATILE' database so that it is saved as if it were the standard 'GLOBALE' database.

The GLOBALE database consists of one or more binary files organised as fixed-length records. During destruction operations, the associated records are declared free and may possibly be reused during the run. At the end of the run, unoccupied records may remain and contribute to the final size of the file. The repacking operation therefore consists in reusing this space by reorganising the records. It is an operation that can lead to a large number of disk reads and writes.

In a standard parallel run (MPI), in "centralised" mode, each instance of the GLOBALE database is processed, which multiplies the input/output.
In distributed mode, each instance manages its own input/output according to its needs.

### 3.2 Keyword INFO_RESU

Causes information relating to the content of all the result data structures stored in the GLOBALE database to be printed in the MESSAGE file.

**Note:**

Use of this keyword can considerably increase the execution time of the command FIN and produce very large output files. For this reason, it is not activated by default.

### 3.3 Keyword INFO_BASE

This keyword makes it possible to print, in the MESSAGE file, the list of objects present in the global database together with their size.
When the database is saved, the printout is produced automatically.
Otherwise, this keyword can be activated in order to display the list.
