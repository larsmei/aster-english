# u2.10.02 User's guide to MFront with code_aster

**Summary:**

The use of the coupling between **code_aster** and the constitutive-law integration module [MFront](https://thelfer.github.io/tfel/web/index.html) is described here. MFront is distributed as Open Source under the GPL and CECILL-A licences.

MFront makes it possible to define a constitutive law in a simple way, close to the physical equations, without having to concern oneself with the solution methods. It offers classes for manipulating data (tensors, for example) in a convenient way and provides efficient algorithms, in terms of performance, for solving the associated non-linear equations. MFront is suited both to implicit and to explicit time schemes.

These constitutive behaviours can be used in **code_aster** for the 3D and 2D modellings, shells, THM and for the joint elements. Large strains can be used with GDEF_LOG. Moreover, MFront produces efficient code, because the tensor operations are optimised, as shown by the *benchmarks* carried out with equivalent constitutive behaviours of **code_aster**.

It must be clearly noted that the use of these *custom* constitutive laws (keyword RELATION='MFRONT' under [COMPORTEMENT](doc:u4.51.11)) implies a specific validation for the study envisaged, because one places oneself outside the qualified domain of **code_aster**.

This document describes how to use a constitutive behaviour defined by the user with the help of MFront in a **code_aster** command file.

## 1 Definition of a constitutive law with MFront

### 1.1 Writing an MFront constitutive behaviour

One writes the constitutive law in the MFront file, following the advice given in the tutorial [bib1]_, or by drawing on a constitutive behaviour already available in the tests of **code_aster** (*cf.* U2.10.02-exemples-d-utilisation).

We shall take here as an example the viscoplastic constitutive behaviour of Lemaître written in implicit form. The file `Lemaitre.mfront` is written:

```
@DSL Implicit;
@Behaviour Lemaitre;
@Author EDF R&D ERMES;
@Date 25/03/2024;
@Description{
    Lemaitre viscoelastic behaviour law (cf. code_aster documentation r5-03-08 for details):
    eto=eel+dp_dt*nv,
    sig=D:eel,
    nv=1.5*dev(sig)/seq,
    dot(p)=((1/K)*seq/p^(1/M))^Np;
}

@Algorithm NewtonRaphson_NumericalJacobian;
@Theta 0.5;
@Epsilon 1.0e-12;
@MaximumNumberOfIterations 100;

@UseQt true;
@MaterialProperty stress young;
@MaterialProperty real poisson;
@MaterialProperty real Np;
@MaterialProperty result_type<real,stress,OpDiv> UN_SUR_K;
@MaterialProperty real UN_SUR_M;

@StateVariable real p;

@LocalVariable StiffnessTensor Dv;

@InitLocalVariables{
    const auto lambda=computeLambda(young,poisson);
    const auto mu=computeMu(young,poisson);
    Dv=lambda*Stensor4::IxI()+real(2.0)*mu*Stensor4::Id();
}

@ComputeStress{
    sig=Dv*eel;
}

@Integrator{
    const auto seq=sigmaeq(sig);
    const auto p_mts=max(p+theta*dp,real(1.0e-8));
    const auto slem=seq*UN_SUR_K/pow(p_mts,UN_SUR_M);
    const auto vp=frequency(1.0)*pow(slem,Np);
    const auto iseq=real(1.0)/max(seq,young*real(1.e-14));
    const auto n=real(1.5)*deviator(sig)*iseq;
    feel+=vp*dt*n;
    feel-=deto;
    fp-=vp*dt;
}

@TangentOperator{
    Stensor4 Je;
    getPartialJacobianInvert(Je);
    Dt=Dv*Je;
}
```

This law is equivalent to the law LEMAITRE, available in **code_aster**.

### 1.2 Creation of the dynamic library from an MFront constitutive behaviour

In order to be usable in **code_aster**, the MFront constitutive behaviour programmed in this way must be transformed into a dynamic library. For this, it must be *compiled*. This can be done in two different ways.

1. **Recommended solution: use of CREA_LIB_MFRONT**
  The macro-command CREA_LIB_MFRONT makes it possible to build the library automatically. It is sufficient to supply the MFront file as input on a logical unit as well as the name of the constitutive behaviour described in this file (behind the directive `@Behaviour`):

```
behav_mfront=CREA_LIB_MFRONT(UNITE_MFRONT=10, NOM_COMPOR="Lemaitre", )
```
  This mode of operation is to be preferred, in particular because it facilitates the use in AsterStudy. For further information, see the documentation of [CREA_LIB_MFRONT](doc:u7.03.04). It is in particular possible to add `DEBUG="OUI"` at the end of the macro-command CREA_LIB_MFRONT if the user wishes to build the library in DEBUG mode.
2. **For experts: building the library by hand**
  In a terminal, one must first *compile* the MFront file:

```
mfront --obuild --interface=generic Lemaitre.mfront
```
  This creates two directories: `include` and `src`. The latter contains in particular the dynamic library `libBehaviour.so`.
  This library must then be supplied as input on a logical unit in the macro-command CREA_LIB_MFRONT, as explained previously:

```
behav_mfront=CREA_LIB_MFRONT(UNITE_LIBRAIRIE=11, NOM_COMPOR="Lemaitre", )
```
  Finally, note that it is possible to add the option `--debug` in the preceding `mfront` command line if the user wishes to build the library in DEBUG mode.

**Note:**

The two methods described previously are exactly identical from a computing point of view, the first hiding from the user the compilation of the MFront file, carried out *on the fly*. In both cases, the macro-command [CREA_LIB_MFRONT](doc:u7.03.04) produces a data structure `compor_mgis` which can be used later in the command file.

### 1.3 Use of the constitutive behaviour in the command file

The use of the MFront constitutive behaviour in the command file is carried out in the following way:

1. The material data are supplied in [DEFI_MATERIAU](doc:u4.43.01), under the keyword MFRONT / MFRONT_FO. For example, for the Lemaître law (the units are here in MPa for `young` and `K`):

```
young=210000.0
poisson=0.3
Np=11.0
UN_SUR_K=0.00032840723
UN_SUR_M=0.178571429
mat_mfront=DEFI_MATERIAU(
    ELAS=_F(E=young, NU=poisson, ),
    MFRONT=_F(LISTE_COEF=(young, poisson, Np, UN_SUR_K, UN_SUR_M, ), ),
)
```
  It is very important to note here that the values of `LISTE_COEF(young, poisson, ...)` are to be given **in the order** of the `@MaterialProperties` directives of the MFront file.

```
mfront-query --material-properties Lemaitre.mfront
```

**Note:**

For advanced users of MFront, it is possible to list the material properties of an MFront file in the correct order with the help of the executable `mfront-query` via the command:

2. Under the keyword COMPORTEMENT of the non-linear analysis commands [STAT_NON_LINE](doc:u4.51.03), [DYNA_NON_LINE](doc:u4.53.01), or [SIMU_POINT_MAT](doc:u4.51.12):

```
sol_mfront=STAT_NON_LINE(
    MODELE=MO,
    CHAM_MATER=CMF,
    INCREMENT=_F(LIST_INST=L_INST, NUME_INST_FIN=5, ),
    NEWTON=_F(REAC_ITER=1),
    EXCIT=(_F(CHARGE=CH1), _F(CHARGE=CH2), ),
    ####################################
    COMPORTEMENT=_F(                   #
        RELATION="MFRONT",             #
        COMPOR_MFRONT=behav_mfront,    #
        RESI_INTE=1.0E-12,             #
        ITER_INTE_MAXI=100,            #
    ####################################
    ),
)
```
  In the case where `RELATION="MFRONT"`, note that only the keyword COMPOR_MFRONT is mandatory and that the prescribed name (here `behav_mfront`) must be consistent with the name used as the output of CREA_LIB_MFRONT in order to build the library. The other two keywords RESI_INTE and ITER_INTE_MAXI are optional and their default values are those contained in the MFront file (respectively via the directives `@Epsilon` and `@MaximumNumberOfIterations`). The values of the MFront file are overloaded only if the corresponding keyword is present on the Aster side.
  Thus, either RESI_INTE is entered under COMPORTEMENT and it is then the prescribed value which is used, or it is the value of the parameter `epsilon` of the MFront file which is used. The latter is automatically initialised to `1.0e-8` when an implicit method is invoked, and can be modified via the directive `@Epsilon` in the MFront file. It should be mentioned that the user is informed if the value of RESI_INTE is larger than that of the parameter `epsilon` of MFront.
  In a similar way, the value supplied on the Aster side for ITER_INTE_MAXI overwrites that of the parameter `iterMax` in the MFront file; otherwise it is the latter which is used by default. On the MFront side, it is automatically initialised to `100` when an implicit method is invoked and can be modified via the directive `@MaximumNumberOfIterations` (or `@IterMax`, although obsolete) in the MFront file. The user is informed if the value of ITER_INTE_MAXI is different from the parameter `iterMax` of MFront.
  In the case where RELATION='MFRONT', it is also possible to add under [COMPORTEMENT](doc:u4.51.11) the following other keywords:

  - VERI_BORNE ('ARRET' by default, otherwise 'SANS' or 'MESSAGE') makes it possible to control the behaviour of MFront in the case where the value of one of the material parameters exceeds bounds specified **in advance** in the MFront file (via the directive `@Bounds`). By default, the integration of the law fails; otherwise the error is passed over in silence, the printing of a message being generated or not on the MFront side. In every case, the return code and the error message of MFront are recovered by **code_aster**.

**Note:**

Unlike the directive `@Bound` controlled by VERI_BORNE on the Aster side, it is mentioned that the directive `@PhysicalBounds` in an MFront file automatically leads to an error if the associated material parameter exceeds the prescribed bounds (automatic failure of the constitutive law).

  - SYME_MATR_TANG ('OUI' by default, otherwise 'NON') makes it possible to specify whether the constitutive matrix is symmetric or not.
  - ALGO_CPLAN ('DEBORST' by default, otherwise 'ANALYTIQUE') makes it possible to define the modelling in the case of plane stresses (*cf.* U2.10.02-modelisations-disponibles).
  - DEFORMATION ('PETIT' by default, otherwise GDEF_LOG) makes it possible to specify the type of small strains used. Unfortunately, the U2.10.02-modeles-de-grandes-deformations are at present no longer accessible for the constitutive behaviours coming from an MFront file.
  - TOUT='OUI' (default keyword) or the other usual keyword GROUP_MA in order to prescribe one or more mesh-cell groups.
  - TYPE_MATR_TANG makes it possible to check the tangent matrix, computed in this case by MFront. The value 'PERTURBATION' makes it possible to replace it by a perturbed tangent matrix, whereas 'VERIFICATION' will compare them. It is mentioned that VALE_PERT_RELA (`1.0e-5` by default) makes it possible to specify the value of the relative perturbation used. It is also recalled that one can use RESI_RADI_RELA in place of TYPE_MATR_TANG.
  Finally, under [COMPORTEMENT](doc:u4.51.11) in the case where RELATION='MFRONT', it is mentioned that the following keywords are ignored:

  - ITER_INTE_PAS
  - ALGO_INTE
  - RIGI_GEOM
  - PARM_THETA
  - REGU_VISC
  or excluded

  - POST_ITER
  - POST_INCR
  - COMPOR
  - NB_VARI
  - LIBRAIRIE
  - NOM_ROUTINE

The rest of the command file is unchanged. For example, if one uses the Lemaître law defined in `Lemaitre.mfront` for the test ssna01a, one can compare the results with those obtained by the law LEMAITRE in **code_aster**.

**Note:**

When the constitutive law fails on the MFront side, an error message is generated and this message is displayed by **code_aster**. In particular, it may be that the constitutive law fails for a reason other than the non-convergence of the algorithm (division by zero, root of a negative number or material parameter outside its bounds of validity, for example). One is referred to the help on the use of MFront with **code_aster** for the handling of abnormal stops of **code_aster** following a failure of the integration of an MFront constitutive law.

### 1.4 Available modellings

The MFront constitutive laws can be used natively in 3D (and its derivatives such as 3D_SI and 3D_INCO_* ), in plane strain (D_PLAN_* ) and in axisymmetric (AXIS_* ). For the case of plane stress (C_PLAN), there are two situations:

- either one uses the native *plane stress* mode of MFront by selecting ALGO_CPLAN='ANALYTIQUE' in the factor keyword COMPORTEMENT. In this case, the MFront file will have to use, according to the value of the directive `@ModellingHypothesis`, the appropriate integrator;
- or one uses [the De Borst algorithm](doc:r5.03.03) with ALGO_CPLAN='DEBORST' in the factor keyword COMPORTEMENT. In this case, this assumes that the MFront file is capable of using a modelling of axisymmetric type.

**Note:**

On the Aster side, it is recalled that the convergence concerning the verification of the plane-stress state can be dissociated from the convergence of the Newton algorithm thanks to the keyword RESI_CPLAN_RELA (`1.0e-6` by default) or RESI_CPLAN_MAXI for the relative or absolute stopping criterion respectively, as well as ITER_CPLAN_MAXI (`10` by default) for the maximum number of iterations left to the De Borst algorithm within each iteration of the algorithm for solving the equilibrium equations (nested schemes).

For the one-dimensional constitutive behaviours (TUYAU_*, POU_D_EM and POU_D_TGM), it is necessary to use the De Borst algorithm because MFront does not support these modellings.

### 1.6 Large-strain models

The large-strain models GDEF_LOG and GREEN_LAGRANGE can be used with MFront. The model SIMO_MIEHE cannot.

The model GDEF_LOG of code_aster necessarily relies on a law written in small strains; there is therefore nothing particular to do in the MFront file.

The model GREEN_LAGRANGE is available with MFront for the modellings 3D, D_PLAN, AXIS and their under-integrated equivalents (3D_SI...).
For the model GREEN_LAGRANGE, one will have to choose in the MFront file the DSL `@DefaultFiniteStrain`.
The Mfront file will then expect the transformation gradient `F1` as input and will have to produce the Cauchy stress `sig` as output.
MFront provides utility routines in order to carry out these conversions if need be.

### 1.7 Help on the use of MFront with code_aster

Wishing to carry out an analysis with a constitutive law coming from an MFront file, it can happen that a user of **code_aster** is confronted with a sudden and abnormal stop of the simulation during the integration of the constitutive law, with a somewhat disconcerting error message of this type:

```
╔══════════════════════════════════════════════════════════════╗
║ <EXCEPTION> <DVP_2>                                          ║
║                                                              ║
║ Erreur numérique (floating point exception).                 ║
║                                                              ║
║ --------------------------------------------                 ║
║ Contexte du message :                                        ║
║    Option         : FULL_MECA                                ║
║    Type d'élément : MECA_HEXA20                              ║
║    Maillage       : 00000001                                 ║
║    Maille         : M7425                                    ║
║    Type de maille : HEXA20                                   ║
║    Cette maille appartient aux groupes de mailles suivants : ║
║       VKCV                                                   ║
║    Position du centre de gravité de la maille :              ║
║       x=0.000035 y=0.000075 z=0.001500                       ║
║                                                              ║
║                                                              ║
║ Il y a probablement une erreur dans la programmation.        ║
║ Veuillez contacter votre assistance technique.               ║
╚══════════════════════════════════════════════════════════════╝
```

Faced with this type of error DVP_2 on the Aster side during the integration of an MFront law, several possibilities can be envisaged in order to explain it:

1. Does the problem come from the writing of the MFront law and, in this case, should one turn to its author?
2. Is it a problem which comes from the MFront library and, in this case, should one contact the MFront development teams?
3. Is it a problem in the interface between **code_aster** and MFront and, in this case, should one open a sheet in the REX of **code_aster**?
4. Are there parameters of [STAT_NON_LINE](doc:u4.51.03), [DYNA_NON_LINE](doc:u4.53.01), or [SIMU_POINT_MAT](doc:u4.51.12) to be adapted and, in this case, which ones and how?

However, statistically, looking at all the REX sheets of **code_aster** opened on this subject, an error in DVP_2 on the Aster side during the integration of a law coming from an MFront file almost certainly comes from the writing of the constitutive law, that is to say problem (1) described above. In other words, it is therefore not an interface problem, neither on the Aster side nor on the MFront side, but very certainly a problem in the drafting of the law.

It seems opportune here to recall that there exist two types of computing errors:

- the normal stops, which correspond to the cases foreseen by the developers, for example a failure of the integration of the MFront constitutive law at a Gauss point. In that case, **code_aster** already recovers the error message on the MFront side, displays it and is capable of taking decisions (such as automatically subdividing the time step) according to the return code sent back by MFront. The current versions of **code_aster** attempt to exploit to the maximum the *fine* information of `mgis` sent back by MFront.
- the abnormal stops, which correspond to specific signals (`CTRL+C` or floating point exception for example) which can certainly be intercepted by the program but which generally cause a sudden stop of the latter. It is mentioned that *debug* tools integrated in **code_aster** make it possible to designate the line where this type of error occurred (*debug* mode ticked in astk, addition in the command DEBUT of the option `ERREUR=_F(ERREUR_F='ABORT')` and/or separate compilation of the MFront library with the option `CXXFLAGS="-g"`). Let us also note in passing that it is entirely normal to be at a loss in front of an error message in an abnormal stop, since precisely the program does not stop as it should, even if it concerns a basic algebraic operation such as a division by zero.

Moreover, if a study is carried out using both **code_aster** and MFront, then it seems necessary to master at least the syntax of **code_aster** and that of MFront, while having a certain amount of information on the law used.

We now detail a certain number of pieces of advice and the approach to be adopted when a user comes across an error DVP_2 in **code_aster** following the failure of the integration of an MFront constitutive law. Since it is almost certain that the problem comes from the writing of the MFront constitutive law, one can thus state a certain number of basic checks to be carried out, in particular if the analysis carried out with **code_aster** fails right from the beginning of the integration of the MFront constitutive law:

- If the MFront file uses the directive [@Brick](https://thelfer.github.io/tfel/web/BehaviourBricks.html), then one must check whether the values supplied are correct and consistent with respect to the model considered, as in [elasto-visco-plasticity](https://thelfer.github.io/tfel/web/StandardElastoViscoPlasticityBrick.html).
- Check that the order of the values supplied in **code_aster** for the material parameters given in [DEFI_MATERIAU](doc:u4.43.01) is the same as that of the MFront file. For example, this can be obtained thanks to the option `--material-properties` of the tool `mfront-query`.
- Check whether the external state variables actually used in the MFront file via the directive `@ExternalStateVariable` (in particular the temperature) are indeed defined in the **code_aster** command file.
- Check the initialisation of the variables in the MFront file and that the order of the internal state variables is correct (directives `@InternalStateVariable` and `@AuxiliaryStateVariable`). It is also possible to use `std::cout<<...<<std::endl;` in order to display the variables. In order to limit the quantity of printouts in the output file, one can add conditions or focus only on the initialisation part (directive `@InitLocalVariables`).

If the error DVP_2 persists and/or the analysis fails further on, it is then very probable that the problem comes from the drafting of the MFront law and that the lack of protection of an algebraic operation is involved (division by zero, exponential of a positive number that is too large, root of a negative integer, etc.). In general, the protection of such algebraic operations settles the problem of the error in DVP_2.

We now propose a methodology for carrying out a study simulation with **code_aster** interfaced with an MFront constitutive law. This will be able to serve as a basis for a future specification of tests of the MFront laws used in **code_aster**. One must also understand clearly that this is an advanced use which requires a complicated analysis with two different interfaced tools. The strategy therefore consists in going from the simplest to the most complicated in such studies.

#### 1.7.1 Is it necessary to use MFront? Can one use code_aster only?

These two questions may appear trivial, but it seems opportune to remind the user to look at whether the MFront law that he or she wishes to use is not already available directly in **code_aster**. Indeed, it seems reasonable to seek to reduce the number of potential errors and therefore to use a law without an interface, integrated directly in **code_aster**, without going through MFront, when this is possible of course.

And even if the user absolutely wishes to use an MFront constitutive law, having a **code_aster** command file which works with an identical or similar law makes it possible to compare the results with the one using MFront, while making sure that a possible non-convergence of the algorithm does indeed come from the non-linearity of the law and not from other phenomena (contact, large strains, etc.).

Moreover, it is very probable that the corresponding documentation of **code_aster** provides ideas, references and test cases on the best way of treating the law in question numerically.

And even in the case of a study using only **code_aster**, one must proceed gradually when one works on a structural analysis, in order to isolate the non-linearities and the difficulties:

- test the law on a Gauss point by *shaking* it a little;
- then start the structural analysis in elasticity without contact, without dependence on the thermal field and in small strains;
- if this goes well, one can add successively and gradually, in this order, the dependence on the thermal field, the large strains and then the contact. One mentions in particular the description of the [good practice](doc:u2.04.04) for simulating non-linear contact (with or without friction).
- and if at the very end the analysis converges, then one can finally add the non-linear law.

Finally, if the structure is geometrically complex, it may also be judicious to start with simpler geometries.

Let us note in passing that deactivating the singularity of the matrix is a bad idea in general. Finally, not having worked with MFront up to this point makes it possible to isolate the problems and to realise already whether the law converges poorly numerically or not (i.e. whether the residual of the Newton method does not decrease).

It is recalled that the prediction operator during the first time step is a central element for ensuring the quadratic convergence of the Newton method. It can be specified in **code_aster** but also directly in MFront via the directive `@PredictionOperator`.

#### 1.7.2 Working on the MFront file on a material point with mtest

In order to work with MFront, it seems indispensable to create a file `*.mtest` and to carry out several attempts at loadings or displacements in order to see and understand how the non-linear law that the user wishes to use behaves, on a material point in the first place. The file `Lemaitre.mtest` associated with the file `Lemaitre.mfront` can be written in the following way:

```
/* ************************************************************************** */
/* MTest case of Lemaitre behaviour law (cf. code_aster documentation         */
/*                                                      r5-03-08 for details) */
/*                                                                            */
/* To vizualize this MFront test on a material point (mtest):                 */
/*           mfront --obuild --interface=generic Lemaitre.mfront              */
/*           mtest Lemaitre.mtest                                             */
/*           gnuplot                                                          */
/*           plot "Lemaitre.res" using 2:8 with lines                         */
/*           exit                                                             */
/* ************************************************************************** */

@ModellingHypothesis "Tridimensional";

@Behaviour "src/libBehaviour.so" "Lemaitre";

@ExternalStateVariable "Temperature" 20.0;

@MaterialProperty<constant> "young" 210000.0; /* given in MPa here */
@MaterialProperty<constant> "poisson" 0.3;
@MaterialProperty<constant> "Np" 11.0;
@MaterialProperty<constant> "UN_SUR_K" 0.00032840723; /* given in MPa⁻1 here */
@MaterialProperty<constant> "UN_SUR_M" 0.178571429;

/*@Parameter "theta" 1.0;*/
/*@Parameter "epsilon" 1.0e-14;*/
/*@UnsignedIntegerParameter "iterMax" 200;*/

@ImposedStrain "EXX" {0:0.0, 1:1.0};
/*@ImposedStrain<function> "EXX" "1.e-3*t";*/
/*@ImposedStress "SXX" {0:0.0, 1:1.0e3};*/

@Times{0, 1 in 2000};
```

Next, a certain number of recommendations for writing an MFront file can be stated:

- It is useful to read a little of the basic [MFront documentation](https://thelfer.github.io/tfel/web/documentations.html), in particular [that](https://thelfer.github.io/tfel/web/documents/mfront/behaviours.pdf) on the writing of a constitutive law.
- It is better to use what already exists in order to minimise implementation errors. More precisely, this means looking at whether the law does not fall within an [@Brick](https://thelfer.github.io/tfel/web/BehaviourBricks.html) already implemented. In the case of laws which involve only the elastic stress tensor `eel` and a viscoplastic multiplier `p` as internal state variables, one must consider using the directive `@FlowRule` and:

- `@DSL IsotropicMisesCreep` for laws of the type $\dot{p}=f(\Vert\sigma\Vert_{eq})$;
- `@DSL IsotropicPlasticMisesFlow` for laws of the type $\dot{p}=f(\Vert\sigma\Vert_{eq},p)$;
- `@DSL IsotropicStrainHardeningMisesCreep` for laws of the type $f(\Vert\sigma\Vert_{eq},p)<=0,~ \dot{p}>=0, ~ \dot{p}*f(\Vert\sigma\Vert_{eq},p)=0$;
- `@DSL MultipleIsotropicMisesFlows` for combinations of the three preceding law models.

> One is sometimes obliged to use the directive `@DSL ImplicitII` (the same thing as `@DSL Implicit` but without pre-defining `eel` as an internal state variable).

- It is indispensable to document one's law precisely in the MFront file.
- All the algebraic operations must be protected correctly. In particular, an `if(a>0){b=1/a;}` protects nothing at all (for example if `a=1.0e-200`) and likewise for a `min(1,exp(x))` (for example if `x=1.0e10`). Moreover, for fractional powers, one uses rather the template `power<int,int>(real)` rather than the function `pow(real,real)`, as is explained in the [associated documentation](https://thelfer.github.io/tfel/web/tfel-math.html).
- The computation of the Jacobian matrix must be carried out analytically. Its computation by perturbations must be reserved for quick tests on a material point and for checking that the analytical computation is correct (directives `@CompareToNumericalJacobian`, `@JacobianComparisonCriterium` and `@PerturbationValueForNumericalJacobianComputation`). Likewise, the computation of the consistent tangent matrix must be carried out as precisely as possible, ideally analytically (in `mtest`, the directives `@CompareToNumericalTangentOperator`, `@TangentOperatorComparisonCriterium` and `@NumericalTangentOperatorPerturbationValue` make it possible to check that its analytical version is correct). It is also recalled that MFront offers a convenient handling of [tensors of order two and four](https://thelfer.github.io/tfel/web/tensors.html).
- It is useful to activate the checking of the physical dimensions of the quantities used via the directive `@UseQt` true in the MFront file. This requires the variables to be dimensioned correctly. One can use the [documentation](https://thelfer.github.io/tfel/web/mfront-types.html) for help.
- It is necessary to think about the bounds of the physical parameters (directive `@PhysicalBounds`) and the bounds of the model (directive `@Bounds`) because these variables will communicate with the outside of the MFront file and the values entered by a user may be inconsistent.
- Do not put physical constants hard-coded in the MFront code but rather use the directive `@StaticVariable` (not modifiable), `@Parameter` (modifiable at execution) and `@IntegerConstant`, etc.
- Initialise **all** the local variables, pay attention to the unused variables, and reduce as far as possible the number of implicit unknowns (directive `@StateVariable`), the other quantities of interest being updated explicitly via the directives `@AuxiliaryStateVariable` and `@UpdateAuxiliaryStateVariables`. It is recalled that the choice of the starting point for the Newton method strongly determines the speed of convergence and the convergence of the algorithm. It may therefore be useful to understand whether there is a better starting point than zero. This is moreover sometimes a very bad starting point and a correct initialisation is necessary during the prediction phase (directive `@Predictor`).
- When an MFront file is intended to be used with **code_aster**, it is necessary not to make the material parameters depend on the units chosen. A quick way generally consists in adding material parameters `LengthUnit` and `StressUnit` and then testing it on an mtest file. Sometimes, the change of units (MPa instead of Pa for example) can condition the matrix better and make the global Newton algorithm converge better.

If the simulation on a material point of an MFront law does not go correctly with `mtest`, for example a problem of convergence of the law as is often the case, then there is generally no chance that the interfacing with **code_aster** will go better.

#### 1.7.3 Working on the MFront file with code_aster

Once the previous stage works, it seems relevant to continue to proceed gradually in the setting up of the study. One therefore tests the MFront law in **code_aster** but first on a material point with the command [SIMU_POINT_MAT](doc:u4.51.12) by shaking it a little, then by gradually adding complexities.

If this stage crashes or does not converge, then one must go back to the previous stage. Indeed, it is easy to transpose the SIMU_POINT_MAT study into `mtest`.

Finally, in the case where the **code_aster** analysis converges on a material point, one can then begin to work on a real structural analysis, proceeding gradually in order to isolate the different types of non-linearities and the difficulties:

- Start the structural analysis in elasticity without contact, without dependence on the thermal field and in small strains.
- If this goes well, one can add successively and gradually, in this order, the dependence on the thermal field, the large strains and then the contact. One mentions in particular the description of the [good practice](doc:u2.04.04) for simulating non-linear contact (with or without friction).
- If at the very end the analysis converges, then one can finally add the non-linear law coming from MFront thanks to the command CREA_LIB_MFRONT.

Finally, if the structure is geometrically complex, it may be judicious to start with simpler geometries.

Let us note in passing that deactivating the singularity of the matrix is a bad idea in general. It is also recalled that the prediction operator during the first time step is a
central element for ensuring the quadratic convergence of the Newton method. It can be specified in **code_aster** but also directly in MFront via the directive `@PredictionOperator`.

To conclude, one must also be humble with respect to the numerical results obtained and remember clearly that certain mechanical phenomena are very difficult to simulate numerically. Consequently, it is normal for a law to have difficulty in converging, a fortiori if one mixes several types of
non-linearities. This therefore requires a good understanding of the underlying physical and numerical mechanisms. In particular, proceeding gradually is therefore necessary, if only in order to realise that the convergence problem may not come from the law but from the simulation of the
thermal field, of the large strains or of the contact.

Other examples are supplied in the [MFront gallery](https://thelfer.github.io/tfel/web/gallery.html).

The test cases [mfron01](doc:v1.03.126), [mfron02](doc:v1.03.127), [mfron03](doc:v1.03.128), [mfron05](doc:v1.03.130) and [mfron06](doc:v1.03.132) make it possible to check the keyword RELATION='MFRONT', with an MFront file supplied as data of the test.

**Note:**

The tutorials and information concerning the interface between **code_aster** and MFront coming from the [new MFront site](https://thelfer.github.io/tfel/web/index.html) and from [the old one](https://tfel.sourceforge.net) describe the old way in which **code_aster** communicated with MFront. Since version 16.3.13, **code_aster** no longer uses the historical interface (option `--interface=aster` in the MFront command line) but the generic interface (option `--interface=generic`) via its support called [MGIS](https://thelfer.github.io/mgis/web/index.html).

In particular, the option `--@AsterGenerateMtestFileOnFailure=true` is no longer available during the compilation of the Mfront file. It made it possible to recover automatically the simulation data of **code_aster** on a material point (file `*.mtest` ) when the integration failed on the latter. The current interface does have an equivalent directive (`--@GenerateMTestFileOnFailure=true`) but its use is useless and to be avoided because, on the one hand, the analysis will take much more time (writing of a different file `*.mtest` at each Gauss point at each analysis), and memory space (with the risk of a **code_aster** error by saturation, impossible to open or write to a file), and, on the other hand, all these files `*.mtest` will be deleted from the temporary directory at the end of the **code_aster** analysis.
