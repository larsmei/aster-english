# Supervisor and command language

> **Summary.**

This document describes the role and the operation:

- of the supervisor, which ensures the control of an execution of *Code_Aster*;

- and of the command language, which ensures communication between the user and the code.

## 1 Introduction

The role of the supervisor is to ensure the command of the progress of operations during the execution of a program. The execution instructions are generally supplied by the user. This requires a formalisation of the communications between the code and its user; this is the *command language*.

The Python language is used to write the command catalogue, the supervisor and the user command files. For the command files, this makes it possible to relieve the supervisor of the task of syntactic analysis, which is devolved to Python itself.

A command file is a succession of calls to Python functions (the commands), defined in the command catalogue. These functions have input arguments: the keywords and their content, and output arguments: the produced concepts. The user who composes his command file must therefore comply with the general syntax of Python (parenthesisation, indentation …) and with the rules imposed by the command catalogue (the arguments supplied are consistent with what the function expects).

For a first contact with the code, the reader may skip chapter 2.

## 2 General operating mechanism of the supervisor

### 2.1 General architecture

The basic elements involved during an execution of an *Aster* analysis are:

- the command file, supplied by the user,

- the command catalogue: it is a python module named cata placed in the Cata package,

- the high-level SUPERVISEUR object,

- the JDC object created by the latter and which is finally executed.

The SUPERVISEUR object is a python object which analyses the options transmitted on the command line, imports the command catalogue, creates the JDC object from the command file and executes it.

The JDC object (name for Jeu De Commandes) is a python object created by the SUPERVISEUR object from the text of the command file and from the command-catalogue module. It contains the ETAPE objects. The JDC object is representative of the user command file.

The ETAPE objects are representative of each of the calls to Aster commands in the command file. Each ETAPE object bears the name of the command which it references, the list of the active keywords and their values, and the type and the name of the produced concept.

The construction and then the execution of the JDC object trigger the following actions:

- syntactic analysis of the user command file: it is at this level that the python syntax is checked (parentheses, commas between keywords, indentation …). The detection of an error (Python SyntaxError) causes the execution of Aster to stop. The first error is fatal: the following errors are not looked for,

- construction of the stages: this consists in creating an ETAPE object for each call to an Aster command in the command file. This object is registered with the JDC, which manages the list of the stages and of the related concepts,

- verification of each ETAPE: if the call to a command in the user file is inconsistent with the command catalogue, a report is displayed and execution is stopped at this level. This is the semantic verification,

- actual execution of the commands: for each stage taken in order, a call to the corresponding high-level FORTRAN routine (op0nnn.f).

### 2.2 Global or step-by-step execution

A command set can be built and executed according to two modes:

- the global mode, for which **all** the stages of the command set are first built and then executed in their order of appearance. This mode is chosen by the keyword PAR_LOT='OUI' in the DEBUT start-up command,

- the step-by-step mode, for which each stage is executed immediately after its construction. This mode is chosen by the keyword PAR_LOT='NON' in the DEBUT command.

If the user specifies nothing in the start-up command, the global mode (PAR_LOT='OUI') is adopted. These two modes each have their advantages and disadvantages.

The global execution mode guarantees the user that the whole of his file is semantically correct before starting analyses which might fail or fail to converge. It would indeed be unfortunate to stop with a fatal error after a long solution because of a keyword forgotten in a post-processing command.

This also means that all the stages of the command set are built and kept in memory. If several thousand stages are reached, this can become very memory-consuming and this mode is then no longer recommended.

The step-by-step mode builds a stage only after having executed the previous one. It therefore detects only the semantic errors of the current command and has the disadvantage described above. It does however make it possible to exploit a computed result (in a concept) in the command file in order, for example, to place conditional instructions there.

In this mode, the executed stage is immediately released from memory. The memory used is then independent of the number of stages to be executed.

Here is an example of a loop with a stopping criterion on the value of a computed quantity (grandeur), stored in the concept of type table: RELV[k]. If, for example, a mandatory keyword is missing in the call to POST_RELEVE_T, this will be detected only after the complete execution of the first MECA_STATIQUE. On the other hand, the step-by-step mode makes possible here the assignment of the variable SYY, since the concept RELV[k] has been completely computed at the moment when the supervisor executes this line.

DEBUT(PAR_LOT='NON')

RESU=[None]*10

RELV=[None]*10

for k in range(1,10):

RESU[k]=MECA_STATIQUE( ... )

RELV[k]=POST_RELEVE_T( ... )

SYY=RELV[k]['VMIS',4]

if SYY < critere :

break

FIN()

It should be noted that the choice of an execution mode conditions the order in which the **semantic** analysis will take place (ETAPE by ETAPE or globally for the whole JDC). But, in both cases, the python **syntactic** analysis is always carried out beforehand for the whole command file.

> **Note.**

*EFICAS can generate and re-read only command sets containing exclusively ASTER commands, without other python instructions; this independently of the* *PAR_LOT mode chosen.*

### 2.3 The construction of the stages

During the construction of each ETAPE object, its semantic consistency with the catalogue of the command to which it refers is checked. Any error detected is recorded in a report which, in global execution mode, is delivered after the analysis of the whole command file.

Examples of semantic checks:

- compliance with the number of arguments of the keywords,

- compliance with the argument type,

- membership of an argument in a list of possible values,

- correctness of the spelling of a keyword or of a factor keyword,

- compliance with the rules of exclusion or of implication between keywords,

- presence of the mandatory keywords.

At this stage, if the command is an operator and produces a concept, the latter is typed. The supervisor checks that a concept of the same name has not already been defined or, if it is reused, that the command authorises it.

### 2.4 The processing of macro-commands

A macro-command, as seen by the user, is an ordinary command. In fact, it does not call a high-level Fortran routine directly but generates other commands.

Two types of macro-command exist:

- the macros in Python,

- the supervisor macros: these are the special commands (DEBUT, FORMULE, INCLUDE, INCLUDE_MATERIAU, POURSUITE) which require processing at the level of their construction.

In the same way as the JDC itself, the call to a macro-command produces a parent object (of type MACRO-ETAPE) which contains child objects: the stages generated by the macro, or even other macros.

A macro-command of the JDC is first processed like the other commands (syntactic verification, construction of the macro stage). It is then “built” by application of the python Build method to the JDC object. After its construction, the stages of the commands produced by the macro are substituted for the stage of the macro itself, for later execution.

It is important to note that the construction phase of the macro-commands takes place just before their execution, and not during the global pass over the command file in PAR_LOT='OUI' mode. This has two consequences:

- EFICAS analyses the syntax of the macro-command itself, but not that of its sub-commands.

- One can on the other hand exploit, in the programming of the macros, previously computed data brought back into the python namespace, without having to impose PAR_LOT='NON' mode on the user of the macro.

### 2.5 The start-up procedures

The start-up procedures available are:

DEBUT (cf. [U4.11.01](doc:u4.11.01) and POURSUITE [U4.11.03](doc:u4.11.03))

At least one of these two procedures must mandatorily be present in the command file. No other Aster command must precede them. If this is the case, or if neither is present, execution will be stopped as soon as the JDC is created. It is these procedures which contain the information on the execution mode (PAR_LOT='OUI' or 'NON') which conditions the execution mode of the commands which follow.

They are supervisor macro-commands which, on their construction, call the Fortran routines making it possible to initialise the analysis by the following tasks:

- "connection" of the logical units of the standard files,

- opening of the databases,

- reading of the element catalogue.

The first task consists in matching the logical-unit numbers of standard input/output files (message, error, result).

The second task consists in defining and opening the databases (direct-access file used by the memory manager) in accordance with the user's instructions; the user can redefine parameters of these files (see documents [U4.11.01](doc:u4.11.01) and [U4.11.03](doc:u4.11.03) on the start-up procedures). The JEVEUX initialisation routines are called for this purpose (see document D6.02.01, the Memory manager, JEVEUX).

The sequence of commands to be executed ends mandatorily with the FIN command. The text which follows FIN must be commented out (that is, begin with #). For an included file, it is the RETOUR command which marks the end of the instructions that ASTER must take into account.

> **Note.**

*In interactive mode, commands entered by hand, do not put a* *FIN command and pass the* *–interact argument on the job-submission command line.*

### 2.6 Links with EFICAS

The kernel of the supervisor is common with Eficas, the editor of Aster command files. When a command file is edited, the latter carries out the syntactic analysis and the consistency checks of the concepts by construction of the JDC and of its ETAPE objects. Eficas does not of course carry out the macro-command construction task, which would require the source code of *Aster*.

## 3 The command language

### 3.1 Python and the command language

A command file for *Code_Aster* is composed exclusively of Python instructions. The first of the constraints is therefore to comply with the rules of this language. One may read the Python tutorial ([www.python.org](http://www.python.org/)) or the many introductory books on Python for more detail, but this is not necessary for the use of Aster.

A command file may contain python instructions of two kinds: *Aster* commands and … any other python instruction. Indeed, a command file is a python program in its own right and one can in particular place in it control structures (loops), tests (if), numerical computations, and calls to pre- and post-processing functions.

In the context of a “classical” use of the code, where the command file contains exclusively Aster commands, the two rules specific to Python to be remembered are:

- No indentation on the first line of the declaration of an instruction.

mail = LIRE_MAILLAGE ( )

Neither a blank nor a tabulation must be placed before the character string mail.

- The arguments of the functions, in other words the keywords of the commands, are separated by commas; they consist of a keyword, the “=” sign, and the content of the keyword.

**Important:**

The EFICAS editor makes it possible to produce only command files of this type: containing exclusively ASTER commands, without any other Python instruction. Using EFICAS essentially guarantees three things:

- the file produced will have a correct python syntax,

- the commands produced will be consistent with the command catalogue,

- the produced concepts will be correctly chained (no use of a concept without its having been created by a previous command).

The user having composed his command file in this way will be safe from a stop at execution on the grounds of a syntax problem.

### 3.2 Notion of concept

Definition: the Aster data structures which the user can handle and name are called *concepts*. These concepts are typed at the time of their creation and can be used only as an input argument of the corresponding type in a later command.

The notion of concept therefore allows the user to handle objects symbolically and independently of their internal representation (which he may not know). Moreover, the python object designated by the name of the concept contains no information other than its type and its class in the python sense (cf. doc D). Its name, transmitted by the supervisor to FORTRAN, allows Aster to find the corresponding data structure in the global database. But it is not possible to have visibility of the data structure from the command file. For example, the following instructions do not make it possible to print the data structure of type maillage and of name mail:

mail=LIRE_MAILLAGE ( )

print mail

but generate the following message:

<Cata.cata.maillage_sdaster object at 0x593cad0>

There is an exception to this rule: the tables. Indeed, a programming device makes it possible to recover simply the information contained in a TABLE data structure by handling the latter as a two-entry array:

```
pour imprimer une valeur:        print         resu[ ‘DX’ , 1]

pour l’affecter à une variable:    valeur    =    resu[ ‘DX’ , 1]
```

This of course assumes that the data structure resu, of type TABLE, has already been computed at the moment when this instruction is encountered: therefore in step-by-step execution mode (PAR_LOT='NON').

**Lexical note:**

Concept names must not exceed 8 characters. Alphanumeric characters are allowed (lower-case and upper-case letters, and digits not placed in first position) as well as the underscore ‘_’. Case is important: the concepts “MAIL” and “Mail” may be used in the same command file and will be regarded as different … this is however not recommended for the readability of the file!

### 3.3 Possible operations

The structure of the command language takes the form of a linear sequence of instructions. Apart from python instructions other than Aster commands, which are not at issue for the moment, three kinds of instructions (or of commands) are available:

- the operator, which carries out an action and which supplies a produced concept of a predefined type that can be used by the following instructions in the command set,

- the procedure, which carries out an action but does not supply a concept,

- the macro-command, which generates a sequence of instructions of the two previous types and which can produce zero, one or several concepts.

Typically, an operator will be an assignment or solution command, and a procedure will be a print command (to a file).

From the syntactic point of view an operator takes the form:

```
nomconcept = opérateur( arguments . . . )
```

Whereas a procedure takes the form:

```
procédure( arguments . . . )
```

The syntax of an operator or of a procedure is described in the following paragraph.

### 3.4 Rules on the concept produced by an operator

#### 3.4.1 Basic principle

At each execution of an operator, the latter supplies a new produced concept of the type predefined in the command catalogue.

*The concepts appearing as an input argument of the commands are not modified.*

#### 3.4.2 Produced concept and reused concept

A reused concept is a concept which, having been produced by an operator, is modified by a new occurrence of this operator or by another operator.

The use of a reused concept is possible, as an exception to the Basic Principle, only under two conditions:

- authorisation given, by the catalogue and the programming of the command, to use reusable concepts for the operator: the reentrant attribute of the catalogue is equal to ‘o’ or ‘f’,

- an explicit request by the user for the reuse of a produced concept, by the attribute reuse=nom_du_concept in the arguments of the commands which allow it.

#### 3.4.3 Checks carried out by the supervisor on the produced concepts

- Produced concept complying with the basic principle:

The supervisor checks that the name of the produced concept is not already assigned by one of the previous commands, in particular by a command of a previous execution in the case of a POURSUITE or of an INCLUDE.

- Concept used in reuse:

The supervisor checks that:

- the name of the produced concept is indeed already assigned.

- the operator is indeed authorised to accept reused concepts,

- the type of the concept complies with the type of concept produced by the operator.

Commented examples:

```
DEBUT ( )

concept=opérateur ( )                    #    (1)        est correct : on défini le concept,

concept=opérateur ( )                    #    (2)        est incorrect : on essaie de redéfinir le
#            concept mais sans le dire,

concept=opérateur (reuse = concept )    #    (3)        est correct, si l'opérateur accepte des
#            concepts existants et si le type est
#            cohérent; c’est incorrect si l'opérateur
#            ne les accepte pas.

FIN ( )
```

In fact a concept can be created only once: which means appearing to the left of the = (equals) sign without reuse being used in the arguments of the command.

In the case of a reuse, specifying the name of the concept again after the reuse attribute is redundant; all the more so since the supervisor checks that the two concept names are identical.

> **Note.**

*A concept can be destroyed, and therefore its name reused afterwards.*

### 3.5 Body of a command

#### 3.5.1 Introduction

The body of a command contains the "variable" part of the command. The declarations are separated by commas and, apart from the reuse attribute mentioned above, they are all of the form:

[keyword] = [argument]

The keyword is necessarily a keyword of the current command, declared in the catalogue of the latter.

#### 3.5.2 Keyword

A keyword is a formal identifier; it is the name of the attribute receiving the argument.

Example: MATRICE = ...

**Syntactic notes:**

- *the order of appearance of the keywords is free; it is not imposed by the order of declaration in the catalogues,*

- *the keywords cannot exceed 16 characters (but only the first 10 characters are significant).*

There are two types of keywords: the simple keywords and the factor keywords, which differ by the nature of their arguments.

#### 3.5.3 Argument of a simple keyword

#### 3.5.3.1 The type of the arguments

The basic types recognised by the supervisor are:

- the integers,

- the reals,

- the complexes,

- the texts,

- the logicals,

- the concepts,

- as well as the lists of these basic types.

The integers and the reals correspond exactly to the equivalent types in python.

- Optional simple keyword expecting a real:

```
Catalogue                :    VALE    = SIMP( statut=’f’ , typ = ‘R’ ) ,

Fichier de commandes    :    VALE    =    10. ,
```

- Optional simple keyword expecting an integer:

```
Catalogue                :    INFO    = SIMP( statut=’f’ , typ = ‘I’ ) ,

Fichier de commandes    :    INFO    =    1 ,
```

The representation of the complex type is a python "tuple" containing a character string indicating the mode of representation of the complex number (real and imaginary parts, or modulus and phase) then the numerical values.

```
Catalogue                    :    VALE_C    = SIMP( statut=’f’ , typ = ‘C’ ) ,

Fichier de commandes        :    VALE_C    = ( ‘RI’ , 0.732 , -0.732 ) ,

Fichier de commandes        :    VALE_C    = ( ‘MP’ , 1. , -45. ) ,
```

The two notations are strictly equivalent. In ‘MP’ notation, the phase is in degrees.

The text type is declared between single quotes. Case is respected. However, when a keyword must take a value from a list predefined in the catalogue, usage has it that this value is today always in capitals.

```
Catalogue                :    TOUT    =SIMP( typ=‘TXM’,into=(‘OUI’,’NON’)) ,

Fichier de commandes    :    TOUT    = ‘OUI’ ,
```

Case is important and, in the context above, the following command line will fail:

```
Fichier de commandes    :    TOUT    = ‘oui’ ,
```

The logical type is not used today in the command catalogue.

The concept is declared simply by its name, without quotes or double quotes.

#### 3.5.3.2 Notion of list

**Caution**:

The word “list” is here a misuse of language. It is not the python “list” type but rather tuples, in the python sense: the various items are declared between an opening parenthesis and a closing parenthesis; they are separated by commas.

Lists are homogeneous lists, that is to say lists whose elements are of the same basic type. Any basic type can be used in a list.

Examples of lists:

| list of integers | (1, 2, 3, 4), |
| --- | --- |
| list of text | ( 'ceci', 'est', 'une', 'liste', 'de', 'texte'), |
| list of concepts | ( resu1, resu2, resu3 ), |

Ease of use:

It is accepted that a list reduced to a single element may be described without parentheses.

Example of an erroneous list:

Heterogeneous list of an integer and a real

```
(1, 3, 4.)
```

#### 3.5.4 Factor keyword

Some information cannot be given globally (all at once in the command); it is therefore important to provide for the repetition of certain keywords, in order to be able to assign different arguments to them. The factor keyword offers this possibility; under a factor keyword, one will therefore find a set of (simple) keywords, which can be used at each occurrence of the factor keyword. This also makes it possible to improve the readability of the command file by grouping keywords which share a common meaning: for example the various parameters of one and the same material.

Unlike the simple keyword, the factor keyword can receive only a single type of object: the supervisor object “_F”, or a list of the latter.

Either the factor keyword has only one occurrence, and one can write for example, at choice:

```
IMPRESSION    =        _F(    RESULTAT =    resu,    UNITE = 6),

ou

IMPRESSION    =    (    _F(    RESULTAT =    resu,    UNITE = 6), ),
```

In the first case, the factor keyword IMPRESSION receives an _F object; in the other, it receives a singleton. Watch the comma; in python, a one-element tuple is written: (element,)

Or the factor keyword has several occurrences, two in this example:

```
IMPRESSION    =    (    _F(    RESULTAT =    resu1,    UNITE = 6),
_F(    RESULTAT =    resu2,    UNITE = 7)    ),
```

The number of occurrences (minimum and/or maximum) expected of a factor keyword is defined in the command catalogue.

**Notion of default value**

It is possible to have default values assigned by the supervisor. These values are defined in the command catalogue and not in the FORTRAN.

There is no distinction, from the point of view of the routine associated with the command, between a value supplied by the user and a default value introduced by the supervisor. This appears when the user commands are printed by the supervisor in the message file: all the default values appear in the command text, if they have not been supplied by the user.

**Reminder**: a default value cannot be given to a concept.

## 4 Definition of values and evaluation of expressions

It is possible to assign values to python variables in order to use them as arguments of simple keywords: these variables are called parameters in EFICAS. They can contain integer, real or complex values, texts, or lists of these types.

Example:

```
young    =    2.E+11

mat        =    DEFI_MATERIAU    ( ELAS = _F( E = young , NU = 0.3 ) )
```

At the end of execution, the python context is saved with the database. Thus, in the restart which will follow, the parameters will still be present, with their predefined values, just like the ASTER concepts.

It is possible to carry out operations in python on the arguments of simple keywords:

```
Pisur2    =    pi/2.

mat        =    MA_COMMANDE    ( VALE = Pisur2 )
```

or:

```
var        =    ’ world’

mat        =    MA_COMMANDE    (    VALE    = pi/2. ,
VALE2    = Pisur2+cos(30.) ,

TEXTE    = ‘hello’+var        )
```

## 5 Use of python in the command files

It is not necessary to know the python language in order to use *Code_Aster*. Indeed, subject to a few basic rules to be respected concerning indentation and parenthesisation, only knowledge of the command language described in the command catalogues is necessary. And furthermore, EFICAS makes it possible to do without referring to the catalogue or to the “syntax” paragraph of the commands, by proposing graphically the keywords to be filled in.

However, the advanced user will be able to put to good use the power of the PYTHON language in his command file, since the latter is already written in this language.

The four main uses can be: the writing of customised macro-commands, the use of general python instructions, the import of useful python modules, and the recovery of information from the *Code_Aster* data structures into PYTHON variables.

> **Note.**

*If one wants to use accented French characters in the command file or the imported modules, the following instruction must be placed on the first or second line of the file:*

# –*– coding: iso–8859–1 –*–

*In python 2.3, the absence of this line causes a warning which will become an error in python 2.4; in ASTER, it is systematically an error.*

### 5.1 Customised macro-commands

See document D5.01.02: “Introducing a new macro-command”.

Customised macro-commands are very easy to program. They can serve to capitalise recurring analysis schemes and thus constitute a trade tool. It is strongly recommended to take the existing macro-commands as an example: the Macro package in the bibpyt directory.

### 5.2 General PYTHON instructions and useful modules

Advanced users can derive great benefit from the use of loops (for), of tests (if), of exceptions (try, except) and, in general, from all the power of the PYTHON language directly in their command file. The list of uses is impossible to draw up exhaustively. Many examples are present in the test cases of the test database. One can for example carry out mesh adaptation by placing the analysis/remeshing sequence in a loop, or establish a stopping criterion for the iterations by a test on a computed value.

Consult the following paragraph devoted to the “particularised” Aster exceptions.

In a loop, if one recreates an already existing concept, one must remember to destroy it beforehand by the DETRUIRE command.

The other miscellaneous python features of interest to the *Code_Aster* user can be:

- reading and writing to a file,

- numerical computation (for example using Numerical Python),

- the call, via the os module, to the script language, and in particular the launching of a third-party code (os.system)

- the handling of character strings

- the call to graphical modules (grace, gnuplot)

### 5.3 PYTHON exceptions of the aster module

The Python exception mechanism is very useful; it allows, for example, one to “try” a command and then regain control if the latter “crashes” by raising a particular exception:

```
try:

bloc d’instructions

except ErreurIdentifiée, message:

bloc d’instructions exécuté si ErreurIdentifiée se produit…
```

In the command file, this mechanism can be used with any exception of the standard Python modules.

One also has exceptions specific to *Code_Aster* (to the aster module), divided into two categories: the exceptions associated with <S> errors, and that associated with <F> errors.

#### 5.3.1 Interception of <S> errors

In the event of an <S> error, the error is identified by one of these exceptions:

| aster.NonConvergenceError | in the event of non-convergence of the analysis, |
| --- | --- |
| aster.EchecComportementError | problem during the integration of the constitutive law, |
| aster.BandeFrequenceVideError | no mode found in the frequency band, |
| aster.MatriceSinguliereError | singular matrix, |
| aster.TraitementContactError | problem during the treatment of contact, |
| aster.MatriceContactSinguliereError | singular contact matrix, |
| aster.ArretCPUError | stop for lack of CPU time. |

All these exceptions derive from the general <S> exception which is aster.error. This means that except aster.error intercepts all the exceptions cited above. It is nevertheless always preferable to specify which error one expects!

Example of use:

```
try:

resu = STAT_NON_LINE(...)

except aster.NonConvergenceError, message:

print ‘Arrêt pour cette raison: %s’ % str(message)

# On sait qu’il faut beaucoup plus d’itérations pour converger

print "On continue en augmentant le nombre d’itérations."

resu = STAT_NON_LINE(reuse = resu,

...,

CONVERGENCE=_F(ITER_GLOB_MAXI=400,),)

except aster.error, message:

print "Une autre erreur s’est produite: %s" % str(message)

print "Stop"

from Utilitai.Utmess import UTMESS

UTMESS(‘F’, ‘Exemple’, ‘Erreur <S> inattendue’)
```

#### 5.3.2 Interception of fatal <F> errors

In the event of a fatal error, the behaviour can be modified by the user.

By default, the code stops with an <F> error; the error traceback (call of the fortran routines) can be seen in the output file.

If one so wishes, the code can raise the aster.FatalError exception, and in this case (as for an <S> error), if the exception is intercepted by an except, the user regains control; otherwise the code stops (no fortran error traceback).

This choice is determined in the DEBUT/POURSUITE commands, factor keyword ERREUR (cf. [U4.11.01] and [U4.11.03](doc:u4.11.03)), and at any time by the aster.onFatalError method.

The latter, called without argument, returns the current behaviour in the event of a fatal error:

comport = aster.onFatalError()

print "Comportement courant en cas d’erreur fatale : %s” % comport

and makes it possible to define the behaviour that one wishes:

aster.onFatalError(‘EXCEPTION’) # on lève l’exception FatalError

or

aster.onFatalError(‘ABORT’) # on s’arrête avec remontée d’erreur.

#### 5.3.3 Validity of concepts when an exception is raised

When an exception is raised and intercepted (by except), the concept produced by the command in which the error occurred is returned as it stands, the command not having finished normally.

In some cases, in particular after a fatal error, it may be that the produced concept is not usable; then use DETRUIRE to delete it.

Likewise, if one wishes to reuse the name of the concept in order to create a new one, one must DETRUIRE the one obtained in the try.

In the event of <S> errors raised in STAT/DYNA_NON_LINE, the concept is generally valid, and can be reused (keyword reuse) in order to continue the analysis with another strategy (as in the example cited previously).

Finally, before control is returned to the user, the objects of the volatile database are deleted by a call to JEDETV, and the Jeveux mark is reset to 1 (with JEDEMA) in order to release the objects brought back into memory.

#### 5.3.4 Precautions in the use of exceptions

The two exceptions aster.error and aster.FatalError are independent (neither derives from the other), which means that if one wishes to regain control in the event of an <S> error and of an <F> error:

- the raising of an exception in the event of an <F> error must be activated with aster.FatalError(‘EXCEPTION’), or in DEBUT/POURSUITE.

- the two exceptions must be intercepted:

except (aster.FatalError, aster.error), message: …

It is not recommended to use “except:” without specifying which exception one expects (this is a general rule in Python, independently of the Aster exceptions). Indeed, the processing carried out under the except has little chance of being valid in every error case.

Likewise, as in the example given above, it is preferable to use the particularised exceptions NonConvergenceError, ArretCPUError, … rather than the higher-level exception aster.error; always with the idea of knowing exactly what has occurred.

### 5.4 Recovery of computed values in PYTHON variables

Exploiting the PYTHON language in one's command file is of interest only if one can conditionally launch actions according to what the code has computed.

Certain bridges exist between python and the data structures computed by the code and present in the JEVEUX memory. Others remain to be programmed; this is an evolving area and future developments are expected.

It is essential to understand that recovering computed data requires that the instructions leading to their being obtained have indeed been executed beforehand. In other words, it is essential to execute the code in PAR_LOT='NON' mode (keyword of the DEBUT command). Indeed, in this case, there is no global analysis of the command file, but each instruction is executed sequentially. When one arrives at an instruction, all the concepts preceding it have therefore already been computed.

Here are a few methods of access to the data structures. The list is not exhaustive; refer to the documentation [U1.03.02](doc:u1.03.02).

### 5.5 Example of dynamic construction of factor keywords

In the case of a factor keyword that is very repetitive to write, the user may want to compose its content by script, in a list or a dictionary, which he will then supply to the factor keyword. The example below shows three ways of writing one and the same factor keyword.

DEBUT(PAR_LOT='NON')

ooo=[ _F(JUSQU_A=1.,PAS=0.1),

_F(JUSQU_A=2.,PAS=0.1),

_F(JUSQU_A=3.,PAS=0.1)]

ppp=[_F(JUSQU_A=float(i),PAS=0.1) for i in range(1,4)]

qqq=[{'JUSQU_A':float(i),'PAS':0.1} for i in range(1,4)]

rrr=[_F(**args) for args in qqq]

li1=DEFI_LIST_REEL( DEBUT=0.,

INTERVALLE=ooo

/ or

INTERVALLE=ppp

/ or

INTERVALLE=rrr

)

FIN()
