# Performance indicators of a run (time/memory)

## 1 Purpose

During a simulation with *Code_Aster*, **default displays record**, in the message and result files (.mess/.resu), **certain sizing characteristics of the run** (RAM consumption, CPU time, system time and user time...). This document details the displays of these performance indicators.

Some **advice is also formulated to help the user take advantage of these diagnostics**. One must, however, be well aware that there is no universal recipe for optimising the overall performance of a run. It depends on the type of study, on the software and hardware aspects of the machine, and even on its load!

**The default settings and the displays/alarms of the code provide a balanced and instrumented mode of operation**. But, to be sure of having made the best use of the capabilities of one's machine, the user must remain attentive to the points described in this document as well as to the advice given in the command documentation. This document takes up many points from the User documentation on the keyword SOLVEUR [U4.50.01](doc:u4.50.01), [U2.08.06](doc:u2.08.06) and on parallelism [U2.08.03](doc:u2.08.03).

## 2 General points

During a *Code_Aster* simulation, default displays record in the message and result files (.mess/.resu) **certain sizing characteristics of the run**. In particular, for each *Aster* operator, one finds:

- The *characteristics of the linear systems* to be built and solved (number of nodes, of equations and of Lagrange multipliers, matrix size...),

- The minimum *JEVEUX* *memories* (in order to switch to Out-Of-Core [1]_) and the optimum memory (in order to switch to In-Core),

- The *memory outside* *JEVEUX* required by certain *external products* (for example MUMPS),

- The CPU, system and "user" (elapsed) *times*,

- The *breakdown of the times* consumed according to the stages of the analysis (elementary computation, assembly, solution of the linear system).

This last description of the times consumed can be presented at different levels of detail (summary printout, detailed printout, and printout detailed by analysis increment) *via* the parameter MESURE_TEMPS/NIVE_DETAIL of the commands DEBUT/POURSUITE. In parallel mode, the mean value, over all the processors, of the times consumed is added, as well as their standard deviation.

## 3 Characteristics of the linear system

A large number of operators (STAT/DYNA/THER_NON_LINE, CALC_MODES, ...) require the construction and the solution of linear systems. To solve these systems of equations, particular algorithms called "**linear solvers**" are used. These linear solvers are in fact ubiquitous in the course of the *Code_Aster* operators, because they are often employed by the numerical algorithms: nonlinear scheme, time integration, modal analysis, etc. They consume most of the CPU time and of the memory.

The **size of the system**, the **proportion of Lagrange multipliers** and the **fill of the matrix** give indirect information on the **memory/CPU consumption** of the run and on possible difficulties in the solution.

Broadly speaking, the algorithmic complexity of the construction of the linear system is of order $\mathit{NNZ}$, whereas that of its solution is of order ${N}^{\alpha}.\mathit{NNZ}$ (with $1<\alpha <2$).

The total memory occupancy is of the type [2]_ $\beta .\mathrm{NNZ}$ (with $10<\beta <100$) $\times 8\mathit{octets}$. This memory consumption covers several *Aster* data structures and/or structures linked to external products (MATR_ASSE, NUME_DDL, factorised matrix...). Fortunately, these data structures break down into several distinct memory segments, and the algorithms do not require them to be present in RAM simultaneously. A good part of these data can thus often be unloaded to disk.

Furthermore, the introduction of Lagrange-type variables [3]_ into the matrices (matrices then said to be dualised) degrades their numerical properties (size, positive definiteness, matrix conditioning). This therefore often implies more numerical processing in the solvers and degrades their performance. This note can moreover be extended to all mixed finite elements (incompressible modelling, continuous contact method...).

**Notes:**

*The display of the characteristics of the problem (figure 3.1) is carried out only once, at the beginning of the command. In general, these characteristics do not change during the run. The only exceptions concern the operator* *STAT_NON_LINE with the X-FEM method in large sliding or the continuous contact method. For these, the matrix profile changes as the iterations proceed.*

*This display takes place very early in the process, once the profile of the* [4]_ *Aster matrix has been created. The assembly of the elementary terms has not yet been carried out* [5]_ *. This is why one cannot decide, a priori, whether the matrix is symmetric or not. In practice, it is very often symmetric and, when this is not the case, it can be symmetrised via the option* SOLVEUR/SYME *.*

## 5 RAM consumption

At any given moment, the **RAM used by** **Code_Aster** may be the sum of three components.

- The **memory allocated directly by the sources of the code.** This is mainly that allocated by **the** **JEVEUX** **package** D6.02.01 in order to manage all the F77 data structures of the code. This package also makes it possible to unload these objects to disk (Out-Of-Core functionality). Depending on the size of the problem, that of the RAM and the programmer's recommendations, JEVEUX performs more or less pronounced exchanges of data between the disk and the RAM.

- The **memory used by external software** called upon by the *Aster* run (MUMPS/PETSc, METIS/SCOTCH, HOMARD, MISS3D...). Most external software operates In-Core. That is to say that it does not directly manage possible memory overflows and that it delegates this task to the operating system. Others, such as the linear solver MUMPS, are potentially OOC and they themselves explicitly manage the unloading to disk of certain large objects (see keyword SOLVEUR/GESTION_MEMOIRE [U4.50.01]).

- The **memory required by the system** (loading of part of the executable, network layer in parallel...) and by the supervisor and the Python libraries.

When a *Code_Aster* operator requiring the construction and the solution of linear systems is used (for example STAT_NON_LINE or CALC_MODES), **the memory limits are often imposed by the linear solver** (see [U4.50.01](doc:u4.50.01)[U2.08.03]). When internal solvers are involved (LDLT, MULT_FRONT, GCPC), their RAM consumption appears in the JEVEUX displays. On the other hand, when an external product is used (MUMPS or PETSC), its own consumption must then be taken into account (which to a large extent replaces that of JEVEUX).

### 5.1 Memory calibration of a run

It is often useful to calibrate an *Aster* run at the RAM level. This can, for example, make it possible to optimise its placement in a batch class (sequential or parallel) or simply to avoid its abrupt stop due to a memory fault. To do this, one can proceed as follows:

- **Step no. 1**: identify, in the course of the run, the operator which seems the most sizing in terms of problem size (it is often the STAT/DYNA_NON_LINE or the CALC_MODES... dealing with the largest model).

- **Step no. 2:** if this is not the case, set the SOLVEUR block of this operator with METHODE='MUMPS' and GESTION_MEMOIRE='EVAL'. At the end of the calibration, remember if necessary to restore the previous setting.

- **Step no. 3:** launch the run as it stands with memory and time parameters that are modest compared with the usual consumption of this type of run. Indeed, with this option, *Code_Aster* will only build the first linear system of the operator and pass it to MUMPS for analysis. The latter will not carry out its most costly stage (in time and especially in memory), that of numerical factorisation. Once this analysis is complete, the MUMPS memory estimates (${\mathit{MUE}}_{\mathit{IC}}$ and ${\mathit{MUE}}_{\mathit{OOC}}$), together with that of JEVEUX (${\mathit{JE}}_{\mathit{OOC}}$), are recorded in the message file (see figure 5.1-a). The run then stops in FATAL ERROR so as to make it possible to move on to the next step as quickly as possible.

- **Step no. 4**: use of the memory estimates proper.

To relaunch the run with the linear solver MUMPS, one has direct access to the "minimum" values of the RAM that are indispensable for the run. Two cases are distinguished according to the memory management mode chosen for MUMPS: In-Core (value $max({\mathit{JE}}_{\mathit{OOC}},{\mathit{MUE}}_{\mathit{IC}})$ if GESTION_MEMOIRE='IN_CORE') or Out-Of-Core (value $max({\mathit{JE}}_{\mathit{OOC}},{\mathit{MUE}}_{\mathit{OOC}})$ if GESTION_MEMOIRE='OUT_OF_CORE'). Depending on the machine/the batch classes available, the complete run must therefore be relaunched, also modifying if necessary this parameter of the SOLVEUR block.

These estimates are established for a given computer and numerical configuration: hardware platform, libraries, number of MPI processes, renumberer, pre-processings...

- **Step no. 4bis**: on the other hand, if one wishes to relaunch the run while changing linear solver or one of the numerical parameters, it is more difficult to deduce the appropriate memory estimate from them. The range of combinations and the variability of the possibilities are too great. A few empirical rules can nevertheless be proposed (in sequential mode). Roughly, if instead of METHODE='MUMPS' one chooses 'MULT_FRONT', the memory estimate should remain valid (with RENUM='METIS', the default value). With 'LDLT', this figure must be significantly revised upwards. With 'PETSC'/'GCPC'+'LDLT_SP', it can probably be reduced to $max({\mathit{JE}}_{\mathit{OOC}},{\mathit{MUE}}_{\text{IC/OOC}}/2)$. With 'PETSC'/'GCPC'+'LDLT_INC' it can probably be reduced to a factor times ${\mathit{JE}}_{\mathit{OOC}}$ according to the fill level of the preconditioner (keyword NIVE_REMPLISAGE, see [R6.01.02]).

- **Step no. 5:** relaunch the complete run, modifying if necessary the setting of the SOLVEUR block and setting Astk with the value deduced at step no. 4 ("Total memory (MB)" menu of figure 5.2-b).

> **Note.**

*This procedure for the memory calibration of a study has only been available since the introduction of the keyword* SOLVEUR/GESTION_MEMOIRE *(from version v11.2 of Code_Aster). For older versions, if the run has already been launched (and if a usable message file is available), one can, at a minimum, cautiously take as the optimum estimate of the memory required the largest value, over all the processors, of the* Vmpeak *of the last operator. Otherwise, one must proceed as mentioned in the earlier versions of this document:*

- **Step no. 1**: as above.

- **Step no. 2**: set the *SOLVEUR* block with *METHODE='MUMPS','OUT_OF_CORE'='OUI'* and *INFO=2.*

- **Step no. 3**: launch the run while limiting the time consumption (for example, with few time steps or little eigenmode searching).

- **Step no. 4**: according to the memory management mode of MUMPS required (IC or OOC), take the maximum of the MUMPS estimate and of the *JEVEUX* consumption.

### 5.2 JEVEUX memory consumption

**Information for quantifying the memory consumption of** **JEVEUX** is recorded at the end of each *Aster* operator (see figure 5.2-a). Broadly speaking, it can be explained as follows:

- ${\mathit{JE}}_{\mathit{OOC}}$ gives the **minimum size** ('Minimum') **that** **JEVEUX needs in order to operate up to this operator**. It will then be completely Out-Of-Core (OOC). Below this value, the run is not possible (in the configuration adopted).

- ${\mathit{JE}}_{\mathit{IC}}$ gives a lower bound ('Optimum'), up to this operator, of the JEVEUX memory required in order to operate completely In-Core (IC): ${\mathit{JE}}_{\mathit{IC}}^{'}$. With at least this value of RAM set in Astk (see ${\mathit{MEM}}_{\mathit{ASTK}}$), the run will proceed in an optimal manner: there is no risk of a crash due to a lack of memory, and access to the purely Aster data structures is little slowed by unloading to disk.

These two figures are necessarily lower than the total value of RAM devoted to the run (set in *Astk*), denoted ${\mathit{MEM}}_{\mathit{ASTK}}$.

By ranking the memory consumption of all the commands, one can identify the one which sizes the run. For a fixed run configuration (number of processors), the larger the memory space reserved for JEVEUX, the more the run will be In-Core (IC) and therefore the faster it will be. One can also, according to the constraints of the batch queues, split one's run into different POURSUITE so as to mix them and thus optimise the "run time/memory" settings.

During the run, **JEVEUX can unload a large part of the objects from RAM to disk**. This mechanism is either:

- Automatic (there is no longer enough RAM space to create an object or to bring it back),

- Managed by the programmer (for example, a call to this release mechanism just before handing over to MUMPS).

The statistics concerning this mechanism are summarised at the end of the message file (see §5.2-d) for all of the commands. Obviously, the more this mechanism intervenes (and on large volumes of memory released), the more the run is slowed down (system and elapsed times which grow, and a stable CPU time). This phenomenon may be accentuated in parallel mode (simultaneous memory contention) depending on the distribution of the processors over the compute nodes and depending on the characteristics of the machine.

### 5.3 Memory consumption of external products (MUMPS)

## 6 Some advice for optimising performance

Here **some advice is formulated to help the user take advantage of the diagnostics recorded** in the message file. One must, however, be well aware that there is no universal recipe for optimising the overall performance of a run. It depends on the type of study, on the software and hardware aspects of the machine, and even on its load!

**The default settings and the displays/alarms of the code provide a balanced and instrumented mode of operation**. But, to be sure of having made the best use of the capabilities of one's machine, the user must remain attentive to the points described in this document as well as to the advice which abounds in the command documentation.

Listed below, and in a non-exhaustive manner, are several questions which it is useful to ask oneself when seeking to optimise the performance of one's run. Of course, some questions (and answers) are cumulative and can therefore apply simultaneously.

### 6.1 Concerning the characteristics of the problem

In view of the points of §3, two empirical rules can be formulated:

- The more the **size of the problem** ($N$) and/or **the fill of the matrix** ($\mathit{NNZ}$) increase, the more costly (CPU/RAM) the construction, and especially the solution, of the linear system will be.

- An increase in the **proportion of Lagrange multipliers** (${N}_{L}/N$) can make the solution of the linear system more difficult (execution time, quality of the solution).

- The size of the problem **sizes the maximum number of processors** which it is relevant to devote to its parallel run: a granularity of at least 20.103 degrees of freedom per MPI process is required.

### 6.2 Concerning the times consumed

To reduce the CPU times, the *Aster* user has various tools available:

- If **most of the costs concern the elementary computations/assemblies and/or the solutions of linear systems** (see §4.1), it is recommended to use *Aster* in parallel mode. It is then preferable to use the linear solver MUMPS in distributed MPI mode or the MULT_FRONT solver in OpenMP. The first strategy also makes it possible to bring down the RAM consumption per processor.

- If **the linear solver** **MUMPS is already being used**, one can deactivate its OOC 12_ functionalities (GESTION_MEMOIRE='IN_CORE') and the improvement of the quality of the solution (RESI_RELA=-1.d0). If the matrix is well conditioned and/or non-symmetric, one can also try relaxation parameters of the linear solver (FILTRAGE_MATRICE, MIXER_PRECISION, SYME).

- If one is carrying out **a nonlinear analysis**, one can test various relaxation parameters of the nonlinear solver (REAC_INCR, REAC_ITER, SYME).

- If one is carrying out a **modal analysis**, the use of the IRAM method is recommended (METHODE='SORENSEN'), together with the splitting of the spectrum sought into several frequency bands (*via* the operator CALC_MODES with OPTION='BANDE' split into several sub-bands).

- In general, the more **the mode of operation of** **JEVEUX** **(and of** **MUMPS) is in IC** (see §5.1), the faster the run. These gains are not, however, very large compared with those provided by parallelism and by the choice of a suitable linear solver (together with its settings).

For each stage of the analysis, one **should normally have a low system time** (SYST) and a cumulative total "CPU time + system time" (CPU+SYST) very close to the real waiting time (ELAPS). If this is not the case, two classic situations may arise:

- **The** **USER+SYS time is much greater than the** **ELAPS time**. The run is certainly using the OpenMP parallelism of the parallel strategies 1c or 2a described in the U2 document on parallelism and in §2.2 of document U4.50.01. This situation is not worrying (and is even intended); the main point is that the turnaround time of the run should be as low as possible!

- **The** **ELAPS time is much greater than the** **CPU time and/or the** **SYS time is large.** The run is probably suffering from memory contention (system swap, RAM/disk I/O...).

- **Line of enquiry no. 1:** This extra cost may come from the **global unloadings of** **JEVEUX**. To confirm this, it is enough to go and read, at the end of the .mess, the statistics concerning dynamic allocation (see §5.2) or the time consumption of the various unloadings (see §4.1). The more calls there have been to the release mechanisms and/or the more large objects have been released, the more the SYST and ELAPS times will deteriorate. **One solution is then to increase the memory size devoted to** **JEVEUX**.

- **Line of enquiry no. 2:** As a corollary of the previous observation, MPI parallel mode tends to increase tenfold the extra costs due to unloadings. Indeed, the distribution of the data induced by parallelism will reduce the size of the JEVEUX objects (if SOLVEUR/MATR_DISTRIBUEE is activated) and thus limit the impact of the unloadings. *Conversely*, these are liable to take place at the same time and on contiguous processors. **A palliative solution** may then consist in "wasting" processors, **by interleaving the active MPI processors with sleeping processors** (for example, the ncpus value of *Astk* initialised to 2).

- **Line of enquiry no. 3:** If the linear solver MUMPS is used in OOC, the problem may come from a **large number of forward/back substitutions** by the product (see stage 1.4 of §4.1). They can be limited by switching off the automatic refinement option (RESI_RELA=-1.d0) or by returning to IC mode (if the memory resources allow it).

### 6.3 Concerning the RAM consumed

- If the consumptions ${\mathit{JE}}_{\mathit{IC}}$ and ${\mathit{JE}}_{\mathit{OOC}}$ are close (a few tens of percent), this means that JEVEUX has often had to operate in OOC mode. There have probably been numerous memory unloadings (see §4.1/5.2). The computation time may suffer as a result (especially in parallel). One should try to add memory or to increase the number of processors (if the MATR_DISTRIBUEE option is activated).

- The **run is often sized in memory**, by the maximum, over the most demanding operator, of the JEVEUX minimum value (${\mathit{JE}}_{\mathit{OOC}}$) and the value used by the linear solver MUMPS (if it is used). To reduce this figure one can act on several factors:

- **If** **MUMPS** **is used and the latter is predominant** (this is often the case): use more processors in MPI (parameters mpi_nbcpu/mpi_nbnoeud of *Astk*), switch to OOC (keyword SOLVEUR/GESTION_MEMOIRE). If the matrix is well conditioned and/or non-symmetric, one can also try relaxation parameters of the linear solver (FILTRAGE_MATRICE, MIXER_PRECISION, SYME).

- **If** **MUMPS** **is used and the latter is not predominant:** use the distribution of JEVEUX objects of the option MATR_DISTRIBUEE in parallel mode.

- If **another linear solver** is used: use MUMPS in parallel, or even GCPC/PETSC (in sequential/parallel mode).

### 6.4 Concerning parallelism

- If **most of the costs concern the elementary computations/assemblies and/or the solutions of linear systems** (see §4.1), it is recommended to use *Aster* in parallel mode. It is then preferable to use the linear solver MUMPS in distributed MPI mode (see the U2 document on parallelism or U4.50.01) or the MULT_FRONT solver in OpenMP.

- It is preferable to limit the parallelism of the run solely to the few operators that are costly (in time/memory): STAT/DYNA_NON_LINE, CALC_MODES ... And therefore, if possible, to split the run into a succession of sequential pre/post-processings and of parallel analyses. During long runs (a few days), this strategy furthermore makes it possible to protect oneself better against possible stops in error, by saving the database associated with each major stage of the run.

- It is useful, beforehand, to **validate** **one's parallel run** by comparing a few iterations in sequential mode and in parallel mode. Moreover, this approach also makes it possible to **calibrate the maximum gains attainable** (theoretical speed-ups) and thus to avoid "wasting too many processors". Thus, if $f$ denotes the parallel portion of the code (determined for example *via* a prior sequential run), then the maximum theoretical speed-up ${\mathrm{S}}_{\mathrm{p}}$ accessible on $p$ processors is calculated according to Amdahl's formula:

${\mathrm{S}}_{\mathrm{p}}=\frac{1}{1-\mathrm{f}+\mathrm{f}/\mathrm{p}}$ .

For example, if the default distributed parallelism is used (scenarios 1b+2b, see the U2 document on parallelism) and stages 1.3/1.4 and 2. (see §4.1) represent 90% of the sequential time ($f=0.90$), the theoretical speed-up is bounded by the value ${\mathrm{S}}_{\infty}=\frac{1}{1-0.9+0.9/\infty }=10$ ! And this, whatever the number of MPI processes allocated.

- In order to optimise one's parallel run, one must watch for possible **load imbalances** in the data flow (CPU and memory) and limit the extra costs due **to memory unloadings** (JEVEUX and MUMPS OOC) (see §4.1) and to the **archiving of fields** (see §4.3). In order to gain run time, one must also rule out any procedure for compaction of the memory (command FIN, keyword RETASSAGE), which is counter-productive in parallel.

- **Resorting to the MPI parallelism** of MUMPS makes it possible to gain in CPU time (on the parallelised stages) and in RAM: thanks to the data distribution of JEVEUX (if the option MATR_DISTRIBUEE is activated) and, above all, thanks to that of the MUMPS objects.

- **A few empirical figures:** it is recommended to allocate at least 20,000 degrees of freedom per MPI process; a standard thermomechanical analysis generally benefits, on 32 processors, from a gain of the order of ten in elapsed time and from a factor of 4 in RAM.
