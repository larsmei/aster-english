# u4.01.00 How to read the command documentation

**Summary:**

This note is a reading guide for booklets U4 and U7 of the User's manual.

It explains in particular the meaning of the meta-characters and of the typographical conventions used to describe the syntax of the commands.

All the examples given here are given for illustration and do not replace the complete description of the commands given in booklets U4 and U7.

**Table of contents**

## 1 Reminders on the syntax of the Code_Aster commands

The command language and its supervisor are completely described in document [U1.03.01](doc:u1.03.01). A few points on the syntax of the *Code_Aster* commands are recalled here.

In *Code_Aster*, the generic term commands covers both the **operators**, the **procedures** and the macro-commands of the command language. An operator supplies a typed **produced concept** (typed by the operator) and named by the user. A procedure does not generate a produced concept; it carries out **actions** such as printouts or resource allocations.

In the example below, the vocabulary used in the description of the commands is recalled.

![Figure](/figures/u4.01.00/Shape1.gif)

**Terminology** **Aster**

An operand is therefore the whole formed by a keyword and its argument. However, in the command documentation, the operands of an operator or of a procedure are often designated by the name of their keyword. For example: RHO, a simple keyword, or ELAS, a factor keyword.

The term **produced concept** is generic for all the operators; it is the result of the work of the operator.

Here, in the DEFI_MATERIAU example, the data structure of type mater (material), named beton by the user, has been created. It groups the names (keywords E, NU, RHO) and the values (arguments 3.4E10, 0.25, 2500.) of the elastic mechanical characteristics (factor keyword ELAS) of the material.

The term **concept of result type** applies to the outputs of the analysis operators, that is to say fields of physical quantities (displacements, temperatures, stresses, forces, modes, etc.) on the nodes or on the mesh cells at different time instants or for different frequencies.

The result concept generally has **subtypes**.

## 2 Standard layout of the user's documents for the commands

Each document presenting a command contains the following chapters:

- Purpose,
- Syntax,
- Operands,
- Examples (where applicable).

This presentation allows the user to find in a single document all the knowledge required to use a command.

## 3 Purpose paragraph

The functionality fulfilled by the command (actions carried out) is stated. The types of the concepts expected on input and of the produced concept are also specified, together with the particular features of the command.

This paragraph is also displayed by the search engines; it therefore contains only text, without equations or formulae.

Example: operator STAT_NON_LINE [U4.51.03](doc:u4.51.03)

**Purpose**:

Compute the quasi-static mechanical evolution of a structure in the non-linear regime.

The non-linearity is related either to the constitutive behaviour of the material (for example plastic), or to the geometry (for example in large displacements). For details on the solution method used, refer to the reference documentation [R5.03.01](doc:r5.03.01).

The evolution can be studied in several successive jobs (re-entrant concept), either as a continuation (the last computed time instant is the initial time instant of the next analysis), or as a recovery starting from an earlier time instant.

If the time required to carry out the run is not sufficient, the program stops, but the results already computed are saved if a database has been defined in the user's study profile. It produces a data structure of type evol_noli.

### 4.1 Meta-characters for the status of operands ( ♦ ◊ / | )

Four meta-characters are used to indicate the status of the operands. Status of the operands means here whether they are declared as mandatory or optional, and the nature of the alternatives in the choice of the operands.

These meta-characters are not part of the command language. They have only a documentary presentation function and must therefore not be used when writing the command file.

#### 4.1.1 Mandatory or optional operands

They are identified by a black or white lozenge at the head.

| ♦ | black lozenge: it is mandatory to declare in the command the operand or operands which follow this sign. |
| --- | --- |
| ◊ | white lozenge: the declaration of the operand or operands which follow this sign is optional. If the operand is absent, the command will where appropriate assign one or more default values. |

| **Example**: operator DEFI_LIST_ENTI | (definition of a list of strictly increasing integers whose values are evenly spaced) |
| --- | --- |

```text
li     =    DEFI_LIST_ENTI

(    ♦    DEBUT = deb    ,
◊    INTERVALLE = _F     (    ♦    JUSQU_A    =    if    ,
♦    PAS            =    ipas,
)
)
```

- It is mandatory to declare the operand identified by the keyword DEBUT and to supply deb, which is the first integer of the list to be built.
- It is not mandatory to declare the operand identified by the factor keyword INTERVALLE. In that case the list of integers will consist of a single integer of value deb (this is stated in the description of the operands).
- If the operand INTERVALLE is declared, then it is mandatory to declare the operand JUSQU_A, which specifies the integer end if of the interval to be subdivided with a constant step, and the operand PAS, which indicates the step ipas used to subdivide the interval.

#### 4.1.2 Alternatives in the choice of the operands

They are identified by the presence, at the head of each choice of the alternative, of:

- a / (slash): exclusive alternative, a single choice among those proposed,
- a | (pipe, semicolon): non-exclusive alternative, one or more choices among those proposed.

| Example of an exclusive alternative: operator AFFE_MODELE | (assignment of the finite-element type over all or part of a mesh). |
| --- | --- |

```text
mo     = AFFE_MODELE (
♦        MAILLAGE = ma
♦        AFFE = _F    (    ♦    /    TOUT        =    'OUI',
/    MAILLE        =    mail    ,            [l_maille]
/     NOEUD        =    noeu    ,            [l_noeud]
/    GROUP_MA    =    g_mail    ,            [l_gr_maille]
/    GROUP_NO    =    g_noeu    ,            [l_gr_noeud]
...............
)

)    ;
```

In the operand AFFE (mandatory) one must indicate where, on the mesh, the finite-element type specified in the operands PHENOMENE and MODELISATION of the same command will be assigned:

- either over the whole mesh (TOUT),
- or on certain mesh cells (MAILLE),
- or on certain nodes (NOEUD),
- or on certain mesh-cell groups (GROUP_MA),
- or on certain node groups (GROUP_NO).

Example of a non-exclusive alternative:

| operator AFFE_CHAR_MECA operand DDL_IMPO | (assignment of imposed displacements on degrees of freedom). |
| --- | --- |

```text
DDL_IMPO = _F    (    ♦    /    TOUT =        'OUI',
/    NOEUD =     lno    ,        [l_noeud]
/    GROUP_NO=     lgno,        [l_gr_noeud]
/    MAILLE =        lma    ,        [l_maille]
/    GROUP_MA=        lgma,        [l_gr_maille]
♦    |    DX =            ux    ,        [R]
|    DY =            uy    ,        [R]
|    DZ =            uz    ,        [R]
|    DRX =            x    ,    [R]
|    DRY =            y    ,    [R]
|    DRZ =            z    ,    [R]
|    GRX =            g    ,        [R]
|    PRES=            p    ,        [R]
|    PHI =                ,        [R]
|    TEMP=            T    ,        [R]
|    PRE1=            pr1    ,        [R]
|    PRE2=            pr2    ,        [R]
)
```

In this operator, one must specify, as a mandatory item:

- the domain of application on the mesh: everywhere (TOUT), on certain nodes (NOEUD) or on certain node groups (GROUP_NO),
- on which degrees of freedom, with which values imposed by the user.

The meta-character **|** indicates that the user may impose a displacement value on **one** (the symbol ♦ indicates that at least one is required) or **several** of the degrees of freedom (DX, DY, DZ, DRX, DRY, DRZ, GRX, PRES, PHI, TEMP, PRE1, PRE2) of the nodes designated beforehand.

#### 4.1.3 Combinations of the meta-characters for the choice of the operands

These meta-characters can be combined to illustrate the multiplicity of choices in certain commands.

**Example**: command DEFI_MATERIAU (definition of a material by its constitutive behaviour properties)

For a thermomechanical study, one needs to define a material which has **both** mechanical characteristics (ELAS) and thermal characteristics (THER), hence the use of the pipe: **|**

But within each choice, one is obliged to choose whether the material properties are dependent (_FO) or not on the temperature, hence the use of the slash: **/**; see below:

```text
ma =     DEFI_MATERIAU        (        |    /ELAS = _F    (    ♦     E =         yg,
♦    NU =        nu,
◊    RHO =        rho,
◊    ALPHA =    dil,
)
……
/ELAS_FO =_F(    ♦     E =         f1,
♦    NU =        f2,
◊    RHO =        f3,
◊    ALPHA =    f4,
)

|    /THER = _F    (    ♦     RHO_CP =     cp,
♦     LAMBDA =    la,
)
……
/THER_FO =_F(    ♦     RHO_CP =    g1,
♦    LAMBDA =    g2,
)
……
);
```

### 4.2 Meta-characters for the type of a concept or of an argument

Like the meta-characters for the status of operands, the brackets [ ] and the asterisk * are not part of the command language. They have only a documentary presentation function.

#### 4.2.1 Types of concepts or of arguments [ ]

They enclose the type of the produced concepts as well as the type of the arguments.

**Example**: command AFFE_MODELE (assignment of the finite elements on the mesh cells of a mesh)

```text
mo    [modele] = AFFE_MODELE

(    ♦    MAILLAGE =    ma,                            [maillage]
♦    AFFE =_F    (    ♦    /    TOUT    = 'OUI',
/    MAILLE    = mail,    [l_maille]

    ....................
)
```

In the example above, it is therefore specified that the concept produced by AFFE_MODELE is of type modele and that the concept expected as the argument of the keyword MAILLE must be of type l_maille (i.e. a list of mesh cells).

#### 4.2.2 Type of the produced concept [*]

This meta-character indicates that the type of the produced concept, or the subtype of the produced concept of result type, depends on the types of the arguments of certain operands. In this case the various possibilities are written after the syntax of the command.

Example: command CREA_CHAMP

In this example, ch2 will be a field at the nodes, a map or a field by element according to the value of TYPE_CHAM.

```text
ch2    [*] = CREA_CHAMP
(    ♦    TYPE_CHAM =    / ‘NOEU_xxxx’,                        [Kn]
/ ‘CART_xxxx’,
/ ‘ELGA_xxxx’,
/ ‘ELNO_xxxx’,
/ ‘ELEM_xxxx’,
)

    Si        TYPE_CHAM        =        'NOEU_TEMP_R'            alors    [*]    =    CHAM_NO_TEMP_R
'NOEU_DEPL_R'                            CHAM_NO_DEPL_R
...
'CART_TEMP_R'                            CARTE_TEMP_R
'CART_DEPL_R'                            CARTE_DEPL_R
...
```

For certain complex commands such as AFFE_CARA_ELEM or DEFI_MATERIAU, for example, the comment character is used to comment on the alternatives of the operands. It has the same meaning as in the command language and is interpreted as such by the supervisor.

### 4.4 Types of the arguments expected by the keywords

The keywords of the operands expect arguments which, in general, fall into four classes:

- values; a symbolic name then specifies the accepted computer type (real, integer, character string, etc.),
- imposed texts; the text or texts ('OUI', 'HY1') are then indicated between quotes,
- names of simple topological entities (node name, mesh-cell names, or lists of names), declared in the mesh file, or names of node groups or of mesh-cell groups, or lists of names of node groups or of mesh-cell groups,
- names and lists of names of concepts produced by the operators.

The table below gathers all the main types of arguments expected by the keywords:

| [R] | real | 3  |
| --- | --- | --- |
| [l_R] | list of reals | (1., 3., 7.) |
| [I] | integer | 7 |
| [l_I] | list of integers | (9, 6, 1, 9) |
| [C] | complex | RI 1.1, 7.8 or MP 10.,1.57 |
| [l_C] | list of complexes | (RI 1.1, 7.), (RI 4.7, 9.) |
| [TXM] | unconstrained text (TITRE name...) | **‘mon titre’** |
| [Kn] | text of length less than or equal to n characters | ’INST’ |
| [l_Kn] | list of texts of length less than or equal to n characters | (‘SIXX’, ‘SIYY’, ‘SIXY’) |
| [noeud] | node name | N23 |
| [l_noeud] | list of node names | (N23, N24, N25) |

In the example above, the concept expected as the argument of MATR_ELEM may be of different types, and the typing of the concept produced by the operator ASSE_MATRICE will depend (according to the rules stated above) on the type of the concept passed as an argument by the user.

## 5 Operands paragraph

For each operand, the meaning of the operand for this command is described, together with the nature and the type of the arguments expected by the keywords, and the restrictions and difficulties of use.

For example, in the documentation of the operator AFFE_MATERIAU, for the operand AFFE, an operand intended to specify on which topological entity or entities of the mesh named ma the material named mat produced by the operator DEFI_MATERIAU will be assigned, one will read:

```text
♦    AFFE
```

Factor keyword which makes it possible to assign different materials on “pieces” of the mesh.

```text
/    TOUT= ‘OUI’,
```

This keyword makes it possible to assign on all the mesh cells of the mesh.

```text
/    GROUP_MA= lgma,
```

This keyword makes it possible to assign on a list of mesh-cell groups of the mesh.

```text
/    MAILLE=    lma,
```

This keyword makes it possible to assign on a list of mesh cells of the mesh.

To each mesh-cell group (keyword GROUP_MA) or each list of mesh cells (keyword MAILLE), or again to the whole mesh (keyword TOUT), a material mat is assigned, which is a concept produced by one of the operators DEFI_MATERIAU [U4.43.01](doc:u4.43.01) or DEFI_COMPOSITE [U4.42.03](doc:u4.42.03).

If a mesh cell appears explicitly (or implicitly) in several occurrences of the factor keyword AFFE, the overloading rule is applied: it is the last assignment which prevails [U2.01.08](doc:u2.01.08).

## 6 Verification / execution phases

The Syntax paragraph of the user's documentation is the exact reflection of the catalogue of the command. This catalogue is a file which contains, written in the language of the supervisor, all the rules on the keywords: presence, exclusion, implication, content …

The EFICAS editor uses this command catalogue and allows the user, if in the end the composed file is valid, to obtain a correct command set.

On execution of the study, the *Code_Aster* supervisor reproduces the same task of syntactic verification: either globally for the whole file, or alternating with execution, command by command.

In addition, during the actual execution of the commands (entered in the FORTRAN part of the source code), further checks may be made. These are constraints which cannot be managed at the level of the command language (equality of the cardinals of different lists …).

## 7 Typography and indentations

For the readability of the documents relating to the commands, everything which relates to the syntax is printed in Courier 10-point type. The different types of functional elements (produced concept, keyword, factor keyword, argument) are distinguished by the use of upper case and lower case.

In upper case:

- names of the operators and of the procedures,
- names of the keywords and of the factor keywords,
- imposed arguments of text type (these are between 'quotes', as in the syntax of the commands).

In lower case:

- names of the produced concepts,
- symbolic names of the arguments,
- types of the produced concepts and of the arguments.

In mixed lower case – upper case when the produced concept admits a subtype. The subtype appears in upper case, as does the FORTRAN type of the quantity of the subtype.

The readability of the syntax is reinforced by the use of indentations. They are used to identify blocks of operands and to set off a group of operands under a factor keyword. They are also used to place the parentheses of one and the same block in vertical alignment.
