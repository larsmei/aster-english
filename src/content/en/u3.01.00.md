# u3.01.00 Description of the Code_Aster mesh file

**Summary:**

This file makes it possible to describe a mesh of *Code_Aster*. It can be built by an automatic interface between a mesher and the code, but it can also be written by hand. It contains:

- an optional title,
- a list of nodes with their coordinates,
- lists of mesh cells; each mesh cell is described by the list of the nodes which defines its topology, and its orientation,
- node groups and mesh-cell groups.

**Note:**

*A concept of type maillage, once read from the mesh file, can be enriched with the help of Code_Aster operators by information which cannot currently be described in the mesh file. This concerns in particular static substructuring. It is moreover possible, now, to create node groups or mesh-cell groups in the course of a study.*

> **Table of contents**

## 1 Structure of the mesh file

The *Aster* mesh file is read from the first line up to the first occurrence of a line beginning with the word **FIN**. This keyword is mandatory.

The *Aster* mesh file is made up of a succession of independent mesh sub-files.

| ![Figure](images/1000000000000124000002006F3F93AA5FEF6722.png)**FIN** |
| --- |

The **Aster mesh** file is a formatted file, in the FORTRAN sense:

- the line length is limited to 80 characters (any information from column 81 onwards is simply ignored);
- the blank character ' ' and the comma ',' are the only separators recognised,
- the character % is a reserved character used to indicate the beginning, up to the end of the line, of a comment,
- the numerical data are interpreted in free format:

```text
1 = 1. = 1.0 = 1.E+0 = .1E1 = 10.D-1
```

The **mesh** file must contain at least:

- a sub-file of node coordinates COOR_2D or COOR_3D, defined by 2 or 3 real numbers in a single orthonormal Cartesian frame.
- one sub-file per type of mesh cell used.

It may contain, in addition, and this is recommended, a TITRE sub-file. It is practically indispensable to define, at the time of meshing, sub-files of mesh-cell groups GROUP_MA and sub-files of node groups GROUP_NO.

It should be remembered that the assignment of a finite-element type can be done only on a mesh cell (or, exceptionally, on a node for the discrete elements) described in the mesh file. The loadings or the boundary conditions are assigned on mesh cells or on nodes according to the case.

## 2 Structure of a sub-file

A sub-file begins with a **keyword** and is terminated by the imposed keyword **FINSF**:

![Figure](/figures/u3.01.00/1000039C000011E100000AC02C0D11B219D36390.svg)

This description is sufficient for *Aster*. The most complete description is the following:

- each sub-file comprises 3 parts:

1. the header of the sub-file,
2. the content of the information,
3. the end marker of the sub-file (FINSF).

![Figure](/figures/u3.01.00/10000B0C000030C8000011AC4B640EA47424B75E.svg)

- MOTCLE and FINSF (end of sub-file) are mandatory because they delimit the sub-file inside the mesh file.
- NOM is optional. When the keyword is GROUP_MA or GROUP_NO, if NOM is absent then the first character string encountered after these keywords will form the NOM of the GROUP_MA or of the GROUP_NO.

By convention any character string which follows the character % is interpreted as a comment.

### 2.1 The header

The role of the header is to provide global information on the content of the sub-file:

| MOT_CLE | In addition to its role as a delimiter of the sub-file, it indicates the nature of the information which will follow. It must be found on the 1st line of the sub-file **and left-justified**. |
| --- | --- |
| NOM | it is used to designate a set of information. It must be found on the 1st line of the header of the sub-file. It is optional. |
|  | All the other keywords are currently ignored by the operator [LIRE_MAILLAGE](doc:u4.21.01). |

### 2.2 List of the information

These are items of information coming from a mesher and written in free format.

The information which this file must contain defines the classical entities of the finite-element method:

| **nodes**: | points defined by a **name** and by their **Cartesian coordinates** in **2D** or **3D** space, |
| --- | --- |
| **mesh cells**: | **named** topological figures, plane or volume (point, segment, triangle, quadrangle, tetrahedron, ...), defined by the ordered list of the nodes which constitute them and on which different types of finite elements, of boundary conditions or of loadings may be applied. The order of the nodes orients the mesh cell. This orientation must be established scrupulously because it is used in particular to define the orientation of the loadings (pressure, …). |

One can also define groups of these topological entities.

- **node groups**: named lists of node names,
- **mesh-cell groups**: named lists of mesh-cell names.

Systematically, whenever one has to refer to nodes (or to mesh cells), one will be able to refer to node groups (or to mesh-cell groups).

The interfaces with the meshers automatically generate such groups (according to criteria specific to the mesher).

These groups make it easier to assign the material characteristics on the mesh, the boundary conditions, or the printing of the results. Indeed, during such operations one refers to the nodes or to the mesh cells, which it is useful to describe by group.

The operator of *Code_Aster* DEFI_GROUP [U4.22.01](doc:u4.22.01) makes it possible to create groups a posteriori on any concept of type maillage already read.

It will be noted that all the entities handled in the code (nodes, mesh cells, node groups, mesh-cell groups) are **named** and usable at any moment by their name (**8 characters** at most for the mesh cells and the nodes, **24 characters** at most for the GROUP_MA and GROUP_NO).

The “case” of the names is preserved: for example, 'GR_AB' is different from 'gr_ab'. The numbering of the entities is never made explicit: it is used only internally in order to point to the values of the different associated variables.

### 2.3 End of a sub-file

It is the reserved and mandatory word FINSF which indicates the end of a sub-file, which begins with a MOTCLE.

## 3 List of the keywords (types of sub-files)

| TITRE | Description of the mesh file, of a documentary nature. The interface operators with meshers build a title from information specific to each mesher |
| --- | --- |
| / COOR_3D | Description of the nodes by three spatial coordinates: * name of the node described (or number interpreted as a name), * 3 coordinates, |
| / COOR_2D | Description of the nodes by 2 coordinates: * name of the node described (or number interpreted as a name), * 2 coordinates, |

```text
/    POI1                                        points            )
/    SEG2        /    SEG3        /    SEG4        segments        )
/    TRIA3        /    TRIA6        /    TRIA7        triangles        )
/    QUAD4        /    QUAD8        /    QUAD9        quadrangles    )    connectivité
/    HEXA8        /    HEXA20        /    HEXA27        hexaèdres        )    des mailles
/    PENTA6        /    PENTA15    /    PENTA18    pentaèdres    )
/    TETRA4        /    TETRA10                    tétraèdres    )
/    PYRAM5        /    PYRAM13                    pyramides        )
```

```text
GROUP_MA        Groupe de mailles (attention le nom est obligatoire)
```

```text
GROUP_NO        Groupe de noeuds (attention le nom est obligatoire)
```

- When a keyword has been read, it remains interpreted until the appearance of FINSF.
- After an FINSF, any unrecognised keyword (typing error) is ignored and a message is issued.
- COOR_2D and COOR_3D are mutually exclusive.
- The presence of a coordinate system in the IDEAS universal file causes the IDEAS/Aster interface to stop.

## 5 List of the description formats

We shall describe the format of the description of the information by a sequence of items.

### 5.1 Correspondence between item and FORTRAN type

```text
NOM_DE_NOEUD
CHARACTER*8

NOM_DE_MAILLE
CHARACTER*8

COORD
REAL*8

LIGNE_DE_TEXTE
CHARACTER*80
```

### 5.3 Repetition of the format

- Any repetition of the format must begin at the beginning of a line.

Examples:

Is **ILLEGAL**:

```text
COOR_2D

N1 1.            2.            N2            1.

3.

FINSF
```

Is **LEGAL**:

```text
COOR_2D

N1 1.

2.

N2 1.

3.

FINSF
```

## 6 Examples of a sub-file

Examples of sub-files describing the spatial coordinates of 5 nodes expressed in the basic global Cartesian frame. Here the content of the information is the same for the 2 sub-files; it is the mode of representation which differs.

### 6.1 File coming from the IDEAS–Aster interface

```text
COOR_3D    NOM=MAILLAGE1            NBOBJ=5            NBLIGE=5        NBLIGT=12
NUMIN=4                NUMAX=14

%            XMAX=10.0        YMAX=20.0        ZMAX=0.0

%FORMAT=(1*NOM_DE_NOEUD,3*COORD)

NO8        5.0        5.0            0.0

NO10        10.0    20.0        0.0

```
