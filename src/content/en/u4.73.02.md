# u4.73.02 Macro-command MACR_RECAL

## 1 Purpose

Recalibrate analysis results on experimental results or on other analysis results.

Consider, on the one hand, one or more test results and, on the other hand, one or more *Code_Aster* analyses modelling these tests. MACR_RECAL makes it possible to determine the parameters of these analyses (which may be parameters of a constitutive law, of a loading, etc.) describing the tests as well as possible.

For more details on the algorithms implemented, refer to [R4.03.06](doc:r4.03.06).

## 3 General presentation

### 3.1 Principle of the recalibration

Consider the model problem of identification of the elastoplastic characteristics $E$ , ${\sigma}_{y}$ , ${E}_{T}$ (respectively Young's modulus, yield stress and hardening modulus) of a material on a uniaxial tensile test.

On the one hand one has the experimental tensile curve giving the evolution of the stress as a function of time, which is a datum:

![Figure](/figures/u4.73.02/10000000000001B3000000E6C0499E934DBD9B1A.png)

On the other hand one has a **function** of the 3 parameters which, for each value of the triplet $E$ , ${\sigma}_{y}$ , ${E}_{T}$, returns a computed tensile curve:

![Figure](/figures/u4.73.02/10000000000002ED00000108C168D8BBAE3213F1.png)

The objective of the recalibration is then to answer the question:

*What are the values of* $(E,{\sigma}_{y},{E}_{T})$ *which describe my experiment as well as possible?*

### 3.2 Organisation of the recalibration

In order to carry out a recalibration successfully, it is necessary to have all of the following information:

- the $N$ experimental curves (an arbitrary weight may be assigned to each of these curves),
- the $P$ parameters to be recalibrated and, for each of them, an estimate of its initial value, its minimum value and its maximum value,
- the command file modelling the $N$ tests that one wants to recalibrate,
- the names of the $N$ quantities to be extracted from the command file above and which will be recalibrated on the $N$ experimental curves. These quantities must be contained in a table coming from POST_RELEVE_T.

The data setup of this information then requires the following organisation:

- a command file called the **master** containing the $N$ experimental curves, the $P$ parameters, the names of the quantities to be recalibrated as well as other information specific to the recalibration, the whole being supplied in MACR_RECAL. The various formats used are specified in what follows,
- a command file called the **slave** modelling the experimental tests.

Indeed, the recalibration is an **iterative** process: the master file executes the slave file, it recovers the $N$ curves computed with the current values of the $P$ parameters, it compares the values of the computed curves with those of the experimental curves, it deduces new values for the $P$ parameters and launches the slave file again. This process continues until convergence is obtained.

In the following part the operands of MACR_RECAL are described. Reference is made there to a few notions of the Python language. It is however in no way necessary to know Python in order to use this macro-command. The part “Example of use” is there to enlighten the user.

The data structure produced is a list of reals containing the values of the parameters at convergence in the event of convergence, or at the last iteration otherwise.

### 3.3 Particular case of use: mode EXTERNE

In this mode of use, the optimisation algorithm is external to *Code_Aster*.

![Figure](/figures/u4.73.02/10000000000004430000011717F85B1174CCF57F.png)

**Figure** 3.3-a **:** MACR_RECAL **method** EXTERNE

Code_Aster is only a black box which takes as input a text file containing the list of the parameter values, carries out the computation of the functional for this set of parameters, possibly carries out the computation of the gradients with respect to the parameters, and returns to the external algorithm, by means of a text file, the value of the functional and possibly of the gradients.

In this mode of operation, paragraph 3.1 remains valid.

### 3.4 Particular case of the recalibration of a dynamic model

In the case of the recalibration of the parameters of a dynamic model using experimental data coming from the dynamic analysis, there are a few particularities for the implementation. The experimental data are in this case natural frequencies and eigenvectors (mode shapes) contained in a mode_meca concept coming from the measurement.

The user has this concept from a data-acquisition software, usually in “.unv” format, and must build a so-called “experimental” model in order to use it in the Code_Aster environment. This “experimental” model contains, among other things, the experimental mesh, that is the mesh of the sensors, coarser than the mesh of the numerical model, which must also be available for the recalibration study.

The user therefore no longer has to supply the experimental curves in the master file, but will supply here the names of the concepts which contain them, concepts which will be extracted by a first slave analysis from the external “unv” file. The format used to transmit this information to MACR_RECAL is the same as that for RESU_CALC: a Python list of $N$ Python lists containing the names of the tables and of the columns containing the experimental responses.

Below one presents the diagram of the recalibration process in the case of dynamics:

![Figure](/figures/u4.73.02/1000000000000309000002990E1B7619C5D63D60.png)

**Figure 3.4-a. Diagram of the operation of the recalibration procedure in dynamics**

> Two other particularities concern the command file of the slave analysis:

- it also contains the commands necessary for the construction of the experimental model. The mode_meca concept usable to extract RESU_EXP is supplied by LIRE_RESU;
- The quantities corresponding to the experimental and numerical responses are always contained in tables but no longer necessarily coming from POST_RELEVE_T. The responses linked to the mode shapes come either from CREA_TABLE (for the experimental MAC criterion) or from MAC_MODES (for the numerical MAC criterion). One recalls that the MAC criterion [U4.52.15](doc:u4.52.15) serves to compare two modal bases; here it is the experimental one and the numerical one.

## 4 Operands

### 4.1 Operand UNITE_ESCL

```text
♦    UNITE_ESCL
```

Logical unit number of the slave file, assigned in the Astk interface (column UL). The extension of this file may be arbitrary.

### 4.2 Operands RESU_EXP, RESU_CALC, FONC_EXP, NOM_FONC_CALC, PARA_X, PARA_Y, POIDS

The user has 2 input modes for supplying the experimental data and the names of the tables and of the columns of the computed results.

He or she has the choice of using:

- RESU_EXP and RESU_CALC and possibly LIST_POIDS, which require the entry of Python lists,
- the keywords FONC_EXP, NOM_FONC_CALC, PARA_X, PARA_Y, POIDS of the factor keyword COURBE, which have the advantage of using Aster concepts.

```text
◊    RESU_EXP
```

Name of the Python list of $N$ numpy arrays containing the $N$ experimental curves. For a static model the list is defined beforehand in the form:

```text
resu_exp=[
    numpy.array([[x0,y0], [x1,y1], ... [xn,yn]]),
    ...
    numpy.array([[u0,v0], [u1,v1], ... [un,vn]])
]
```

For the recalibration of a dynamic model with experimental modal data (frequencies and eigenvectors), it will be the name of the Python list of $N$ Python lists containing the names of the tables and of the columns containing the experimental responses. For example:

```text
resu_exp=[[‘REPEX1’,’NUM_ORDR’,’FREQ’],[‘REPEX2’,’NUM_ORDR’,’MAC_EXP’]]
```

```text
◊    RESU_CALC
```

Name of the list of N Python lists containing the names of the tables and of the columns containing the numerical responses corresponding to the experimental measurements on which the recalibration will be carried out. For example:

```text
resu_calc=[['TABLE1’,’INST’,’SIYY’], ['TABLE2’,’INST’,’V1’], ...]
```

```text
◊    LIST_POIDS
```

Name of the Numpy array containing the $N$ weights to be assigned to the $N$ experimental curves. If the keyword is not supplied, then each curve has the same weight. The list is defined beforehand in the form:

```text
LIST_POIDS= numpy.array([p1, p2, ...])
```

```text
◊    FONC_EXP
```

Name of the function previously defined by the operator DEFI_FONCTION which corresponds to the experimental data. To make the link with RESU_EXP, the function supplied to this keyword at iteration $i$ corresponds to the $i$ th numerical array of RESU_EXP.

```text
   ◊    NOM_FONC_CALC

Chaîne de caractères correspondant au nom que l'on souhaite attribuer à la fonction après     recalage des données expérimentales.
```

```text
   ◊    POIDS

Valeur du poids à affecter à la courbe expérimentale. Si non renseigné, alors la valeur est 1.
```

```text
◊    PARA_X
```

Name of the parameter $X$ of the computed function.

```text
◊    PARA_Y
```

Name of the parameter $Y$ of the computed function. For example:

```text
COURBE=(

_F(FONC_EXP=fct1, NOM_FONC_CALC='TABLE1',PARA_X='INST',PARA_Y='SIYY',),

_F(FONC_EXP=fct2, NOM_FONC_CALC='TABLE2',PARA_X='INST',PARA_Y='V1',),)
```

### 4.3 Operands LIST_PARA, PARA_OPTI, NOM_PARA, VALE_INI, VALE_MIN, VALE_MAX

The user has 2 input modes for supplying the names and the values of the parameters.

He or she has the choice of using:

- LIST_PARA, which require the entry of Python lists,
- the keywords NOM_PARA, VALE_INI, VALE_MIN, VALE_MAX of the factor keyword PARA_OPTI, which have the advantage of using Code_Aster concepts (numerical values or character strings).

```text
◊    LIST_PARA
```

Name of the Python list of $P$ Python lists containing the names of the variables, their initial values, their minimum values and their maximum values. This list is defined beforehand in the form:

```text
List_para=[['PARA1__’, INI_1, MIN_1, MAX_1],
    [‘PARA2__’, INI_2, MIN_2, MAX_2],
    ....
    [‘PARAP__’, INI_P, MIN_P, MAX_P]]
```

**Warning:**

*One requires that the names of the variables end with two underscores (for example:* *YOUN__).*

**Note:**

*The bounds are not handled by the algorithms FMIN, FMINBFGS and FMINNCG.*

```text
◊    NOM_PARA
```

Name of the parameter. The character string supplied to NOM_PARA at iteration $i$ corresponds to the first element of the $i$ th Python list of the list supplied to LIST_PARA.

```text
◊    VALE_INI
```

Initial value of the parameter. The real supplied to NOM_PARA at iteration $i$ corresponds to the second element of the $i$ th Python list of the list supplied to LIST_PARA.

```text
◊    VALE_MIN
```

Minimum value of the parameter. The real supplied to NOM_PARA at iteration $i$ corresponds to the third element of the $i$ th Python list of the list supplied to LIST_PARA.

```text
◊    VALE_MAX
```

Maximum value of the parameter. The real supplied to NOM_PARA at iteration $i$ corresponds to the fourth element of the $i$ th Python list of the list supplied to LIST_PARA.

### 4.8 Operand TOLE_FONC

```text
◊    TOLE_FONC
```

Stopping criterion of the recalibration algorithm based on the variation of the functional from one iteration to the next. This criterion corresponds to the absolute value of the norm of the functional.

### 4.9 Operand TOLE_PARA

```text
◊    TOLE_PARA
```

Stopping criterion of the recalibration algorithm based on the variation of the parameters from one iteration to the next. This criterion corresponds to the $\mathit{L2}$ norm: square root of the sum of the squares of the differences of each parameter.

### 4.10 Operand PARA_DIFF_FINI

```text
◊    PARA_DIFF_FINI
```

The recalibration requires the computation of the derivatives of the responses with respect to the parameters.

This computation is carried out by finite differences. PARA_DIFF_FINI corresponds to $\alpha$ in the following formula:

$\frac{\partial f}{\partial x}\approx \frac{f(x+\alpha x)-f(x)}{\alpha x}$

### 4.11 Operand GRAPHIQUE

```text
◊    UNITE
```

Logical unit number of the plots produced during the recalibration. At each iteration, MACR_RECAL produces $N$ graphic files (whose format is defined by the keyword PILOTE) representing the $N$ experimental and computed curves.

```text
◊    PILOTE
```

Type of display of the plots.

If PILOTE = 'INTERACTIF' or 'INTERACTIF_BG', xmgrace is opened interactively with the plot. With 'INTERACTIF_BG', xmgrace is called in the background and the analysis continues.

If PILOTE is 'POSTSCRIPT', 'EPS', 'MIF', 'SVG', 'PNM', 'PNG', 'JPEG' or 'PDF' then xmgrace is used to generate the file of the corresponding format, in the logical unit defined by UNITE.

**Warning:**

*The* INTERACTIF *mode is possible only when the recalibration runs interactively and not in batch.*

```text
◊    FORMAT
```

Choice of the software for displaying the curves in interactive mode: xmgrace or gnuplot. The use of Xmgrace is blocking: one must close the Xmgrace window in order to continue the execution.

```text
◊    AFFICHAGE
```

Display of the curves at each iteration or only at the end.

### 4.12 Operand METHODE

```text
◊    METHODE
```

Method or optimisation algorithm chosen:

1. LEVENBERG (default): Levenberg–Marquardt algorithm. This algorithm is the one recommended for quadratic minimisation problems of least-squares type, such as problems of recalibration of material parameters.
2. FMIN: Nelder–Mead simplex algorithm (uses only estimates of the functional).
3. FMINBFGS: quasi-Newton method (uses the functional and the gradient of the functional).
4. FMINNCG: line-search Newton conjugate-gradient method (uses the functional, the gradient of the functional and its Hessian).
5. GENETIQUE: evolutionary algorithm based on the mechanism of selection and replacement. It is an algorithm which is expensive in CPU time; its use is advised only for a coarse exploration of the parameter space within the hybrid recalibration technique presented in the following point.
6. HYBRIDE: technique which combines the stochastic with the deterministic — the evolutionary algorithm with the Levenberg–Marquardt algorithm.
7. Mode EXTERNE: this method makes it possible to use an optimisation algorithm external to *Code_Aster*, for example Matlab or Scilab, and to use *Code_Aster* only for the estimation of the functional and possibly of the gradient by finite differences. This is not a keyword of MACR_RECAL, because mode EXTERNE is used directly by calling the file bibpyt/Macro/recal.py.

**Concerning the choice of the optimisation algorithm**, it is strongly advised to opt for the default algorithm, **Levenberg–Marquardt**. The latter is very often superior to the FMIN* algorithms for minimisation problems of least-squares type, such as the recalibration of parameters. Indeed, it uses the functional in its vector form whereas the other algorithms use a scalar functional, consequently less rich. Moreover, it uses an active-constraint method in order to handle bounds on the parameters, whereas the other algorithms do not handle the bounds.

The other algorithms may nevertheless be useful in the cases where Levenberg–Marquardt is in difficulty. For example, the FMIN algorithm does not use gradients, whose evaluation may in certain very particular cases generate numerical problems (very sensitive parameters, too few experimental values, or others). The FMIN algorithm is distinctly slower, but will be able to reach convergence (to draw a parallel, the issue is similar to that of using the elastic matrix in place of the tangent matrix in STAT_NON_LINE).

For the Levenberg–Marquardt algorithm, the document [R4.03.06](doc:r4.03.06) describes more precisely the mathematical algorithms brought into play.

The FMIN* algorithms have been taken over in full from a Python module distributed on the Internet ([http://pylab.sourceforge.net](http://pylab.sourceforge.net)) under the GPL licence by Travis E. Oliphant, who is moreover the principal contributor to the Python-Scipy project and responsible for the optimisation module of Scipy. The details of the algorithms and of the implementation can be found on the page
[http://pylab.sourceforge.net](http://pylab.sourceforge.net/).

The HYBRIDE method is advised when one has a high degree of uncertainty on the optimal values of the parameters or when the functional presents numerous local minima. Thus, within this method, one first launches a coarse search with the evolutionary algorithm, which will make it possible to avoid the local minima, followed by a refinement of the optimisation with the Levenberg–Marquardt algorithm.

### 4.13 Keyword CALCUL_ESCLAVE

#### 4.13.1 Operand LANCEMENT

```text
◊    LANCEMENT
```

Method of launching the slave files: inclusion or distribution. The two modes have advantages and disadvantages, and the choice of one or the other depends mainly on the run times of the slave files, as well as on their compatibility with Inclusion mode.

#### 4.13.2 Operand INCLUSION

```text
◊    INCLUSION
```

In this mode, the slave file is included. There is therefore no loss of time for the generation of a new study, the creation of the temporary execution directory, etc. In return, only one slave study will be able to run at the same time on the machine. On the other hand, certain slave studies (for example those using included data files, or somewhat complex execution profiles) are not compatible.

**Note:**

*In INCLUSION mode, the Aster command INCLUDE cannot be present in the slave file (incompatibility with the Aster supervisor).*

*One must therefore replace the command:*

*INCLUDE(UNITE=n)*

*by the command:*

*execfile(fort.n)*

*where n is the logical unit of the file to be included.*

#### 4.13.3 Operands DISTRIBUTION, MODE, MEMOIRE, TEMPS, CLASSE, UNITE_SUIVI

```text
◊    DISTRIBUTION
```

In this mode, at each iteration of the optimisation algorithm, the $N+1$ slave analyses (for a recalibration of $N$ parameters) are executed in parallel, in batch or interactively, using the distributed-analysis module of as_run. Compared with Inclusion mode, each study is slightly longer to execute, because one must regenerate a new Code_Aster study, create the temporary files, etc. On the other hand, as the studies are launched in parallel, depending on the characteristics of the slave studies (size and duration), the larger the number of parameters, the more Distributed mode becomes advantageous over Inclusion mode.

In distributed mode, additional parameters are available in order to control the executions of the slave analyses:

```text
◊    MODE : INTERACTIF ou BATCH
◊    MEMOIRE : mémoire en Mo
◊    TEMPS : temps en secondes
◊    CLASSE : classe de batch, permet de forcer les calculs à utiliser une classe spécifique, par exemple «distr» sur le serveur Code_Aster
◊    UNITE_SUIVI : si ce mot-clé est préciser, il défini l'unité logique du fichier du profil dans lequel seront stockés tous les fichiers output des jobs esclaves
◊    NMAX_SIMULT: nombre de calculs esclaves lancés en parallèle en mode distribution (si aucune valeur n'est renseigné, le code décide automatiquement de ce nombre)
```

It is possible to use MPI parallelism for the slave studies. In this case, it is necessary to launch the master analysis with an MPI version and on a single processor (in interactive mode or in batch). The MPI characteristics of the slave analyses must be indicated by the following keywords:

```text
◊    MPI_NBCPU: nombre de processeurs MPI pour chacun des calculs esclaves lancés en parallèle
◊    MPI_NBNOEUD: nombre de nœuds pour chaque calcul esclave lancé en parallèle
```

One notes that operating problems may disturb the launching of the distributed slave analyses (for example, the batch classes are badly defined and the analyses cannot execute). In this case, the error obtained in the .mess of the master analysis may be rather terse (an error message of the kind “at least one of the slave analyses could not start”). In order to obtain additional information concerning the distributed module of as_run, one must set UNITE_SUIVI and INFO=2 simultaneously.

### 4.14 Operands NB_PARENTS and NB_FILS

```text
◊    NB_PARENTS
```

For the method GENETIQUE or HYBRIDE, this operand defines the size of the population of the parameter sets. Initially all the individuals are identical and initialised with the initial values of the parameters supplied by the user in LIST_PARA. During the optimisation the population evolves, the least “adapted” individuals being replaced by others which have supplied a better value of the functional.

```text
◊    NB_FILS
```

Represents the replacement rate of the population. More precisely, the best “parent” (the one for which the value of the functional is the smallest) is allowed to reproduce, thus generating NB_FILS “children”. At that moment the size of the population is NB_PARENTS+NB_FILS. According to the hierarchy of the values of the functional, only the best individuals of this whole population are retained and one returns to the initial size: NB_PARENTS.

### 4.15 Operand ECART_TYPE

```text
◊    ECART_TYPE
```

This is the value of the standard deviation that the user imposes for the quasi-random draws of the “children”. The more one wants to explore the topological space of the parameters, the more one must increase this value. Corroborated with the size of the population and the replacement rate, this operand makes it possible to drive the evolutionary algorithm according to the complexity of the model and the degree of uncertainty on the optimal values of the parameters. If one knows little about the values of the parameters to be recalibrated, it is advisable to use a large population size, a likewise high replacement rate and a large standard deviation. The counterpart will be a very high CPU time.

### 4.16 Operand ITER_ALGO_GENE

```text
◊    ITER_ALGO_GENE
```

Maximum number of iterations for the evolutionary algorithm. If one uses the HYBRIDE method, this value (or RESI_ALGO_GENE) will determine the switch to the Levenberg–Marquardt algorithm.

### 4.17 Operand RESI_ALGO_GENE

```text
◊    RESI_ALGO_GENE
```

Relative residual of the recalibration of the evolutionary algorithm. If one uses the HYBRIDE method, this value (or ITER_ALGO_GENE) will determine the switch to the Levenberg–Marquardt algorithm.

### 4.18 Operand GRAINE

```text
◊    GRAINE
```

Value imposed by the user for the seed of the generator of the random draws in the evolutionary algorithm. If one supplies a value for this keyword, one forces the random-number generator present in the evolutionary algorithm to generate always the same draws, and one will therefore have a repetition of the solution. Its use is reserved **only** for the test cases, for reasons of monitoring the non-regression of the code.


```text

```

For the methods FMINBFGS, FMINNCG or EXTERNE, this keyword makes it possible to indicate to *Code_Aster* the way of computing the gradients (non-dimensionalised or not), or else not to compute them.

## 5 Precautions of use

Here is a set of pieces of advice **indispensable** to the proper use of the recalibration.

- The experimental curves are defined as arrays with two columns: one for the abscissae and one for the ordinates.
- The experimental curves must be functions: only one ordinate must correspond to an abscissa. If an experimental curve contains cycles (for example stress as a function of strain in loading–unloading), one must then split this parameterised curve into two curves, expressing on the one hand the abscissae and on the other hand the ordinates of the cyclic curve as a function of the parameter (for example strain as a function of time and stress as a function of time).

![Figure](/figures/u4.73.02/Shape8.gif)

- One must recalibrate $N$ computed curves on $N$ experimental curves.
- The first computed curve will be recalibrated on the first experimental curve, the second computed curve will be recalibrated on the second experimental curve, and so on in the order supplied for the operands RESU_EXP and RESU_CALC.
- The computed quantities supplied under the operand RESU_CALC must come from POST_RELEVE_T (except for dynamics, where one may have tables coming from CREA_TABLE and MAC_MODES).
- The recalibration parameters must be declared as a block at the beginning of the slave command file. For example:

```python
DEBUT()

DSDE__ = 200.

YOUN__ = 8.E4

SIGY__ = 10.

......
```

- The initial values of the recalibration parameters are those supplied for the operand LIST_PARA and not those present in the user's slave file.
- At each recalibration iteration, the analyses defined in the slave file must converge. In the context of the recalibration of non-linear analyses, it is therefore strongly recommended to use the automatic cutting of the time step.
- In the context of the recalibration of non-linear analyses with automatic cutting of the time step, it is **indispensable** to define an archiving list under the operand LIST_ARCH.
- The recalibration is a powerful means of obtaining parameter values from tests. It is however not miraculous: the **experimental** curves must contain enough information to identify the parameters. It is for example impossible to identify elastoplastic parameters with a test remaining in the elastic domain. The experimental tests must therefore excite the parameters to be identified.
- In the same logic, it is desirable that the **experimental** curves contain a sufficient number of points to describe properly the action of the parameters to be identified.
- Finally, in the case of the use of several experimental curves, the fact that they have the same number of points balances the information that they provide.

#### 6.2.1 Data setup

In the master file one first supplies the names of the tables which will contain both the computed results and the numerical results:

```python
calcul = [["REPONSE1", "NUME_ORDRE", "FREQ"], ["REPONSE2", "NUME_ORDRE", "MAC"]]

experience = [["REPEXP1", "NUME_ORDRE", "FREQ"], ["REPEXP2", "NUME_ORDRE", "MAC_EXP"]]
```

### 6.3 Parametric identification of a conservative system by exploiting the orthogonality of the eigenmodes

This example is treated by modelling D of the test case SDLS121 [V2.03.121](doc:v2.03.121).

One wishes to recalibrate the thickness of a plate and the value of a discrete mass which is located on it, by using experimental measurements of eigenmodes.

From the mode shapes recorded at the observation points, one carries out an expansion onto the supporting numerical model. One then tries to recover the parameters of the model such that the generalised mass and stiffness matrices relative to the modes identified experimentally are diagonal and that the discrepancy between the measured natural circular frequency and the computed natural circular frequency is minimal.

#### 6.3.1 Data setup

The technique illustrated here exploits the identified mode shapes extended onto the supporting numerical model. This mode shape can be obtained by means of an independent analysis by depositing the extended shapes in a file which will later be read by the slave file. For practical reasons, one carries out the expansion in the driving file. It is thus easier to recover the support model which will be used in the slave file.

In the master file one supplies both the target values (experimental values) and the names of the tables which contain the results coming from the numerical analysis carried out in the slave file.

The different steps are recalled below.

- Creation of an experimental model in order to be able to define the location of the measurement points. The nodes of the mesh may be linked to one another by discrete elements in order to facilitate the visualisation of the measured information. The mechanical characteristics that one assigns to this model do not influence the results; they allow the model to receive the identified eigenmodes
- Reading of the identified eigenmodes
- Creation of the supporting numerical model for the expansion of the measurement
- Definition of the expansion basis (here, a modal basis)
- Computation of the coordinates of the identified modes in the expansion basis
- Expansion of the measured information onto the support model
- Writing of the extended modes in a file in order to be able to use it in the slave analysis
- Definition of the target values

The target values are deposited in two lists. The first list contains the off-diagonal terms which should be zero and the second list contains the identified natural frequencies.

- Definition of the recalibration parameters
- Launching of the optimisation procedure

#### 6.3.2 Slave analysis

The slave analysis creates the tables which will contain the values computed from the input parameters. The different analysis steps are described below:

- Creation of the support model (same numbering of the degrees of freedom as that which served for the expansion of the measurement)
- Reading of the extended mode shapes
- Computation of the generalised mass and stiffness matrices via MAC_MODES
- Creation of the tables which contain the off-diagonal terms of the generalised matrices
- Creation of the table which contains the natural frequencies estimated by means of the generalised matrices

### 6.4 Parametric identification of a dissipative system by exploiting the norm relations of the mode shapes

This example is treated by modelling E of the test case SDLS121 [V2.03.121](doc:v2.03.121).

One wishes to recalibrate the thickness of a plate, the value of a point mass on the plate and the discrete dampings distributed over the plate.

From the complex mode shapes recorded at the observation points, one carries out an expansion onto the supporting numerical model. One then tries to recover the parameters of the model in such a way that the eigenmodes identified experimentally satisfy the norm relations associated with the numerical model. One focuses only on the diagonal terms of the normalisation matrix.

#### 6.4.1 Data setup

The data setup resembles that presented in the previous chapter (6.3). The difference lies in the expansion of the mode shape. The mode shapes are complex here. One carries out the expansion by processing the real part and the imaginary part independently. The extended complex shape is obtained after assembly of the extended real shape and of the extended imaginary shape.

The different steps are described below:

- Creation of the experimental model
- Reading of the identified (experimental) eigenmodes
- Expansion of the measurement
- Definition of the target values (the target values are zero vectors here)
- Definition of the recalibration parameters
- Launching of the optimisation procedure

#### 6.4.2 Slave analysis

The slave analysis creates the tables which will contain the diagonal terms of the normalisation matrix.

The different analysis steps are described below:

- Creation of the support model (same numbering of the degrees of freedom as that which served for the expansion of the measurement)
- Reading of the extended mode shapes
- Reading of the natural frequencies and of the reduced damping ratios
- Computation of the matrix–vector products by PROD_MATR_CHAM
- creation of the table which contains the terms relating to damping and mass: $\frac{{y}_{\nu}^{T}B\bar{{y}_{\nu}}+2\Re ({s}_{\nu}){y}_{\nu}^{T}M\bar{{y}_{\nu}}}{\mid {n}_{\nu}\mid }={z}_{1\nu }$
- creation of the table which contains the terms relating to stiffness and mass: $\frac{{s}_{\nu}\bar{{s}_{\nu}}{y}_{\nu}^{T}M\bar{{y}_{\nu}}-{y}_{\nu}^{T}K\bar{{y}_{\nu}}}{\mid {n}_{\nu}{s}_{\nu}\mid }={z}_{2\nu }$
- creation of the table which contains the terms relating to mass, stiffness and damping: $\frac{{s}_{\nu}^{2}{y}_{\nu}^{T}{\mathit{My}}_{\nu}+{s}_{\nu}{y}_{\nu}^{T}{\mathit{By}}_{\nu}+{y}_{\nu}^{T}{\mathit{Ky}}_{\nu}}{{n}_{\nu}{s}_{\nu}}={z}_{3\nu }$

## 7 Use of mode EXTERNE

### 7.1 Warning

We draw attention to the fact that this mode of operation is to be reserved for advanced use. Most cases should be treated with the algorithms supplied in the command MACR_RECAL, and in particular the Levenberg–Marquardt algorithm, which is the best suited to problems of parameter recalibration.

This mode of operation requires external software in order to carry out the optimisation (Python code, Matlab, Scilab, black-box type software, etc.). Moreover, it is necessary to have some Python skills.

**Finally, the use of mode EXTERNE falls outside the quality-assurance scope of Aster**, and should not be used for safety-important studies (IPS).

### 7.2 Methodology

#### 7.2.1 Principle

In this mode of use, *Code_Aster* is used only for the evaluation of the functional for an optimisation software which is completely external to *Code_Aster*.

![Figure](/figures/u4.73.02/10000000000004350000010FAD02ED26C44BAC83.png)

**Figure** 7.2.1-a **:** MACR_RECAL **“External algorithm”**

Generally, optimisation software packages ask the user to write a procedure for the computation of the functional: f = F(param).

If the software allows the reading/writing of files and the execution of external code (“system” command or others), then it is potentially usable with MACR_RECAL. One will encapsulate the call to the Python procedure **recal.py** as well as the writing of the parameter file and the re-reading of the file of the value of the functional in the routine for the computation of F.

![Figure](/figures/u4.73.02/1000000000000469000001B4C28F438388EBCB2C.png)

**Figure** 7.2.1-b **:** MACR_RECAL **“Principle of mode EXTERNE”, example** Matlab

The optimisation software launches *Code_Aster* at each evaluation of the functional. The functional-evaluation routine goes through text files in order to send to *Code_Aster* the parameters to be used and in order to recover the value of the functional. The Python routine recal.py can therefore be called independently of Aster and makes the link between the optimisation software and *Code_Aster* (recovery of the parameter file, reformatting of the slave file, launching of Aster, recovery of the functional).

In practice, one must have a classical Astk profile of the slave study (and not the profile of one use of MACR_RECAL). This profile must be completely functional.

Under this EXTERNE mode, the mode of operation is the following: the routine recal.py takes care of recovering the parameters from the command line or from an input.txt file, will replace these parameters in the slave profile, then will launch the execution of the slave study for the new parameters, and finally will return in a text file output.txt the values of the functional.

To date, this mode of operation has been tested with several optimisation software packages (the optimisation *toolbox* of Matlab, the Tomlab *toolbox* for Matlab, and the optimisation module of Python-Scipy), but it is possible to use almost any software provided that this software allows the external execution of a script. One thinks in particular of Zopt (Zebulon), SiDoLo.

This procedure needs:

1. the .export file of the Astk study defined previously (the standard MACR_RECAL study)
2. a text file containing the list of the parameters

From these two files, it launches a *Code_Aster* analysis for the specified parameters (or two *Code_Aster* analyses, see above) and generates a text file containing only the value of the functional (scalar or vector).

This procedure can be launched without an argument. It will then look **in the current directory** for default files:

1. if there is only one .export file in the current directory, it will be used (otherwise the procedure stops in error)
2. the default input file will be looked for under the name “input.txt”
3. the output file will be generated with the name “output.txt”

The arguments –i (--input) and -o (--output) make it possible to specify the files.

The argument –g (--output_grad) makes it possible to specify the text file in which the gradient will be written, if the latter is requested (argument -G).

Other arguments are available:

1. --info: defines the message level; 0=silent, 1 or 2;
2. --objective: makes it possible to specify whether the functional must be returned in vector or scalar form;
3. --gradient: makes it possible to specify whether one does not want Aster to compute and return the gradients (no), and, if one wants the gradients, to specify whether one wants them non-dimensionalised or not;

By default, a *Code_Aster* .output file is created in the execution directory of the procedure, making it possible to have access to the output of the last *Code_Aster* analysis.

Finally, one must configure the environment variable ASTER_ROOT (the base path of Aster) in order to be able to launch the file recal.py in Python, or else use the argument --aster_root.

The proper operation of the procedure recal.py can be checked manually, by generating an input file with parameter values and by launching the procedure manually. Example on the *Code_Aster* machine:

cd directory

export ASTER_ROOT=/aster

echo “10., 20., 30. ” >input.txt

Python $ASTER_ROOT/NEW10/bibpyt/Macro/recal.py etude.export –-info=2

cat ouput.txt

The *Code_Aster* analysis should launch and finish properly. An output.txt file must be generated in the current directory.

### 7.3 Example: optimisation module of Matlab©

If one takes up the principle again and applies it to an optimisation algorithm which would be written in Matlab, one must write two files go.m and fonction.m which carry out the actions described below:

![Figure](/figures/u4.73.02/1000000000000473000001B239F3CF50B8EEDE7A.png)

**Figure** 7.3-a **:** MACR_RECAL **“Principle of mode EXTERNE” applied to** Matlab©

The following example uses the optimisation module of Matlab and carries out the *Code_Aster* analyses on the local server.

**File go.m** (initialisation and launching of the optimisation)

```text
clear all;

format long;

system('rm -f fort.91');

options = optimset('Display', 'iter', 'LevenbergMarquardt', 'on', 'TolFun', 1e-8, 'MaxFunEvals', 1000, 'MaxIter', 100);

% Params : DSDE__, SIGY__, YOUN__

x0 = [:ref:` 1000., 30., 100000.  < 1000., 30., 100000. >`];

lb = [:ref:` 500., 5., 50000.  < 500., 5., 50000. >`];

ub = [:ref:` 10000., 500., 500000.  < 10000., 500., 500000. >`];

% vecteur

[x,resnorm,residual,exitflag,output,lambda,jacobian] = lsqnonlin(@fonction,x0,lb,ub,options)

% scalaire

%[x,fval,exitflag,output] = fmincon(@fonction,x0,[],[],[],[],lb,ub,[],options)
```

**File fonction.m** (computation of F(param)) / Linux version

```text
function f = fonction(x)

system('rm -f input.txt');

system('rm -f output.txt');

% Ecriture des parametres

dlmwrite('input.txt', x, 'precision', '%.20f');

% Local

iret = system('export ASTER_ROOT=/opt/aster ; Python $ASTER_ROOT/NEW10/bibpyt/Macro/recal.py **etude.export**  --objective_type=vector');

f = dlmread('output.txt', ',', 0, 0); % relit un scalaire ou un vecteur
```

In go.m, one gives two examples of algorithms. The algorithm lsqnonlin minimises a vector functional and one must therefore uncomment the first line “iret=”. This algorithm is based on Levenberg–Marquardt with active constraints, and is therefore similar to the one implemented in *Code_Aster*.

**Note:**

*It is important to note the presence of the command* *format long and of the argument* *precision for the command* *dlmwrite. This makes it possible to work with a sufficient number of significant digits and not to stop if the tolerance on the function is no longer satisfied.*

**Note 2:**

*When the optimisation software is not capable of handling the return codes of the external execution, one must take care to stop the procedure cleanly in the event of an abnormal stop of the Code_Aster analysis. This is the reason why one deletes the files* *input.txt and* *output.txt just after their use, so as not to fall into endless loops.*
