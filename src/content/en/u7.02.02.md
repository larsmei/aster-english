# u7.02.02 Operator LIRE_CHAMP

## 1 Purpose

Read a field from a file in MED format and store it in a concept of type field.

The field is designated in the file by its name and possibly by a time parameter.

The concept produced is of the type corresponding to what was requested.

## 3 Operands

### 3.1 Operand FORMAT

```text
◊    FORMAT =    'MED'
```

Choice of the format of the file containing the field to be read.

**Note:**

*Only the format* *MED is operational today. However, with the sequence of* *LIRE_TABLE then* *CREA_CHAMP/EXTR_TABLE* *one can read a field stored in a table in the format* *ASTER*

### 3.2 Operand TYPE_CHAM

```text
♦    TYPE_CHAM =        /    'NOEU_TEMP_R' ,
/    'NOEU_DEPL_R' ,
/    'ELGA_SIEF_R' ,
/    etc ...
```

One designates here the type of the concept to be produced. The name of the type is built with the usual *Code_Aster* logic. The first four characters are 'NOEU', 'ELEM', 'ELNO', 'ELGA' or 'CART'. One then finds '_'. The following sequence defines the type of field: 'TEMP', 'DEPL', 'SIEF', etc. ... The name ends with '_R', '_F' or '_C' according to the computer type of the values.

Example: 'NOEU_TEMP_R', 'NOEU_DEPL_R', 'ELGA_SIEF_R' etc. ...

**Warning:**

*There is no consistency check! One may very well create a temperature concept by rereading a field that was a displacement when the file was written.*

**Note:**

*It may happen that values read in the file are not assigned in the final field. For example, if one reads a pressure field on TETRA4 elements whereas it must be assigned to boundary mesh cells (because that is its nature), one will be warned by this type of alarm:*

*<A> <LIRE_RESU> <LRCEME>*

*VALUES NOT ASSIGNED IN THE FIELD: 3699*

*VALUES READ IN THE FILE* *: 3699*

### 3.3 Operand MAILLAGE

```text
♦    MAILLAGE = ma
```

Name of the ASTER mesh on which the field to be read will be expressed.

#### 3.3.1 Operands NUME_DDL

In the case of a model mixing different modellings (for example: 3D and beams), it may be of interest to use this keyword so that the field produced carries the correct components on the nodes of the mesh. Without this keyword, the field produced will be rectangular, of size number of nodes * maximum number of components over all the nodes.

### 3.4 Operand NOM_MED

```text
♦    NOM_MED=    nommed
```

Name, according to the MED convention, of the field to be read in the file. It is a string of 32 characters.

### 3.5 Operand MODELE

```text
◊    MODELE = mo
```

Name of the ASTER model on which the field to be read will be expressed. This operand is mandatory if the field to be read is a "by elements" field (TYPE_CHAM='ELxx_yyyy')

### 3.6 Operand PROL_ZERO

```text
◊    PROL_ZERO = 'NON' / 'OUI'
```

When one creates a "by elements" field, the structure of this field is imposed by Aster. If, for example, one creates an "ELNO" stress field on a 3D model, all the nodes of the elements must carry the components SIXX, SIYY, …, SIYZ. If the MED field that one reads does not possess all the values expected by Aster, one must "invent" these missing values. The "invented" value will be 0. if PROL_ZERO='OUI'; it will be "NaN" (Not a Number) if PROL_ZERO='NON'

### 3.7 Selection of the time parameter NUME_ORDRE, NUME_PT, INST, CRITERE, PRECISION

If the field was written in the file without reference to a time parameter, nothing is to be mentioned in this reading command. Otherwise one must specify which time instant it is. This is done by designating an order number, a time step or a value of an archiving time instant. Refer to the document [U4.71.00](doc:u4.71.00) for the details on these keywords.

### 3.8 Operand NOM_CMP_IDEM or NOM_CMP and NOM_CMP_MED

> The user must necessarily put NOM_CMP_IDEM or NOM_CMP in the command file.

#### 3.8.1 Operand NOM_CMP_IDEM

```text
◊    /    NOM_CMP_IDEM = 'OUI'
```

Indicates that one must read in the MED file the components whose same name appears in the list of the components of the field in the *Code_Aster* sense.

#### 3.8.2 Operands NOM_CMP, NOM_CMP_MED

```text
◊    /    ♦    NOM_CMP        =    lcmp ,
♦    NOM_CMP_MED    =    lcmpmed ,
```

These two lists must be of the same length. One reads in the MED file the components listed in lcmpmed, then one assigns them to the components in the *Code_Aster* sense, of the same rank in the list lcmp.

### 3.9 Operand NOM_MAIL_MED

```text
◊    NOM_MAIL_MED= nomamed
```

If this operand is absent, one looks for the field linked to the first mesh in the file. This is what happens when the file contains only one mesh.

If the file contains several meshes, one specifies here which one is associated with the field that one wants to read.

### 3.10 Operand UNITE

```text
◊    UNITE=    unite
```

Logical-unit number of the file; it corresponds to the value supplied in astk or by using the command DEFI_FICHIER.

### 3.11 Operand INFO

```text
◊    INFO    =    /    1 ,[DEFAUT]
/    2 ,
```

If INFO is equal to 2, a few debugging printouts take place.

Otherwise, nothing takes place.

## 4 Example

```text
temp2    =    LIRE_CHAMP    (
MAILLAGE        =    m2,
NOM_MED        =    'RESUUN__TEMP',
NUME_ORDRE    =    2,
TYPE_CHAM        =    'NOEU_TEMP_R',
)
```

This command will create a field at the nodes of name temp2 and of type NOEU_TEMP_R. The support mesh is m2. The values are those stored under the name RESUUN__TEMP in the MED file supplied on unit 81 with the order number 2.
