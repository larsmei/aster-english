# u4.67.01 Operator DEFI_BASE_REDUITE

The purpose of the operator is to build the reduced basis from a non-linear analysis (thermal or mechanical) or from a parametric linear analysis.

There are two methods:

- For non-linear problems, the operator relies on an sd_resultat of type evol_ther or evol_noli and carries out a singular value decomposition (SVD) on the transient or an incremental POD type strategy;
- For parametric linear problems, one uses a greedy-type algorithm. In this case, one defines the linear system to be solved.

The operator also makes it possible to truncate a basis (primal or dual) onto a reduced domain (for example produced by the command DEFI_DOMAINE_REDUIT).

Two types of basis can be produced:

- the so-called "primal" bases: they rely on the displacement fields for mechanics and on the temperature fields for thermal analysis;
- the so-called "dual" bases: they rely on the stress fields for mechanics and on the flux fields for thermal analysis.

The operator produces a concept of type mode_empi.

## 2 Operands

The operator returns a data structure of type mode_empi (empirical modes).

### 2.1 Operand BASE

It is possible to enrich a basis of empirical modes by the following operations. In this case, one supplies it here.

### 2.2 Operand OPERATION

This keyword makes it possible to choose the way of computing the empirical modes:

- By a POD (OPERATION='POD'): one carries out an SVD on the snapshot matrix containing the results over a transient. This operation is exact (in the sense of the extraction of the empirical modes) but may potentially be costly (in CPU and in memory);
- By an incremental POD (OPERATION='POD_INCR'): one builds the empirical basis in an incremental manner (see [R5.01.50](doc:r5.01.50)). This method is less accurate than the classical POD but much less costly. Moreover, it makes it possible to enrich an existing empirical basis with new results;
- By a greedy method (OPERATION='GLOUTON', see [R5.01.50](doc:r5.01.50)) on parametric problems;

It is also possible to truncate a basis (primal or dual) onto a reduced domain (for example produced by the command DEFI_DOMAINE_REDUIT) with OPERATION='TRONCATURE' or to re-orthogonalise an existing basis by the keyword OPERATION='ORTHO'.

### 2.3 Operands for the POD strategies

#### 2.3.1 Operand RESULTAT

Name of the result data structure to be analysed in order to generate the reduced basis. Two possible types of result: evol_noli or evol_ther.

Limitations of use:

- Works only in 3D (thermal and mechanical);
- One cannot use Dirichlet boundary conditions by dualisation (AFFE_CHAR_MECA or AFFE_CHAR_THER). One must use Dirichlet boundary conditions by elimination (AFFE_CHAR_CINE).

#### 2.3.2 Operand SNAPSHOT

This keyword makes it possible to filter the time instants in the result given by the keyword RESULTAT in order to generate the snapshot matrix. The selected time instants are referenced by their order number.

#### 2.3.3 Operand TABL_COOR_REDUIT

When one computes an empirical basis by the incremental POD method in order to enrich an already existing basis, it is necessary to have the reduced coordinates of the previous analysis. These coordinates are stored in a data structure table named 'COOR_REDUIT' which is attached to the empirical basis. One can recover it via the operator RECU_TABLE. For example:

```python
coorredp = RECU_TABLE(CO=base, NOM_TABLE="COOR_REDUIT")
```
But if you recover the previously computed empirical basis, by using an operator such as LIRE_RESU (in particular in MED format), this table is not available. The keyword TABL_COOR_REDUIT therefore makes it possible to give it to DEFI_BASE_REDUITE.

It is therefore necessary beforehand to have saved this table at the same time as the empirical basis (by an IMPR_TABLE), then to recover it (by a LIRE_TABLE) in order to give it to DEFI_BASE_REDUITE. A typical succession of commands is therefore the following:

1. Creation of a first reduced basis

  - non-linear analysis
  - creation of the basis with DEFI_BASE_REDUITE
  - recovery of the table of reduced coordinates with RECU_TABLE
  - saving of the empirical basis by IMPR_RESU
  - saving of the table of reduced coordinates by IMPR_TABLE
2. Enrichment of the reduced basis

  - non-linear analysis
  - reading of the previous empirical basis by LIRE_RESU
  - reading of the previous table of reduced coordinates by LIRE_TABLE
  - enrichment of the reduced basis by DEFI_BASE_REDUITE by giving the previous basis (keyword BASE) and the previous table of reduced coordinates (keyword TABL_COOR_REDUIT)

#### 2.3.4 Operand NOM_CHAM

One specifies the type of field of the reduced basis. The possible fields are:

- 'DEPL', 'SIEF_NOEU', 'SIEF_ELGA' or 'VARI_ELGA' if the data structure is of type evol_noli;
- 'TEMP' or 'FLUX_NOEU' if the data structure is of type evol_ther.

#### 2.3.5 Operands NOM_CMP and NOM_VARI

It is possible to select the name of the component on which the empirical modes will be built.

For the VARI_ELGA fields, it is strongly recommended to build one basis per component type. In this case, the use of NOM_VARI is possible and allows the user to give the name of the internal variable (e.g.: 'EPSEQ') rather than its order number (e.g.: 'V1'). In practice the modes will have the same number of components as the initial field but the components not selected by these keywords will have a zero value.

#### 2.3.6 Operand TYPE_BASE

One specifies the type of reduced basis.

The line-type case is specific to the numerical simulation of welding. This case requires specifying the welding axis and information concerning the section of the welded zone, perpendicular to the welding axis.

#### 2.3.7 Operands AXE and SECTION

Operands used in the line-type case (specific to the numerical simulation of welding).

AXE makes it possible to specify the welding axis.

SECTION makes it possible to specify the node group contained in the first section of the mesh of the welded zone.

**Note**

These operands make it possible to define a local numbering used for the analysis of the reduced modes.

#### 2.3.8 Operands NB_MODE / TOLE_SVD

TOLE_SVD denotes the tolerance retained for the SVD. The default value is 1.0E-6.

The selected modes are those whose singular value is greater than *tole x sing_maxi* where sing_maxi is the maximum singular value given by the SVD.

**Note**

The incremental POD (OPERATION='POD_INCR') also performs an SVD but not on the snapshot matrix. This parameter is therefore also useful in this case.

NB_MODE is the number of modes retained for the construction of the reduced basis.

The user must supply only one of the two operands in order to fix the number of modes retained for the construction of the reduced basis.

#### 2.3.9 Operand TOLE

This parameter makes it possible to adjust the accuracy of the incremental POD.

### 2.4 Operands for the GLOUTON strategies

The method OPERATION='GLOUTON' makes it possible to build an empirical basis on a parameterised problem. The basic principle is to build the linear system which solves the targeted problem and to give the list of the parameters which vary. The empirical basis is then built by a greedy-type algorithm (greedy algorithm) to which one must supply the variation of the parameters.

The linear system will thus be written:

$$
\sum_{i=1}^{{n}_{m}}{\alpha}_{i}\left({\gamma}_{j=1,{n}_{p}}\right){M}_{i}=\sum_{i=1}^{{n}_{v}}{\beta}_{i}\left({\gamma}_{j=1,{n}_{p}}\right){V}_{i}
$$

It contains ${n}_{m}$ assembled matrices ${M}_{i}$ (real or complex). These matrices can be built in the classical way in code_aster (CALC_MATR_ELEM and ASSE_MATRICE for example). In front of each matrix, there is a coefficient ${\alpha}_{i=1,{n}_{m}}$, which is either constant (real or complex), or a function or a formula (real or complex) which depends on at most ${\gamma}_{j=1,{n}_{p}}$ parameters.

Finally, the right-hand side $V$ is also a linear combination of ${n}_{v}$ vectors (real or complex) with a coefficient ${\beta}_{i=1,{n}_{v}}$, which is either constant (real or complex), or a function or a formula (real or complex) which depends on at most ${\gamma}_{j=1,{n}_{p}}$ parameters.

In order to build the empirical basis, one must traverse the space of the parameters, which the user defines by the parameter spaces.

#### 2.4.1 Operands MATR_ASSE and VECT_ASSE

These operands will build the linear system to be solved.

One gives the list of the assembled matrices ${M}_{i}$ by the factor keyword MATR_ASSE.

The name of the matrix (coming for example from the command ASSE_MATRICE) is given in MATRICE.

One then chooses the coefficient in front of each matrix. This coefficient is either constant (real by COEF_R or complex by COEF_C), or a function (real by FONC_R or complex by FONC_C). In the case of a function, it must depend on the parameters whose list (the variation) is given by the factor keyword VARI_PARA (see parameter space).

The keywords define the right-hand side $V$ by the keyword VECT_ASSE.

One then chooses the coefficient in front of each vector. This coefficient is either constant (real by COEF_R or complex by COEF_C), or a function (real by FONC_R or complex by FONC_C). In the case of a function, it must depend on the parameters whose list (the variation) is given by the factor keyword VARI_PARA (see parameter space).

#### 2.4.2 Operands VARI_PARA, NB_VARI_COEF and TYPE_VARI_COEF

These operands define the parametric space traversed in order to build the empirical basis.

NB_VARI_COEF gives the number of parameters when one traverses the parametric space. The keyword TYPE_VARI_COEF makes it possible to state that one is going to give *explicitly* the list of the values of the parameters (the only mode available for the moment).

The factor keyword VARI_PARA gives the list of the parameters ${\gamma}_{j=1,{n}_{p}}$ and their values.

For each occurrence, one gives the name of the parameter in NOM_PARA. This parameter is necessarily used in the coefficients ${\alpha}_{i=1,{n}_{m}}$ in front of the matrices. For each parameter, one gives the list of its values by VALE_PARA. The length of the vector VALE_PARA is necessarily equal to NB_VARI_COEF. One must also give an initial value VALE_INIT (which initialises the greedy algorithm).

#### 2.4.3 Operand SOLVEUR

This keyword gives the parameters of the solver used (see [U4.50.01](doc:u4.50.01)). Indeed the greedy algorithm will solve the defined linear system a large number of times.

#### 2.4.4 Operand ORTHO_BASE

This keyword makes it possible to carry out an orthonormalisation of the empirical basis when ORTHO_BASE='OUI'. This orthonormalisation is carried out with an iterative Gram-Schmidt type algorithm (IGS) following the Kahan-Parlett version.

#### 2.4.5 Operand TYPE_BASE

When TYPE_BASE='IFS_STAB', one creates an empirical basis which will be stable when it is used for fluid-structure interaction models (model $\lbrace u,p,\varphi \rbrace$ see [R4.02.02](doc:r4.02.02)) in transient dynamics.

The strategy consists in building an empirical basis by diagonalisation of three bases on each of the components (see [R5.01.50](doc:r5.01.50)). When one activates this keyword, a check of the components present is carried out on the components of the input result.

### 2.5 Other operations

#### 2.5.1 Truncation of a basis

The method OPERATION='TRONCATURE' makes it possible to truncate an empirical basis onto a model more restricted than the one which was used to build the basis. This operation is essential when one carries out model hyper-reduction (see keyword DOMAINE_REDUIT in STAT_NON_LINE and THER_NON_LINE).

The input keyword BASE gives the empirical basis to be truncated. The keyword MODELE_REDUIT gives the model onto which the basis will be truncated. It is indeed the model and not the mesh.

#### 2.5.2 Orthonormalisation of a basis

The method OPERATION='ORTHO' makes it possible to orthonormalise an empirical basis. A standard POD procedure makes it possible to obtain an orthonormal basis. On the other hand, it may happen in certain cases that a basis is not orthonormal:

- when one uses a greedy-type algorithm,
- when one uses an incremental POD type algorithm with certain parameter values that are too "relaxed",
- when the initial system to be solved is ill-conditioned.

The input keyword BASE gives the empirical basis to be orthonormalised.

This orthonormalisation is carried out with an iterative Gram-Schmidt type algorithm (IGS) following the Kahan-Parlett version. The parameter ALPHA makes it possible to adjust the algorithm. The larger it is, the less the algorithm will iterate but the more imperfect the orthonormalisation will be.

## 3 Examples of use

Example of use of the incremental mode by enrichment (OPERATION='POD_INCR'):

```python
mat1 = AFFE_MATERIAU(AFFE=_F(TOUT="OUI", MATER=acier1))

resu1 = STAT_NON_LINE(CHAM_MATER=mat1, ...)

mode1 = DEFI_BASE_REDUITE(RESULTAT=resu1, OPERATION="POD", NOM_CHAM="DEPL")

mat2 = AFFE_MATERIAU(AFFE=_F(TOUT="OUI", MATER=acier2))

resu2 = STAT_NON_LINE(CHAM_MATER=mat2, ...)

mode1 = DEFI_BASE_REDUITE(reuse=mode1, OPERATION="POD_INCR", RESULTAT=resu2, NOM_CHAM="DEPL")
```
The empirical basis mode1 has been built on two sets of material parameters.

- In the example above, the first DEFI_BASE_REDUITE could have been used in incremental mode (OPERATION='POD_INCR');
- With a very small tolerance (keyword TOLE), the incremental mode tends towards a classical SVD.

**Notes**
