# u4.65.02 Operator DEFI_MODELE_GENE

## 1 Purpose

Create the global structure from the substructures in dynamic substructuring (cf [R4.06.02](doc:r4.06.02)).

Within an analysis using the dynamic substructuring methods (modal or harmonic analysis), the operator DEFI_MODELE_GENE makes it possible to describe the global structure from the macro-elements coming from MACR_ELEM_DYNA [U4.65.01](doc:u4.65.01) and from the various connections which link the substructures to one another. A macro-element may serve for the definition of several substructures, whatever their orientation in the physical frame, if the coupling is carried out by static modes (option ‘CLASSIQUE’). This possibility makes it possible to take into account the repetition of a component in the global structure.

Produces a data structure of type modele_gene.

## 2 Syntax

```text
modele_gene = DEFI_MODELE_GENE(
    ◆ SOUS_STRUC = _F(
         ◆ NOM = text,
         ◆ MACR_ELEM_DYNA = macr_elem_dyna,
         ◆ ANGL_NAUT = float,
         ◆ TRANS = float,
      ),
    ◆ LIAISON = _F(
         ◆ SOUS_STRUC_1 = text,
         ◆ INTERFACE_1 = text,
         ◆ SOUS_STRUC_2 = text,
         ◆ INTERFACE_2 = text,
         ◇ / GROUP_MA_MAIT_1 = grma,
           / GROUP_MA_MAIT_2 = grma,
         ◇ OPTION = / "REDUIT",
                    / "CLASSIQUE" (par défaut),
      ),
    ◇ VERIF = _F(
         ◇ STOP_ERREUR = / "OUI" (par défaut),
                         / "NON",
         ◇ PRECISION = float (défaut: 0.001),
         ◇ CRITERE = / "RELATIF" (par défaut),
                     / "ABSOLU",
      ),
    ◇ INFO = / 1 (par défaut),
             / 2,
)

◆ : obligatoire
◇ : optionnel
⟐ : présent par défaut
& : ensemble
/ : un seul parmi
| : plusieurs choix possibles
```

## 3 Operands

### 3.1 Keyword SOUS_STRUC

```text
♦    SOUS_STRUC
```

Factor keyword making it possible to define all the substructures which make up the global structure. The definition of a substructure is made by giving its name, the macro-element associated with it, and its orientation in the physical frame.

#### 3.1.1 Operand NOM

```text
♦    NOM = ’nom_sstruc’
```

Name of 8 characters at most, which will subsequently make it possible to designate the substructure in:

- operator: DEFI_MODELE_GENE [U4.65.02](doc:u4.65.02), operands: LIAISON and SOUS_STRUC_1,
- operator: DEFI_SQUELETTE [U4.24.01](doc:u4.24.01), operand: SOUS_STRUC,
- operator: ASSE_VECT_GENE [U4.65.05](doc:u4.65.05), operand: SOUS_STRUC,
- operator: REST_SOUS_STRUC [U4.63.32](doc:u4.63.32), operand: SOUS_STRUC.

#### 3.1.2 Operand MACR_ELEM_DYNA

```text
♦     MACR_ELEM_DYNA = macro_dyna
```

Name of the macr_elem_dyna concept coming from the operator MACR_ELEM_DYNA [U4.65.01](doc:u4.65.01) which designates the condensed model of the substructure. One recalls that a macro-element may serve for the definition of several substructures.

#### 3.1.3 Operand ANGL_NAUT

```text
◊    ANGL_NAUT = angl_naut
```

List of the 3 nautical angles, in degrees, which make it possible to pass from the orientation of the model which gave rise to the macro-element to that of the substructure.

One should refer to the operator AFFE_CARA_ELEM [U4.42.01](doc:u4.42.01): Operand ORIENTATION for the definition and the use of the nautical angles.

#### 3.1.4 Operand TRANS

```text
◊    TRANS= trans
```

List of 3 translation components which make it possible to build a new substructure from the model which gave rise to the macro-element, by applying an overall translation.

### 3.2 Keyword LIAISON

```text
♦    LIAISON
```

Factor keyword making it possible to define all the connection interfaces between substructures. A connection is defined by the names of the two substructures facing each other and, for each of them, the name of the corresponding interface.

In the case of a mesh incompatibility between the two substructures facing each other, it is necessary to indicate which of the two will have its interface considered as master (keywords GROUP_MA_MAIT*). The slave nodes which are projected onto the master interface are defined beforehand by DEFI_INTERF_DYNA [U4.64.01](doc:u4.64.01). The "joining" of the 2 interfaces will be done by writing linear relations between the degrees of freedom of the 2 faces.

**Note:**

*It is recommended that, in the case of incompatible interfaces, the master interface be the interface whose discretisation is the coarsest. In the case of the use of classical static modes (as many as there are degrees of freedom), one should therefore use the interface with the smallest number of degrees of freedom as the master interface. In the case of the use of coupling modes, this choice may be more delicate. The choice of the master interface may appreciably affect the quality of the result if the two models have very different discretisations. See the discussion of this subject in section* 5.2 *.*

The displacements of the nodes of the slave face will be linked to the displacements of their projections onto the master face. For each node of the slave face, one will write 2 (in 2D) or 3 (in 3D) linear relations.

One application of this functionality is, for example, the joining of a mesh formed of linear elements (P1) onto another, quadratic, mesh (P2). In this case it is rather advisable to choose the quadratic face as the "slave" face.

It is possible to define a connection by reduced modes (or interface modes) by means of the keyword OPTION.

#### 3.2.1 Operand SOUS_STRUC_1

```text
♦    SOUS_STRUC_1 = ’nom_sstruc1’
```

Name of the first of the substructures involved on either side of the connection. It must have been defined beforehand by the keyword: SOUS_STRUC.

#### 3.2.2 Operand INTERFACE_1

```text
♦    INTERFACE_1 = ’nom_int1’
```

Name of the interface of the first substructure involved in the connection. It must have been defined beforehand by the operator DEFI_INTERF_DYNA [U4.64.01](doc:u4.64.01) for the macro-element supporting the substructure.

**Note:**

*In the case of the use of coupling modes (operator MODE_STATIQUE) with the keyword MODE_INTERF, it is indispensable that the dynamic interface be of type CRAIGB.*

#### 3.2.3 Operand GROUP_MA_MAIT_1

```text
◊    GROUP_MA_MAIT_1    = lgma1
```

This keyword makes it possible to designate the master substructure, independently of the mesh-cell group specified as input. The operator DEFI_MODELE_GENE takes charge of the search for the facing mesh cells in all cases, relying on the definition of the interfaces facing each other (operator DEFI_INTERF_DYNA – U4.64.01). If the interface is incompatible, and the keyword is not supplied, it is substructure 1 which is defined as the master.

#### 3.2.4 Operand SOUS_STRUC_2

```text
♦    SOUS_STRUC_2 = ’nom_sstruc2’
```

Name of the second of the substructures involved on either side of the connection. It must have been defined beforehand by the keyword SOUS_STRUC.

#### 3.2.5 Operand INTERFACE_2

```text
♦    INTERFACE_2 = ’nom_int2’
```

Name of the interface of the second substructure involved in the connection. It must have been defined beforehand by the operator DEFI_INTERF_DYNA [U4.64.01](doc:u4.64.01) for the macro-element supporting the substructure.

**Note:**

*In the case of the use of coupling modes (operator MODE_STATIQUE) with the keyword MODE_INTERF, it is indispensable that the dynamic interface be of type CRAIGB.*

#### 3.2.6 Operand GROUP_MA_MAIT_2

```text
◊    GROUP_MA_MAIT_2    =    lgma2
```

This keyword makes it possible to designate the master substructure, independently of the mesh-cell group specified as input. The operator DEFI_MODELE_GENE takes charge of the search for the facing mesh cells in all cases, relying on the definition of the interfaces facing each other (operator DEFI_INTERF_DYNA – U4.64.01). If the interface is incompatible, and the keyword is not supplied, it is substructure 1 which is defined as the master.

#### 3.2.7 Operand OPTION

```text
◊    OPTION    =    /'CLASSIQUE',
/'REDUIT',
```

Makes it possible to choose between a classical substructuring by static modes (Mac-Neal method, harmonic Craig-Bampton or not) or by interface modes.

### 3.3 Keyword VERIF

```text
◊    VERIF
```

Factor keyword making it possible to check the consistency of the generalised model: one checks that the connection is compatible with the orientations and the translations assigned to the substructures. The nodes of the two interfaces do not *a priori* have to be ordered so that they coincide in pairs. If the nodes of the interfaces are not facing each other in pairs, the code detects this state and reorders the nodes so as to put them back facing each other.

#### 3.3.1 Operand STOP_ERREUR

Makes it possible to carry out or not the consistency check of the generalised model.

#### 3.3.2 Operands PRECISION / CRITERE

Indicates the precision threshold beyond which the connections are incompatible. It is the distance (relative or absolute according to CRITERE) beyond which the connection nodes are considered too far apart to be effectively connected.

### 3.4 Keyword INFO

> Keyword making it possible to specify the printout level.

## 4 Execution phase

The operator carries out a certain number of checks on the consistency of the connections if the connection does not present a mesh incompatibility:

- identical number of nodes on either side of the connection,
- consistency, at each node, after orientation of the active degrees of freedom on either side of the connection.

### 5.2 In the case of the option 'REDUIT'

The operator computes the oriented connection matrices involved in the generalised model:

${{L}_{j}^{k}}_{\text{}\mathrm{orientee}}={B}_{j}^{k}{R}^{k}{\Phi}^{k}$

| where: |  | the exponent ![Figure](images/Object_15.svg) characterises the substructure, |
| --- | --- | --- |
|  |  | the index ![Figure](images/Object_18.svg) characterises the connection interface, |
|  | ${B}_{j}^{k}$ | is the matrix extracting the degrees of freedom of the connection ![Figure](images/Object_20.svg)<string>:146: (INFO/1) Unexpected possible title overline or transition. Treating it as ordinary text because it's so short., |
|  | ${R}^{k}$ | is the rotation matrix which makes it possible to pass from the orientation of the model which gave rise to the macro-element to that of the substructure, |
|  | ${\Phi}^{k}$ | is the column matrix of the eigenvectors of the substructure ![Figure](images/Object_25.svg)<string>:159: (INFO/1) Unexpected possible title overline or transition. Treating it as ordinary text because it's so short.. |

In the case of the option ‘REDUIT’, one joins the generalised motions of the two interfaces. One ensures:

${[{\Phi}_{\mathrm{esclave}}]}^{T}{{q}_{j}^{1}}_{\mathrm{orientee}}={[{\Phi}_{\mathrm{esclave}}]}^{T}{{q}_{j}^{2}}_{\mathrm{orientee}}$ , with ${{q}_{j}^{k}}_{\mathrm{orientee}}={{L}_{j}^{k}}_{\mathrm{orientee}}{\eta}^{k}$

Indeed, in the case of the option «CLASSIQUE», the choice of the master and slave degrees of freedom amounts to writing the connection equation in the form

![Figure](/figures/u4.65.02/Object_5.svg)

${y}_{\mathrm{esclave}}-C{y}_{\mathrm{maître}}=0$ ,

where $y$ corresponds to the degrees of freedom. Now, the use of a space of reduced dimension in order to write the relation amounts to imposing the following constraints:

![Figure](/figures/u4.65.02/Object_8.svg)

${\Phi}_{\mathrm{esclave}}{q}_{\mathrm{esclave}}-C{\Phi}_{\mathrm{maître}}{q}_{\mathrm{maître}}=0$ .

One therefore has more equations than unknowns, the number of generalised degrees of freedom ${q}_{\mathrm{esclave}}$ being distinctly smaller than the number of physical degrees of freedom of the interface ${y}_{\mathrm{esclave}}$. In order to ensure the proper conditioning of the joining conditions, one therefore projects this relation onto the restriction, to the interface, of the modes of the slave substructure, and the relation to be satisfied then becomes:

${\Phi}_{\mathrm{esclave}}^{T}{\Phi}_{\mathrm{esclave}}{q}_{\mathrm{esclave}}-{\Phi}_{\mathrm{esclave}}^{T}C{\Phi}_{\mathrm{maître}}{q}_{\mathrm{maître}}=0$

The choice of the master substructure therefore governs the quality of the joining in the case of strongly incompatible interfaces.

**Note:**

*When using the option, particular care must be taken over the choice of the master and slave interfaces, inasmuch as the kinematic relation between the interfaces is written on the physical degrees of freedom, but the relation is then projected onto the modes of the slave interface. If the two modellings are identical (3D–3D, or 2D-2D) and the discretisations are equivalent, then the master interface will be the interface presenting the largest number of modes. In the case of different modellings, one must make sure that one has an equivalent number of interface modes for each of the substructures, ideally slightly fewer for the slave substructure, and choose as the master interface the one presenting the coarsest discretisation. In all cases, pending the development of tools making it possible to assess the quality of the joining, one will have to carry out a visual check of the results.*
