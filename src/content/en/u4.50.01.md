# u4.50.01 Keyword SOLVEUR

## 1 Purpose

The factor keyword SOLVEUR is common to all the commands which solve **systems of linear equations** (STAT_NON_LINE, CALC_MODES, ...). To solve these systems of equations, particular algorithms called “linear solvers” are used. The keyword SOLVEUR makes it possible to choose the linear solver to be used from among two categories: the direct solvers and the iterative solvers.

Among the direct solvers, one has the classical “Gauss” algorithm (METHODE='LDLT'), a multifrontal factorisation ('MULT_FRONT') and the MUMPS library ('MUMPS').

For the iterative solvers, it is possible to call a conjugate gradient ('GCPC') or certain algorithms of the PETSc library ('PETSC').

Only MULT_FRONT, MUMPS and PETSC are **parallelised**. The first in shared memory (OpenMP), the other two mainly in distributed memory (MPI). Their parallel schemes can even be chained (PETSc + MUMPS as a preconditioner) or take advantage of a second level of parallelism (OpenMP in MUMPS and the BLAS library).

On the other hand, whatever their level of parallelism, all the solvers remain compatible with a parallel processing of the elementary analyses and of the assemblies.

Furthermore, only the three direct solvers are compatible with the modal analysis, the buckling studies and certain time-step refinement procedures in non-linear analysis.

**For further details and advice** on the use of the linear solvers one may consult the specific user's guides [U2.08.03](doc:u2.08.03)/[U2.08.06].

## 3 Operands

### 3.1 Operand METHODE

This keyword makes it possible to choose the method for solving the linear systems:

| **#Direct** **solvers** |  |
| --- | --- |
| /'MULT_FRONT' | **Direct solver of multifrontal type** (without pivoting during the factorisation). This method is parallelised in shared memory (OpenMP) and can be executed on several processors (*via* the Astk interface, menu Options / Launching options / ncpus). |
|  |  |
| /'LDLT' | **Direct solver with Crout factorisation** by blocks (without pivoting). This solver is paged, so it can run with little memory. |
|  |  |
| /'MUMPS' [ **DEFAUT** ] | **Direct solver of multifrontal type** with pivoting. This solver calls the MUMPS library developed by CERFACS/CNRS/ENS Lyon/INPT/INRIA/University of Bordeaux. It makes it possible to treat models leading to non-positive-definite matrices (apart from the boundary conditions). For example, the ‘mixed’ elements having degrees of freedom of ‘Lagrange’ type (incompressible elements, etc.). This method is parallelised mainly in distributed memory (MPI) but some of its steps can also benefit from shared-memory parallelism (OpenMP). It can be executed on several cores, themselves possibly distributed over several nodes. MUMPS is supplied with external 64-bit renumberers. This makes it possible to extend the scope of use of code_aster to very large finite-element models (> 107 degrees of freedom). Note, however, that solving the linear systems associated with these models requires large computing resources and the activation of the various levels of parallelism or even one of the acceleration options. |
| **#Iterative solvers** |  |
| /'GCPC' | **Iterative solver of conjugate-gradient type with preconditioning** by an incomplete factorisation to *k* levels or else a complete factorisation in single precision. |
|  |  |
| /'PETSC' | **Iterative solvers from the PETSc library** (*Argonne National Laboratory*) with various preconditioners. This method is parallelised in distributed memory (MPI) and can be executed on several processors. Warning: the solvers PETSC and MUMPS being incompatible in sequential mode, PETSC is not available in the sequential versions of code_aster. To use PETSC, one must therefore launch a parallel version of code_aster (even if only one processor is requested). |
|  |  |
|  |  |

**Advice:**

**The default method is** **MUMPS**. It makes it possible, at the same time, to take full advantage of the gains in time and memory provided by **parallelism**, and to solve **numerically difficult problems** (X-FEM, incompressibility, THM...).

To solve more efficiently a problem of **large size** (> 106 degrees of freedom), one may resort to the ‘low-rank’ compressions of MUMPS (cf. keywords ACCELERATION/LOW_RANK_SEUIL) or, if the functional scope allows it, to the iterative solvers PETSC or GCPC.

**For further details and advice** on the use of the linear solvers one may consult the specific user's guides [U2.08.03](doc:u2.08.03) and [U2.08.06](doc:u2.08.06).

### 3.2 Parameters common to several solvers

```text
◊    NPREC    =                /    nprec
/    8        [DEFAUT]

◊    STOP_SINGULIER    =    /    'OUI'    [DEFAUT]
/    'NON'
```

These two parameters are common to all the direct linear solvers (LDLT, MULT_FRONT, MUMPS).

They are used to control the course of the numerical factorisation and the quality of the solution of the linear system. The numerical factorisation of a matrix can fail in two situations: a problem in constructing the factorised matrix (a structurally or numerically singular matrix) and the numerical detection of a singularity (unstable solution of the linear system).

The keywords NPREC and STOP_SINGULIER make it possible to set the singularity-detection threshold and the behaviour to adopt in the event of failure during the factorisation.

nprec is used to calibrate the singularity-detection process for the matrix of the system to be solved. With LDLT and MULT_FRONT, the absolute value of nprec is taken; with MUMPS, nprec is taken because its sign matters: if $\text{nprec}<0$ , singularity detection is disabled, otherwise it is enabled.

In all cases, if the value nprec is left at zero it is initialised to the default value (8).

By initialising this parameter to a fairly low value (1 or 2) (respectively a high value, for example 20), singularity detection will be triggered very often (respectively rarely).

```text
Pour LDLT , MULT_FRONT:
```

When, at the end of the factorisation, a diagonal term $d'$ is found to have become very small (compared with what it was before the factorisation $d$ ), the matrix is (probably) almost singular. Let $n=\log∣\frac{d}{d'}∣$ ; this magnitude ratio indicates that on one equation (at least) $n$ significant digits have been lost.

If $n>\text{nprec}$ , the matrix is considered to be singular. If the user has indicated:

| STOP_SINGULIER='OUI' | The code then stops in error. |
| --- | --- |
| STOP_SINGULIER='NON' | Execution continues after an ALARME has been issued. The quality of the solution is then not guaranteed. This setting is not recommended. In non-linear analysis, it is not necessarily too detrimental to the quality of the results because they are “corrected” by the Newton process. |

```text
Pour MUMPS:
```

If, for at least one pivot, the infinity norm of the row (or of the column) is lower than the threshold ${10}^{-\text{nprec}}$ then the matrix is considered to be singular.

Some aspects of the two types of singularity-detection criterion are compared in the documentation [U2.08.03](doc:u2.08.03).

**Notes:**

- *Any significant loss of significant digits during a factorisation is an indicator of an ill-posed problem. Several causes are possible (non-exhaustive list): insufficient restraint boundary conditions on the structure, redundant linear relations, very heterogeneous numerical data (penalty terms that are too large)...*
- *For* LDLT *and* MULT_FRONT *, singularity detection is performed all the time because it is very inexpensive.*
- *As regards* MUMPS *, a mechanism makes it possible to check the quality of the solution by another means (* RESI_RELA *). The freedom to disable this criterion has therefore been left (by choosing a negative* nprec *).*
- *By default, with the direct solver* MUMPS *, there is therefore a double check on the quality of the solution: in linear analysis,* RESI_RELA *and* NPREC *; in non-linear analysis, the Newton criterion and* NPREC *. It is possible to switch them off, but this is not recommended without a valid reason.*

```text
◊    ELIM_LAGR    = 'NON'/'OUI'/'LAGR2'

Ce mot clé permet d'éliminer les équations de Lagrange correspondant aux conditions cinématiques dualisées.

Par défaut (sauf pour MUMPS), ces équations ne sont pas éliminées ('NON').

La technique d'élimination utilisée pour ELIM_LAGR='OUI' est décrite dans [:ref:`R3.03.05 <R3.03.05>`].

Pour utiliser ELIM_LAGR='OUI' sur plusieurs processeurs, il est impératif d'avoir au préalable choisi DISTRIBUTION='CENTRALISE'dans AFFE_MODELE.La phase d'élimination est alors répliquée sur tous les processeurs (sans entraîner de gain en temps). La résolution du système linéaire résultant s'effectue ensuite en parallèle sur tous les processeurs (cette fois avec un gain en temps, qui dépend du solveur linéaire choisi).

On ne peut pas utiliser ELIM_LAGR='OUI' avec le solveur linéaire direct 'MULT_FRONT'.

Dans le cas du solveur MUMPS, une troisième valeur est possible: 'LAGR2'. L'objectif est alors de supprimer la deuxième équation de Lagrange, mais de conserver la première.

La valeur 'LAGR2' est le défaut pour le solveur MUMPS.
```

This parameter may be temporarily disabled by the code so as not to distort the computation of the determinant of the matrix. This feature is mainly required by the operators CALC_MODES with OPTION among ['PROCHE','AJUSTE','SEPARE'] and INFO_MODE. The user is then warned of this automatic change of setting *via* a dedicated message (only with INFO=2).

### 3.3 METHODE='MULT_FRONT'

**Scope of use:**

> Robust solver, not recommended however for modellings requiring pivoting (mixed finite elements, incompressible…), for generalised matrices with links (operators ASSE_ELEM/MATR_SSD…) as well as on large finite-element models (> 106 degrees of freedom).

In these situations, rather use the MUMPS method (cf. §3.5) or, in non-linear analysis, PETSC + PRE_COND='LDLT_SP' (cf. § 3.7).

```text
◊    RENUM =
```

This argument makes it possible to number the nodes of the model in order to reduce the size of the factorised matrix (and therefore the CPU and memory consumption of the solution):

| /'METIS' [ **DEFAUT** ] | Numbering method based on a nested dissection. The external product of the same name is used; it is a worldwide standard in the field. It is, in general, the most efficient method (in CPU time and in memory). |
| --- | --- |
| /'MD' | (‘Minimum Degree’) this numbering of the nodes minimises the fill-in of the matrix during its factorisation. |
| /'MDA' | (‘Approximate Minimum Degree’) this numbering is in principle less optimal than 'MD' as regards fill-in but it is cheaper to compute. It is nevertheless preferable to 'MD' for large models ($\ge 50000$ degrees of freedom). |

**Note:**

- *In the case of generalised matrices*  1 *comprising link constraints,* *MULT_FRONT does not apply any renumbering. This strategy is not detrimental because these matrices are often nearly full and of small size. The choice of renumberer made by the user is therefore ignored. An information message reports this situation in the message file.*

### 3.4 METHODE='LDLT'

**Scope of use:**

> Universal solver but only on small finite-element models (< 105 degrees of freedom). Beyond that, the method is very slow.

Not recommended for modellings requiring pivoting (mixed finite elements, incompressible...).

**Note:**

- *The matrix is systematically renumbered using the Reverse-Cuthill-Mackee algorithm. The user cannot modify this choice.*

### 3.5 METHODE='MUMPS'

**Scope of use:**

> Universal solver, efficient and robust. To be used on all types of problem and in particular large finite-element models (>106 degrees of freedom), or even very large models (>107 degrees of freedom). Especially if they mix modellings, types of finite element, or if the associated linear systems require pivoting (mixed finite elements, incompressible, X-FEM modelling, dualised boundary condition, links between mesh-cell groups, etc.).

In non-linear analysis, it is often preferable to use MUMPS as a preconditioner, *via* the option PETSC + PRE_COND='LDLT_SP'/'LDLT_DP' (cf. §3.7).

The MUMPS solver, currently developed by CERFACS/CNRS/ENS Lyon/INPT/INRIA/University of Bordeaux, is a direct solver of parallelised multifrontal type (in MPI and in OpenMP). It is robust because it makes it possible to pivot the rows and columns of the matrix during the numerical factorisation.

Only the public version of MUMPS 5.5.1 is accepted in the coupling with *code_aster*.

Furthermore, their restricted-access versions MUMPS v5.5.5 consortium are also accepted but only for EDF use. They provide access, ahead of the public version, to exploratory features.

All are now compiled with external 64-bit renumberers ((PAR)METIS, (PT)SCOTCH and PORD), which allows MUMPS, by activating them (cf. keyword RENUM), to treat very large finite-element models (millions of mesh cells).

Note, however, that solving the linear systems associated with these models requires large computing resources and the activation of the various levels of parallelism or even one of the acceleration options (cf. keyword ACCELERATION).

For further information one may consult §4 of [U2.08.03](doc:u2.08.03) and [U2.08.06](doc:u2.08.06).

#### 3.5.1 Functional parameters

```text
◊    TYPE_RESOL =
```

This keyword makes it possible to choose the type of MUMPS solution:

| /'NONSYM' | Must be chosen for non-symmetric matrices. |
| --- | --- |
| /'SYMGEN' | Must be chosen for symmetric non-positive-definite matrices. This is the most general case in *code_aster* because of the dualisation of the boundary conditions by Lagrange multipliers. |
| /'SYMDEF' | May be chosen for symmetric positive-definite matrices. There is no pivoting. The algorithm is faster and less costly in memory. |
| /'AUTO' [ **DEFAUT** ] | The code will choose 'NONSYM' for non-symmetric matrices and 'SYMGEN' for symmetric matrices. |

It is not forbidden to choose 'NONSYM' for a symmetric matrix. This will probably double the computing cost but this option gives MUMPS more algorithmic possibilities (pivoting, *scaling*…). *Conversely*, it can be worthwhile, in non-linear analysis, to symmetrise one's non-symmetric problem (cf. [U4.51.03](doc:u4.51.03), keyword MATR_RIGI_SYME). It is the same kind of device as for the relaxation parameters FILTRAGE_MATRICE and MIXER_PRECISION.

```text
◊    RESI_RELA    =    /    resi
/    1.d-6    [DEFAUT] en linéaire
/    -1.d0    [DEFAUT] en non linéaire et en calcul modal.

Ce paramètre est désactivé par une valeur négative. Il est appelable dans les opérateurs qui peuvent avoir besoin de contrôler la qualité d'une résolution complète de système linéaire (donc pas les opérateurs éclatés effectuant juste des factorisations ; Par exemple FACTORISER et INFO_MODE).
```

By specifying a strictly positive value for this keyword (for example ${10}^{-6}$ ), the user indicates that he or she wishes to test the validity of the solution of each linear system solved by MUMPS (relative to the exact solution).

This cautious approach is recommended when the solution is not itself corrected by another algorithmic process (Newton algorithm, singularity detection…), in short in the linear operators THER_LINEAIRE and MECA_STATIQUE. In non-linear analysis or in modal analysis, the singularity-detection criterion and the correction of the enclosing algorithm (Newton or modal solver) are sufficient safeguards. One can therefore switch off this checking process (this is what is done by default *via* the value -1), all the more so as it has a non-negligible cost in time and as this cost is greater (in relative terms) in parallel and/or with memory management that offloads large objects to disk (cf. keyword GESTION_MEMOIRE). It is an additional feature that the other direct solvers of *code_aster* do not offer.

If the relative error (based on the condition numbers and the backward errors of the linear system treated) on the solution estimated by MUMPS is greater than resi, the code stops in ERREUR_FATALE, stating the nature of the problem and the values concerned.

Activating this keyword also initiates an iterative refinement process (unless POSTTRAITEMENTS='SANS') whose objective is to improve the solution obtained. This post-processing has a particular setting (keyword POSTTRAITEMENTS). It is the solution resulting from this iterative improvement process that is tested by RESI_RELA.

**Note:**

  - *In the particular case where* *POSTTRAITEMENTS='MINI'* *and* *RESI_RELA>0, the quality estimate made by MUMPS is only partial (based solely on the backward errors) and therefore code_aster does not stop the analysis if this value is greater than* *resi. This combination of keywords is of interest only with* *INFO=2 in order to assess the qualities of the solutions.*

#### 3.5.2 Relaxation parameters

```text
◊    FILTRAGE_MATRICE    =    /    filtma
/    -1.d0    [DEFAUT]

◊    MIXER_PRECISION    =    /    'OUI'
/    'NON'    [DEFAUT]
```

These parameters are reserved for quasi-static non-linear analysis. **A negative value of** filtma **disables the feature.**

These features make it possible to “relax” the solutions carried out with MUMPS in order to gain in performance. The idea is simple. In non-linear analysis, the computation of the tangent matrix may be affected by error. This will probably slow down the Newton process (in number of iterations), but if handling this approximate matrix is less costly, one can globally gain in time (fewer floating-point operations), in memory consumption (RAM or even disk if OOC is activated) and in bandwidth (cache effect, volume of I/O).

Thus, activating the feature FILTRAGE_MATRICE, with a value of filtma>0, leads *code_aster* to supply MUMPS only with the matrix terms satisfying

$∣{\mathrm{K}}_{ij}∣>\mathrm{filtma}\cdot \left(∣{\mathrm{K}}_{ii}∣+∣{\mathrm{K}}_{jj}∣\right)$

The filter is therefore based on a threshold relative to the absolute values of the corresponding diagonal terms.

By initialising MIXER_PRECISION to 'OUI', one uses the single-precision version of MUMPS while supplying it with a double-precision Aster matrix (possibly filtered via FILTRAGE_MATRICE). Hence potentially gains in memory (often 50%) and in time at the solution stage. However, this device is really worthwhile only if the tangent matrix is well conditioned ($\eta \left(\mathrm{K}\right)<{10}^{+6}$). Otherwise the solution of the linear system is too inaccurate and the non-linear algorithm may no longer converge.

**Notes:**

  - *These parameters for relaxing the solutions of linear systems via MUMPS are in line with those that already exist for the non-linear solvers (keywords* *NEWTON/REAC_ITER, MATRICE...). These families of parameters are clearly complementary and they can make it possible to gain tens of per cent in CPU and RAM consumption. Spending a little time calibrating them, on a first data set, can pay off when one subsequently has to carry out many similar analyses.*
- *This idea has been taken up with the preconditioner* *LDLT_SP of* *GCPC/PETSC.*
- But to gain memory space without risking a loss of accuracy of the analysis, one can also look at the following: parallel analysis [U2.08.03], parameters *GESTION_MEMOIRE,* *MATR_DISTRIBUEE* or even *RENUM.*

#### 3.5.3 Numerical parameters

```text
◊    PRETRAITEMENTS    =
```

This keyword makes it possible to control the type of pre-processing to be applied to the system in order to improve its solution (various strategies for equilibrating the terms of the matrix and for permuting its rows and its columns):

| /'SANS' | No pre-processing. |
| --- | --- |
| /'AUTO' [ **DEFAUT** ] | MUMPS chooses the best combination of parameters according to the situation. |

```text
◊    RENUM    =
```

This keyword makes it possible to control the renumbering and the elimination order. The various tools proposed are not necessarily all available. This depends on the installation of MUMPS/code_aster. These tools fall into two categories: the “basic” tools dedicated to one use and supplied with MUMPS ('AMD', 'AMF', 'QAMD', 'PORD'), and the richer and more “sophisticated” libraries which must be installed separately ('METIS/PARMETIS', 'SCOTCH/PTSCOTCH').

| /'AMD' | ‘Approximate Minimum Degree’ (approximate minimum degree) |
| --- | --- |
| /'AMF' | 'Approximate Minimum Fill' (approximate minimum fill) |
| /'QAMD' | Variant of 'AMD' (automatic detection of a nearly dense row) |
| /'PORD' | External renumbering tool distributed with MUMPS. |
| /'METIS' | External renumbering tool (also available with METHODE='MULT_FRONT'). It has been the reference renumberer since the end of the 1990s. It is recognised and used worldwide. |
| /'PARMETIS' | MPI parallel version of the previous tool. Available only with the MPI version of code_aster. Cf. [U2.08.03](doc:u2.08.03). To be preferred on very large finite-element models (millions of mesh cells). |
| /'SCOTCH' | External renumbering tool which tends to supersede the reference tool in the field (METIS). |
| /'PTSCOTCH' | MPI parallel version of the previous tool. Available only with the MPI version of code_aster. Cf. [U2.08.03](doc:u2.08.03). To be preferred on very large finite-element models (millions of mesh cells). |
| /'AUTO' [ **DEFAUT** ] | MUMPS chooses the best combination of parameters according to the problem and the packages available. If the user specifies a particular renumberer and the latter is not available, the solver chooses the most suitable one from the list of those available and an ALARME is issued. |

**Note:**

- *The choice of renumberer is of great importance for the memory and time consumption of the linear solver. If one seeks to optimise/tune the numerical parameters linked to the linear solver, this parameter must be one of the first to try.* This step is also accelerated by the “analysis by blocks” option activated with the values ‘FR+’, ‘FR++’, ‘LR+’ and ‘LR++’ of the keyword ACCELERATION.
- *The renumberers* (PAR)METIS *,* (PT)SCOTCH *and* PORD *are compiled in 64 bits in order to allow MUMPS to solve linear systems of several tens of millions of unknowns.*

#### 3.5.4 Parameters for memory management

To gain RAM without changing linear solver (and modelling or computer platform), several strategies are available (and often combinable). They are listed here in order of importance.

- **At constant numerical accuracy and with gains in computing time:**

Parallelism (Options/mpi_** menu of Astk) coupled, or not, with the activation of the keyword MATR_DISTRIBUEE in distributed parallelism mode (default mode);

Activation of the pre-processings (done by default, cf. PRETRAITEMENTS);

Redistribution of the parallelism between the MPI level and the OpenMP level (cf. REDUCTION_MPI).

- **At constant numerical accuracy but with, potentially, losses in computing time:**

Explicit activation of the disk-offloading capabilities of MUMPS (cf. GESTION_MEMOIRE),

Change of renumberer (cf. keyword RENUM seen previously).

One must also take care to provide an additional space reserved for pivoting of reasonable size: keyword PCENT_PIVOT. **Often the default values of these parameters (GESTION_MEMOIRE='AUTO',** **RENUM='AUTO'** **and** **PCENT_PIVOT=20) provide the best compromises** for adapting this part of the setting to the situation.

- **By accepting a loss of accuracy** within a non-linear process (e.g. STAT or DYNA_NON_LINE, CALC_MODES, ...): all the relaxation parameters linked to the solver (FILTRAGE_MATRICE, MIXER_PRECISION seen previously) or even those linked to the non-linear process proper (elastic tangent matrix, projection space in modal analysis...).
- By no longer using MUMPS as a direct solver but as a preconditioner (cf. GCPC or PETSC with REAC_PRECOND='LDLT_SP/DP' cf. §3.6/3.7).

For further information one may consult the documents [U2.08.03](doc:u2.08.03) (User's guide of the linear solvers) and [U2.08.06](doc:u2.08.06) (User's guide of parallelism).

```text
◊    PCENT_PIVOT    =    /    pcent    [I]
/    20%        [DEFAUT]
```

This keyword makes it possible to choose a percentage of memory that MUMPS will reserve at the start of the analysis for pivoting. Indeed, in order to factorise an *Aster* matrix, it is often preferable to permute two of its rows and/or of its columns (cf. [R6.02.03](doc:r6.02.03) §2.3.1). Now the data objects managing this pivoting are difficult to size *a priori*. This is why the tool asks the user for a prior and arbitrary estimate of this additional space.

The default value is 20%. It corresponds to a reasonable number of pivotings which is sufficient for most *Aster* analyses. If for example MUMPS estimates at 100 the space necessary for a factorisation without pivoting, it will ultimately allocate 120 to manage the analysis with pivoting. A value exceeding 50% must remain exceptional.

Subsequently, if the memory space required by the pivotings proves larger, the space allocated will be insufficient and the code will ask for this criterion to be increased. Two situations will then arise according to the type of memory management chosen (*via* the keyword GESTION_MEMOIRE):

- If it is a precise mode, 'IN-CORE' or 'OUT_OF_CORE', the analysis stops in ERREUR_FATALE and proposes various remedial solutions.
- If it is the automatic mode, 'AUTO', the analysis will continue and try again to factorise with a doubled value of PCENT_PIVOT. Up to three attempts of this type will be made before, in the event of repeated failures, a stop in ERREUR_FATALE + proposal of various remedial solutions.

**Notes:**

- *For small problems (<1000 degrees of freedom), MUMPS may underestimate its needs for memory pre-allocations. A large value of* *PCENT_PIVOT (>100) is then not surprising.*
- *Self-learning process: if, in the process described previously, one is led to modify automatically the value of* *PCENT_PIVOT, it is this new value which is used until the end of the operator. It is assumed that the numerical difficulty will not* *decrease and this pivoting value is therefore kept so as not to waste any more time on aborted factorisation attempts.*
- *In 'AUTO' mode, together with the doubling of the additional pivoting space, one may also be led to switch automatically to MUMPS Out-Of-Core memory management (as if one had explicitly set* *GESTION_MEMOIRE='OUT_OF_CORE'). This occurs according to certain MUMPS return codes or at the third (and last) attempt.*

```text
◊    GESTION_MEMOIRE=
```

This keyword makes it possible to choose the memory-management mode of the external product MUMPS, or even, as a last resort, of certain objects managed directly by *code_aster*.

The first two modes are “without a safety net”: no correction of the setting will be made “on the fly” in the event of a problem. Unlike the 3rd mode, the automatic mode, which will do everything (within certain limits!) so that the analysis does not fail for reasons of memory space. In particular, according to the memory that it manages to free elsewhere, it will play on the In-Core and Out-Of-Core modes of MUMPS or even on the space required for its pivoting (cf. keyword PCENT_PIVOT).

Activating Out-Of-Core helps to reduce the RAM required per processor, but it can slow down the analysis (cost of the RAM/disk I/O). This extra cost can be significant when many forward and backward substitutions are performed (e.g. non-linear analysis with many time steps or Newton iterations, search for many eigenmodes in a modal analysis...). Because in these algorithmic steps, as much time is spent handling the data (in RAM) as fetching them (from disk). This is all the more true when the disk is shared by several computing cores. For this reason, the In-Core mode is favoured as much as possible (especially in parallel).

In 'EVAL' mode, the pre-estimates of the memory consumptions are much faster and less costly in memory than the complete analysis. They can make it possible to calibrate one's study on a local machine or on an interactive node of a centralised machine before launching the study proper in batch mode.

Anecdotally, this mode can also be used to test roughly the data setup and/or the executable used. If everything works up to this evaluation, that is rather a good sign for the subsequent analysis!

In 'AUTO' mode, MUMPS is allowed to “spread out in RAM” in order to gain time and to limit the late memory needs linked to pivoting. MUMPS will thus be able to take all the memory it deems necessary, even possibly beyond its initial estimates. This allows it to cope with possible future needs. To this end, *code_aster* supplies it with an estimate of the available RAM.

These pre-allocations often make it possible to no longer have to adjust, often “by rule of thumb”, the parameter 'PCENT_PIVOT'. Hence a definite saving of time in setting up the studies.

Furthermore, in 'AUTO' mode, a *code_aster* + MUMPS analysis thus really takes advantage of all the available memory: the Vmpeak is close to the figure set in Astk.

On the other hand, in the other two modes ('IN_CORE' and 'OUT_OF_CORE'), MUMPS is not allowed to “spread out” in RAM. It pre-allocates no additional space beyond its initial memory estimates. This makes it possible to keep a safe mode of operation in the event of a poor evaluation of the available memory 4
.

Another mechanism also makes it possible to remedy this kind of inconvenience: if MUMPS tries to allocate an object of size greater than the memory space actually available, a new factorisation is attempted, no longer allowing it to pre-allocate additional space. This corrective strategy, similar to that used for the parameter PCENT_PIVOT, is activated only with the 'AUTO' mode.

**Notes:**

- *In the standard modes ('IN_CORE' and 'OUT_OF_CORE')* *code_aster offloads to disk the largest objects*  5 *linked to the linear system. This is in order to leave MUMPS a maximum of room in RAM. If subsequently MUMPS does not have enough room to allocate its data, an alarm is issued and the analysis continues. Depending on the cases, the analysis may finish without mishap but at the price of a large extra cost in time (system swap) or stop in* *ERREUR_FATALE. The user is then offered various alternatives, including the setting in 'AUTO' mode.*
- *In 'AUTO' mode, if this freed space is insufficient to allow MUMPS to operate fully in In-Core, the whole remainder of unloadable* *JEVEUX objects is offloaded to disk. Then, according to the memory space thus freed, the In-Core or Out-Of-Core mode of MUMPS is activated or one stops in* *ERREUR_FATALE (+ advice).*
- *The massive offloading of* *JEVEUX* *objects mentioned previously can, in exceptional cases, greatly slow down the execution. This can happen for example in the event of congestion of the disk accesses in parallel mode or when a great deal of data is offloaded (fields at the various time steps, projected fields...). The solution may then be to occupy fewer processors per node, to consume less memory (increase the number of processors, Out-Of-Core mode..) or to split one's analysis into several steps.*
- *In 'EVAL' mode, the evaluation and then the stop are carried out at the first matrix factorisation via MUMPS. That is, for example, in the prediction phase for* *STAT_NON_LINE, or in the Sturm test for* *CALC_MODES. This is often sufficient to have a good order of magnitude of the memory requirements. To possibly postpone this evaluation, one must split one's analysis and use another linear solver (for example 'MULT_FRONT') for the operators that one wishes to preserve.*

```text
◊    MATR_DISTRIBUEE    =    /    'OUI'
/    'NON' [DEFAUT]
```

**This parameter is for the moment limited to the operators** MECA_STATIQUE, STAT_NON_LINE and DYNA_NON_LINE and it is active only in distributed parallel mode (AFFE_MODELE/PARTITION/PARALLELISME!='CENTRALISE').

By activating this keyword, the storage of the assembled matrix is done in a distributed manner on all the processors (values belonging to the other processors, which are useless, are no longer stored). This makes it possible to save memory in parallel with no extra cost in time, and no loss of accuracy (this keyword has no influence in sequential mode or in centralised parallel mode).

#### 3.5.5 Parameters for reducing the computing time

To reduce the computing time without changing linear solver (and modelling or computer platform), several strategies are available (and combinable). They are listed here in order of importance.

- **At constant numerical accuracy:**
- MPI and/or OpenMP parallelism or, possibly, an optimised combination of the two (cf. keyword REDUCTION_MPI);
- activation of various accelerations and/or compressions (cf. keyword ACCELERATION);
- change of renumberer (keyword RENUM seen previously; often the choice made by default is optimal);
- activation of the pre-processings (done by default, keyword PRETRAITEMENTS);
- the use of MUMPS, not as a direct solver but as a preconditioner. Can be very efficient, especially in non-linear analysis, with the reuse over several Newton steps of the same preconditioner (cf. PETSC or GCPC with PRE_COND='LDLT_SP/DP' §3.6/3.7)
- **By accepting a loss of accuracy,** which is often not detrimental (the accuracy is sufficient) or is compensated by an enclosing non-linear process (e.g. STAT or DYNA_NON_LINE, CALC_MODES...):
- for large-size problems (*N* at least > 2.106 degrees of freedom), activation of the low-rank compressions (cf. keywords ACCELERATION/LOW_RANK_SEUIL below);
- the relaxation parameters linked to the solver (FILTRAGE_MATRICE, MIXER_PRECISION seen previously) or even those linked to the non-linear process proper (elastic tangent matrix, projection space in modal analysis...);
- the reduction of the post-processings (keyword POSTTRAITEMENTS).

For further information one may consult the documents [U2.08.03](doc:u2.08.03) (User's guide of the linear solvers) and [U2.08.06](doc:u2.08.06) (User's guide of parallelism).

These keywords define the type of acceleration implemented in order to reduce the computing time. These accelerations can significantly reduce the computing time of large studies, and this without restriction of the scope of use and with little or no impact on the accuracy, the robustness and the overall behaviour of the simulation. Their availability depends on the versions of MUMPS coupled with code_aster.

They are especially worthwhile on large-size problems (N at least > 2.10 6 degrees of freedom). The gains observed on a few code_aster studies vary from 20% to 80%. They increase with the size of the problem and with its massive character, and they are complementary to those provided by parallelism and by the renumberer.

The various values of the parameter ACCELERATION are:

- *The value 'AUTO'* (taken by default) chooses the best setting according to the version of MUMPS available, the case treated and the computing configuration. For the public version ‘AUTO’=’FR’ and, for the consortium version, ‘AUTO’=’FR+’ (except in modal analysis where AUTO=’FR’).
- *The value 'FR'* allows a standard MUMPS solution (known as 'Full-Rank') to be implemented, that is to say without 'low-rank' compression and without “aggressive optimisations” of the options internal to MUMPS.
- *The value 'FR+'* allows a solution without 'low-rank' compression to be implemented but activating “aggressive optimisations” of options internal to MUMPS. In particular one activates the analysis by blocks, which appreciably accelerates this first, often costly, step of MUMPS.
- *The value 'FR++*  ' adds to ‘ *FR+*  ' particular options of MUMPS which accelerate the 2nd and 3rd steps of MUMPS (numerical factorisation and forward and backward substitutions): extended OpenMP scope, relaxed pivoting, accelerated symbolic factorisation… However, in particular cases, these aggressive options can disturb singularity detection (increase the value of NPREC) or the memory estimates (set GESTION_MEMOIRE='IN_CORE'/'OUT_OF_CORE').
- *The value 'LR'* activates a MUMPS solution with 'Low-Rank' compression. The compression rate is fixed by the parameter supplied by the keyword LOW_RANK_SEUIL. *Roughly speaking*, the larger this figure is (relative to the default precision, 10-15), for example 10-12 or 10-9, the greater the compression will be and therefore the more interesting the gains in performance can be. From a certain compression threshold (therefore “of approximation”), it is advisable to activate, in addition, the iterative refinement procedure (for example *via* POSTTRAITEMENTS='MINI'). This makes it possible to recover, often at a low extra cost, an error on the solution close to that which would have been obtained with the standard analysis, 'FR'.
- *The values 'LR+'/* *'LR++'* activate the same option as previously ('LR') but adding the “aggressive optimisations” of 'FR++'. If the compression rate is positive (LOW_RANK_SEUIL >0), the standard BLR compression algorithm of MUMPS is used (known as ‘UFSC’); otherwise, it is its exploratory version (known as ‘UCFS’), potentially faster, because the compression is done earlier in the algorithmic process of MUMPS, but therefore less numerically stable. Depending on the options, one then rather targets the computing-time criterion or the memory consumption.
- *The value '* L *R+'* favours the gain in time.
- *The value '* L *R+* + *'* favours the gain in memory (additional compressions and use of mixed precisions).

For further details on these two keywords one may consult [U2.08.03](doc:u2.08.03) §7.2.7.

**Scope of use:**

This keyword makes it possible to choose the preconditioning method:

| /'LDLT_INC' [ **DEFAUT** ] | Incomplete **LDL**T decomposition (by level) of the assembled matrix |
| --- | --- |
| /'LDLT_SP' | Single-precision factorisation computed by MUMPS |
| /'LDLT_DP' | Double-precision factorisation computed by MUMPS |

The use of 'LDLT_SP' or 'LDLT_DP' is more costly in CPU/RAM but more robust. These preconditioners are obtained by computing with the MUMPS library an approximate factorisation of the matrix of the linear system. This factorisation can be computed in single (LDLT_SP) or in double (LDLT_DP) precision. Its interest lies above all in its reuse (cf. keyword REAC_PRECOND) during several solutions if one seeks to solve problems of multiple right-hand side type (e.g. STAT_NON_LINE or thermo-mechanical chaining with MECA_STATIQUE).

```text
◊    NIVE_REMPLISSAGE    =    /    niv
/    0    [DEFAUT]
```

This parameter concerns only the preconditioner LDLT_INC. The preconditioning matrix ($\text{P}$ ) used to accelerate the convergence of the conjugate gradient is obtained by factorising more or less completely the initial matrix ($\text{K}$ ).

The larger niv is, the closer the matrix $\text{P}$ is to ${\text{K}}^{-1}$ and therefore the faster the conjugate gradient converges (in number of iterations). On the other hand, the larger niv is, the more bulky the storage of $\text{P}$ becomes (in memory and on disk) and the more costly the iterations are in CPU.

It is advisable to use the default value ($\mathit{niv}=0$ ). If $\mathit{niv}=0$ does not allow the conjugate gradient to converge, one will try successively the values $\mathit{niv}=1,2,3\dots$ .

Likewise, if the number of iterations of the conjugate gradient is judged too large, it is often beneficial to increase the fill-in level.

```text
◊    REAC_PRECOND    =    /    reac
/    30    [DEFAUT]

Ce paramètre ne concerne que les préconditionneurs LDLT_SPet LDLT_DP
```

These preconditioners are much more costly to build than the incomplete preconditioner but they are more robust. To make it really competitive with respect to the classical direct solvers (MULT_FRONT or double-precision MUMPS), it must be kept during several successive solutions. One thus takes advantage of the “relative proximity” of these successive iterates. To this end, the parameter REAC_PRECOND conditions the number of times the same preconditioner is kept while the matrix of the problem has changed. As long as the iterative method GCPC takes fewer than reac iterations to converge, the preconditioner is kept unchanged; if it exceeds this number, the preconditioner is updated by recomputing a factorisation.

### 3.7 METHODE='PETSC'

**Scope of use:**

> All types of real problem except those requiring mandatory singularity detection (modal analysis). To be used in priority on non-linear problems (with PRE_COND='LDLT_SP') or on “frontier” problems (> 5.107 degrees of freedom).

**Warning:** the solvers PETSC and MUMPS being incompatible in sequential mode, only MUMPS is available in the sequential versions of code_aster. To use PETSC, one must therefore always launch a parallel version of code_aster (even if only one processor is requested).

```text
◊    ALGORITHME    =
```

| --- | --- |
| /'GMRES' | 'Generalised Minimal RESidual' |

| /'CR' | Conjugate residual |
| /'GCR' | 'Generalised Conjugate Residual' |

The default method ensures the best ratio between robustness and cost of the analysis.

The methods 'CG' and 'CR' are to be reserved for modellings leading to symmetric matrices. In the non-symmetric case, besides 'GMRES', one can call 'GCR', which treats arbitrary matrices.

The algorithm ' GMRES_LMP' relies on the iterative solver 'GMRES'. It must necessarily be used with the first-level preconditioner 'LDLT_SP'. Its use is worthwhile in a non-linear analysis: indeed, the second-level preconditioner improves the preconditioning of a system from spectral information coming from the previous linear solutions (see [R6.01.02](doc:r6.01.02) )

| /'LDLT_INC' | Incomplete factorisation by level |
| --- | --- |
| /'LDLT_SP' [ **DEFAUT** ] | Single-precision factorisation computed with MUMPS |
| /'LDLT_DP' | Double-precision factorisation computed with MUMPS |
| /'ML' | Algebraic multigrid “*multilevel*” (ML library) |
| /'BOOMER' | Algebraic multigrid “BoomerAMG” (HYPRE library) |

| /'HPDDM' | Domain decomposition (HPDDM library) |
| /'BLOC_LAGR' | Block preconditioner of Augmented Lagrangian type |
| /'JACOBI' | Standard diagonal preconditioner |
| /'SOR' | 'Successive Over Relaxation' |
| /'FIELDSPLIT' | Block preconditioner (advanced feature) |
| /'UTILISATEUR' | Preconditioner in Python (advanced feature) |
| /'SANS' | No preconditioner |

Only *LDLT_SP,* *LDLT_DP,* *ML,* *BOOMER and* *JACOBI* have exactly the same operation in sequential and in parallel mode. The other two, *'LDLT_INC' and* *'SOR'*, modify the analysis slightly by using diagonal blocks local to the processors. They are simpler to implement but less efficient. 'SANS' makes it possible not to apply a preconditioner, which is of interest only when setting up an analysis.

The algebraic multigrid preconditioners *ML, BOOMER and* *GAMG* as well as the domain-decomposition preconditioner *HPDDM* have a very restricted scope of application:

- analysis without Lagrange multipliers (use AFFE_CHAR_CINE to impose the loadings),
- with a number of degrees of freedom constant per node.

They are nevertheless very efficient in parallel. It will be noted that the preconditioner ML relies, in the course of its algorithm, on a random draw, which can lead to a slightly different convergence between two identical solutions. These multigrid preconditioners are to be used with the solvers CG or GCR (which can work when CG fails).

It should be noted that the domain-decomposition preconditioner *HPDDM* can be used only in the context of massive parallelism (by using the keyword PARTITIONNEUR of the command LIRE_MAILLAGE).

The preconditioner 'BLOC_LAGR' is a block preconditioner designed for analyses with Lagrange multipliers. It must be used with METHODE='PETSC'.

The preconditioners 'LDLT_SP' and 'LDLT_DP' are *a priori* the most robust, but also the most costly to build. However, and unlike the other preconditioners, they are not rebuilt at each linear solution, which finally makes them competitive (*cf.* keyword REAC_PRECOND). These preconditioners are to be used with the default solver FGMRES (or else CG or GCR if the matrix is symmetric). It is preferable to avoid GMRES (or else its symmetric equivalent CR) combined with a single-precision preconditioner (risk of obtaining an inaccurate solution, because the stopping criterion of the solver is disturbed by the mixture of arithmetics).

In a non-linear analysis, one can finally use 'LDLT_SP' with the algorithm 'GMRES_LMP': a second-level preconditioner (LMP) then improves the preconditioning of a linear solution from spectral information coming from the previous linear solutions (see [R6.01.02](doc:r6.01.02) ).

The preconditioner 'FIELDSPLIT' offers a very general framework for defining block preconditioners. It is a very powerful feature which requires a very good knowledge of iterative methods and of the PETSc library. It is used essentially in research work.

The preconditioner 'UTILISATEUR' allows the use of a preconditioner defined by the user in a function, relying on the Python interface of PETSc. It is an advanced feature which requires a very good knowledge of iterative methods and of the PETSc library. It is used essentially in research work.

These preconditioners are much more costly than the incomplete preconditioner but they are more robust. To make them really competitive with respect to the classical direct solvers (MULT_FRONT or double-precision MUMPS), they must be kept during several successive solutions.

The parameter REAC_PRECOND conditions the number of times the same preconditioner is kept while the matrix of the problem has changed. As long as the iterative solver (ALGORITHME) called by PETSC takes fewer than reac iterations to converge, the preconditioner is kept unchanged; if it exceeds this number, the preconditioner is updated by performing a single-precision factorisation again.

Convergence criterion of the algorithm. It is a relative criterion on the preconditioned residual:

$\frac{\parallel {M}^{-1}.{\text{r}}_{m}\parallel }{\parallel {M}^{-1}.\text{f}\parallel }\le \mathit{resi}$

${\text{r}}_{m}$ is the residual at iteration $m$

**Notes:**

1. *The convergence criterion for* *PETSC is evaluated differently from* *GCPC;*
2. *When the preconditioner is of poor quality (for example because of a poor conditioning of the problem), the convergence criterion used by* *PETSC can give rise to poor solutions; this is why, in the linear analysis operators, an additional check on the non-preconditioned residual is carried out. The tolerance chosen for this additional criterion is* $\sqrt{\mathit{resi}}$ *;*
3. *The algorithm* *'GCR' relies on right preconditioning and therefore checks the convergence criterion in the non-preconditioned norm.*
4. *When the preconditioner* *LDLT_INC is used, the matrix is systematically renumbered using the Reverse-Cuthill-Mackee algorithm. The user cannot modify this choice.*
5. The preconditioner *LDLT_INC is incompatible with* *MATR_DISTRIBUEE='OUI'.*
