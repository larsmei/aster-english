## 1 General points

The static substructuring implemented in *Aster* can be used in **linear mechanics** and **in non-linear mechanics on linear parts of a model**. It can be carried out a priori at **several levels**: a substructure can contain other substructures of lower level. All the types of elements of the phenomenon "MECANIQUE" are accepted, as are all the loadings supported by these elements.

Substructuring is currently implemented within the framework of the ordinary commands [U4.4‑] and [U4.5-]. It is not, however, implemented within the framework of the global commands: MECA_STATIQUE, CALC_CHAMP, POST_ELEM, ...

An exception exists: the commands STAT_NON_LINE and DYNA_NON_LINE accept static macro-elements (see u2.07.02-utilisation-macro-elements).

Static substructuring consists in "condensing" statically the problem to be treated: one eliminates a certain number of unknowns (internal ones). There then remain the so-called "external" unknowns, fewer in number.

It is a method which reduces the size of the problem. One may therefore expect gains in CPU time and in disk occupancy. This static condensation applies naturally to the stiffness and mass matrices and to the right-hand sides representing the various loadings. In this case, the condensation method can be interpreted algebraically as a solution of the linear system by the "elimination" method. The solution of a linear statics problem is therefore not modified by the substructuring. On the other hand, it is possible to condense the mass matrix statically (Guyan condensation), but in that case the search for the eigenmodes of the condensed structure **is altered** by the substructuring method (see for example IMBERT [bib1]_). Other substructuring methods exist for dynamics problems in *Aster* [U4.55].

The theoretical principles of static substructuring are well explained in the book by IMBERT [bib1]_ and the PERMAS manuals [bib2]_.

The use of static substructuring in the non-linear regime is dealt with in a first, separate chapter.

In the remainder of this document, these theoretical principles will be assumed known and one will be concerned only with the "user" aspects. For this purpose, one will make much use of an example: the test case SSLP100 of the *Aster* validation manual. Through this test case, we have tried to illustrate a large number of capabilities of the software, by deliberately complicating the test:

- substructuring at several levels (2),
- use of one macro-element to generate several substructures by successive rotations,
- boundary conditions and loadings at several levels,
- mixture of substructures and ordinary finite elements,
- "follower" loading or not.

The command file of this test case, whose lines have been numbered, is given in the appendix to this document. When one wishes to refer to line n of this file, one will write {line n}.

## 2 Use of macro-elements in STAT_NON_LINE (or DYNA_NON_LINE)

One can carry out a non-linear analysis with STAT_NON_LINE [u4.51.03](doc:u4.51.03) on a model containing macro-elements. The interest of this type of analysis is a possible gain in performance (memory and/or CPU).

For the analysis with macro-elements to be more economical, the model must possess large linear elastic zones (possibly repetitive). These elastic zones (which one will condense into macro-elements) must also have a boundary as small as possible. A favourable situation will be, for example, the case of a fully elastic structure with a small zone of confined plasticity (cf. u2.07.02-fig-structure-elastique).

![Figure](/figures/u2.07.02/10000000000003420000018C9CC5433B9E5F115F.png)

*Fully elastic structure with a small zone of confined plasticity*

One will then condense the whole of the elastic part onto the interface nodes alone, with the zone of potential plasticity.

The use of macro-elements in STAT_NON_LINE (see test cases SSLP100C and D) is subject to the following requirements:

1. each macro-element must be linear elastic; its temperature must not vary with time,
2. there can be no contact with macro-elements,
3. the loadings assigned to the macro-elements are "constant" (not multiplied by "FONC_MULT"),
4. the macro-elements must not undergo large rotations,
5. the "line search" is not possible.

Once the analysis has been carried out with STAT_NON_LINE, the usual post-processing (CALC_CHAMP, POST_ELEM) will have an effect only on the ordinary finite elements of the model (the macro-elements are ignored). If one wishes to examine, for example, the state of stress inside a macro-element, one must use the basic commands: CREA_CHAMP/EXTR, DEPL_INTERNE, … (see §4.3 and §4.4).

## 5 General organisation of the analyses and definitions

### 5.1 Construction of the global model

The principle of the implementation of static substructuring in *Code_Aster* is that of an ascending approach:

a **model** having been defined, one condenses it (operator MACR_ELEM_STAT) onto some of its nodes. One then obtains a **macro-element** which, functionally, closely resembles a new, "larger" finite element. This macro-element can then be integrated into a **model** of higher level (operators DEFI_MAILLAGE and AFFE_MODELE). This new model can then be condensed in its turn, and so on, with no a priori limitation on the number of levels.

**Definition**:

- the nodes onto which a macro-element is condensed are said to be "**external**" (the others are "**internal**"),
- **level**: this is a notion useful for understanding the command text; every level describes the structuring relations between the different models and the different macro-elements. For us, it is an integer. The condensation operation increases the level by $+1$ : a model of level $n$ gives, by condensation, a macro-element of level $n+1$ which will be integrated into a model of level $n+1$ ,
- the operator MACR_ELEM_STAT is the only operator making it possible to create a macro-element in static substructuring,
- the operator DEFI_MAILLAGE is the only operator using the macro-elements in static substructuring.

**For our example:**

- MO_1 {line 22} is the model of lowest level (-2),
- S_1 {lines 45, 59} is the macro-element of intermediate level (-1),
- MA_123 and MO_123 {lines 68, 87} represent the mesh and the model of intermediate level (-1),
- S_123 {line 104} is the macro-element of highest level (0),
- MAG0, MAG and MOG {lines 120, 125, 129} represent meshes and a model of highest level (0): the distinction between the meshes MAG0 and MAG will be explained at u2.07.02-operateur-defi-maillage-ligne-120 and u2.07.02-operateur-asse-maillage-ligne-125.

### 5.2 Macro-element and substructure

One calls **macro-element** the result of the operator MACR_ELEM_STAT: it is a model condensed onto its external nodes.

One calls **substructure** an **occurrence** of a macro-element in a model of the same level. A substructure is a macro-element placed in position in physical space. The position of a substructure is given by the coordinates of the nodes of the super mesh cell associated with it.

One and the same macro-element can give rise to several substructures by defining several positions: in our example, the macro-element S_1 generates 3 substructures S_1, S_2 and S_3 by appropriate rotations.

A substructure is in some sense a new "finite element". The macro-element is the "type" of this element: one assigns a macro-element on a super mesh cell in order to form a substructure.

One calls **super mesh cell** the geometrical support of a substructure. It is a **named** object included in a **mesh**. A super mesh cell, like an ordinary mesh cell, is only an ordered list of node names.

Like an ordinary finite element, a substructure possesses:

- an "elementary" stiffness matrix (and/or of mass, of damping, …),
- "elementary" loading vectors,
- a support mesh cell (one will speak of a super mesh cell),
- nodes carrying degrees of freedom.

Unlike an ordinary finite element, a substructure has several limitations:

- the support mesh cell is not a simple type: TRIA3, …, HEXA20: certain post-processing is therefore not possible,
- it has no type_élément, no shape functions, …
- the only analysis options available are RIGI_MECA, MASS_MECA and CHAR_MECA,
- the nodes may be LAGRANGE nodes coming from the dualisation of the internal kinematic conditions.

**Identification of the substructures and of the macro-elements:**

The macro-elements are concepts named by the user.

The substructures (like the ordinary finite elements) are identified by the name of the super mesh cells which support them.

**In our example:**

- S_1 and S_123 are the two macro-elements defined by the user {lines 45 and 104},
- S_1, S_2, S_3, S_123 are the names of the super mesh cells (and therefore of the substructures) which the user gives when constructing the meshes MA_123 and MAG0.

**Note:**

*There is no possible confusion (on the part of the program) between a substructure and a macro-element of the same name (here S_1 and S_123, although this does not make the command file easier to read!).*

### 5.3 Descent into the substructures

The **ascending** approach, which we have just detailed, makes it possible to construct the global, or final, model (mog) on which one carries out the solution:

| CALC_MATR_ELEM |  |
| --- | --- |
| CALC_VECT_ELEM |  |
| ASSE_MATRICE | {lines 151-184} |
| … |  |
| RESOUDRE |  |

This solution has as its result the displacement field of the nodes of the global model. These nodes are:

- the nodes of the ordinary finite elements of the model (here the quadrilateral IJBA),
- the **external** nodes of the substructures of the model: (here a single substructure: S_123).

To recover the displacement field on the internal nodes of the substructures, one must then "**descend**" the tree of the substructures by means of the operator DEPL_INTERNE.

This operator computes the displacement field on **all** the nodes of the substructure from the data of the displacement field on its external nodes.

For our example and for load case 1:

| U1S_123 | {line 193} | is the displacement on the substructure | S_123 |
| --- | --- | --- | --- |
| U1S_1 | {line 197} | is the displacement on the substructure | S_1 |
| U1S_2 | {line 199} | is the displacement on the substructure | S_2 |
| U1S_3 | {line 201} | is the displacement on the substructure | S_3 |

### 5.4 Post-processing

The usual post-processing: analysis of the strains, of the stresses, … can be carried out only by the ordinary finite elements, which alone know the notion of interpolation function.

One will therefore be able to compute the stresses at a given point of the structure only with the model containing the ordinary finite element containing that point. Before that, it will have been necessary to compute the displacement field on this model:

**Example:**

- to compute the stresses on the quadrilateral IJBA one will use the model: MOG and the displacements: U1
- to compute the stresses on the polygon DCEF one will use the model: MO_1 and the displacements: U1S_2

**Note**

One must use CALC_CHAMP, but to do so one is obliged to create an evol_elas data structure by the command CREA_RESU.

### 6.2 Operator MACR_ELEM_STAT {lines 45-59}

- The example illustrates the fact that one can define the macro-element in several successive stages (use of the operator MACR_ELEM_STAT 3 times: {lines 45, 50 and 56} with the enrichment symbol &).

> At the first call, one truly defines the macro-element:

- its "volume": the model mo_1
- its external nodes {line 48}
- the material field and the kinematic conditions applied to it {line 47}.

> At the next 2 calls {lines 50 and 56}, one enriches the data structure of the macro-element:

- computation of the condensed stiffness matrix {line 52}
- computation of two "load cases" {lines 53 and 58}.

> This possibility of enriching the macro-element makes it possible to "repair an omission" without starting again from scratch:

- addition of a new load case,
- computation of the condensed mass for a Guyan method.

- Definition of load case 1: CHF1 {line 53}

> This load case is a follower one (SUIV = 'OUI') because the pressure is a loading which always acts along the normal to the edge.
> Having specified the load CHBL_1 serves no purpose here, because the kinematic conditions are zero DX = 0.0 DY = 0.0 {line 29}.
