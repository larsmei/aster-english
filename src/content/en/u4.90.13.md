# u4.90.13 Macro-command PERM_MAC3COEUR

## 1 Purpose

Macro-command making it possible to define the loading of a core from previous results.

## 2 Syntax

```text
evol_noli = PERM_MAC3COEUR(
    ◆ TYPE_COEUR_N = / "MONO",
                     / "MONO_FROID",
                     / "TEST",
                     / "900",
                     / "1300",
                     / "N4",
                     / "LIGNE900",
                     / "LIGNE1300",
                     / "LIGNEN4",
    # Si: is_in("TYPE_COEUR_N", ("LIGNE900","LIGNE1300","LIGNEN4"))
        ◆ NB_ASSEMBLAGE_N = int,
    ◆ TYPE_COEUR_NP1 = / "MONO",
                       / "MONO_FROID",
                       / "TEST",
                       / "900",
                       / "1300",
                       / "N4",
                       / "LIGNE900",
                       / "LIGNE1300",
                       / "LIGNEN4",
    # Si: is_in("TYPE_COEUR_NP1", ("LIGNE900","LIGNE1300","LIGNEN4"))
        ◆ NB_ASSEMBLAGE_NP1 = int,
    ◆ TABLE_N = table,
    ◆ RESU_N = evol_noli,
    ◆ TABLE_NP1 = table,
    ◆ MAILLAGE_NP1 = maillage,
)

◆ : obligatoire
◇ : optionnel
⟐ : présent par défaut
& : ensemble
/ : un seul parmi
| : plusieurs choix possibles
```

## 3 Principle

The command makes it possible to start an analysis of a cycle (CALC_MAC3COEUR / DEFORMATION) from previous results, taking into account the loading pattern and the names of the assemblies. It is thus possible to chain the cycle analyses: for example

- from the results of the analyses of CHO101 (starting core), one can start the analysis of CHO102 (arrival core) with fresh assemblies and assemblies coming from CHO101,
- after the analysis of CHO101 and CHO102 (starting cores), one can start the analysis of CHO103 (arrival core) from fresh assemblies, assemblies coming from CHO101 and assemblies coming from CHO102
- it is also possible to start a core analysis of any type (say 'N4' to take an example) from a set of results of core analyses of arbitrary types (say 'MONO' to take an example): it is sufficient that the names of the assemblies correspond between the arrival core and the starting cores.

## 4 Operands

### 4.1 Operand TYPE_COEUR_N

Name of the type of the starting core.

### 4.2 Operand NB_ASSEMBLAGE_N

In the case of a starting core of type 'LIGNEXXX' (with XXX='900','1300', 'N4' or 'EPR'), makes it possible to specify the length of the starting line

### 4.3 Operand TYPE_COEUR_NP1

Name of the type of the arrival core.

### 4.4 Operand NB_ASSEMBLAGE_NP1

In the case of an arrival core of type 'LIGNEXXX' (with XXX='900','1300' or 'N4'), makes it possible to specify the length of the arrival line

### 4.5 Operand TABLE_N

Ordered list of tables containing the assembly information (mainly name, position and design) in the starting cores. If an assembly (identified by its name) appears in several tables, the result used will be the last one that appears in the list. The lists TABLE_N and RESU_N must therefore be ordered from the oldest to the most recent. For example

> TABLE_N = (tab_CHO101, tab_CHO102),
> RESU_N = (resu_CHO101,resu_CHO102)

### 4.6 Operand RESU_N

Ordered list of results on the starting cores (the list must be of the same length as TABLE_N, and TABLE_N and RESU_N must be in the same order)

### 4.7 Operand TABLE_NP1

Table containing the assembly information in the arrival core

Warning: it is essential that the information concerning an assembly be consistent in the starting and arrival tables (for example, an assembly of the same name in the starting and arrival tables must also have the same design in those tables)

### 4.8 Operand MAILLAGE_NP1

Mesh corresponding to the description of the arrival core.
