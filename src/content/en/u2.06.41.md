# u2.06.41 Validation of a dynamic model by analysis–test correlation

**Summary**

This documentation is intended to describe the principal tools for assisting the validation of models in structural dynamics by analysis–test correlation. In particular, one describes:

- how to import data coming from measurements,
- validation by the MAC criterion,
- validation by comparison of computed/simulated FRFs

## 1 Introduction

In order to evaluate the predictive capability of a numerical model in structural dynamics, it can be useful, or even indispensable, to validate it against data measured *in situ* . The most classical manner is the comparison of the eigenmodes (frequencies and shapes) computed and identified experimentally, two by two. The eigenmodes reflect the global behaviour of the structure, and are often used as the sole validation tool. The principal difficulty in this case is to be capable of pairing the numerical and experimental modes two by two.

The objective of this documentation is to describe the methods and tools usable in Code_Aster for comparing the data of the analysis and of the measurement. Section  2 deals with the importation of data coming from measurement software into *Code_Aster* . In section  3 , the use of one of the principal criteria for model validation is detailed: the MAC matrix. In section  4 , other means proposed in the *Code_Aster*  environment for validation (comparison of FRFs and of shapes) are addressed.

## 2 Importing measured data into Code_Aster

### 2.1 Which data to import?

The measured data come from a signal-acquisition and processing software. Among them one may cite:

- LMS TestLab,
- Me'Scope,
- B&K Pulse,
- Labview,
- …

Most of these software packages make it possible to export data in the universal format, developed by the IDEAS software (extension *.unv), data which can be read back into *Code_Aster* by LIRE_RESU(FORMAT='IDEAS').

These files generally contain the information relating to the mesh of the structure and to the experimental data. The unv files are ascii files. Each set of data is called a “dataset”, and is framed in the file by two “-1”. The number which follows the first occurrence “-1” corresponds to the type of dataset. Each dataset is composed of several lines (record), and each line contains data arranged in columns (field)

It is important to understand certain characteristics of this storage, because the data must be recalled when calling LIRE_RESU. In particular:

- Record 6 $(1,2,2,8,2,3)$ :

  - 1 : domain of structural mechanics,
  - 2 : one describes an eigenmode (“normal mode”)
  - 2 : 3 degrees of freedom per node,
  - 8 : displacement field,
  - 2 : real field (5 for complex),
  - 6 : number of columns of values
- Record 7 $(2,4,1,1)$ :

  - 2,4: specific to the eigenmodes,
  - 1 : load case (1 by default),
  - 1, number of the mode
- Record 8: $2.18331e+011.00000e+003.74657e-030.00000e+00$

  - $2.18331e+01$ : natural frequency,
  - $1.00000e+00$ : modal mass,
  - $3.74657e-03$ : modal damping

### 2.2 Creation of an experimental model in Code_Aster

The handling of experimental data in Code_Aster requires the adequate data structures to be created, with the formalism of the code. One must therefore reproduce all the steps of the creation of the model, up to the assembly of the matrices which are used in LIRE_RESU (keywords MATR_RIGI and MATR_MASS in the example above).

#### 2.2.1 General case

In the general case, the nodes are all connected to one another by linear SEG2 elements. The commands to be chained are the following:

- importation and reading of the mesh with PRE_IDEAS and LIRE_MAILLAGE,
- assignment of a mechanical modelling of type DIS_T; one could use a DIS_TR modelling in the case where the field to be read had 6 degrees of freedom per node (for example, if one is capable of measuring the rotational degrees of freedom),
- assignment of arbitrary geometric characteristics in mass and stiffness on the nodes and segments with AFFE_CARA_ELEM,
- assembly of the matrices with ASSEMBLAGE,
- reading of the data with LIRE_RESU.

Example: test case sdls112a, slightly modified so as not to take the orphan nodes into account.

PRE_IDEAS(UNITE_IDEAS=32,UNITE_MAILLAGE=22);

MAYAEXP=LIRE_MAILLAGE(UNITE=22);

MAYAEXP=DEFI_GROUP(reuse =MAYAEXP,

MAILLAGE=MAYAEXP,

CREA_GROUP_MA=_F(NOM='ALL_EXP',TOUT='OUI',),

CREA_GROUP_NO=_F(GROUP_MA='ALL_EXP',),);

MODEXP=AFFE_MODELE(MAILLAGE=MAYAEXP,

AFFE=_F(GROUP_MA='ALL_EXP',

PHENOMENE='MECANIQUE',

MODELISATION='DIS_T',),);

CHCAREXP=AFFE_CARA_ELEM(MODELE=MODEXP,

CARA='K_T_D_L',

VALE=(1.0,1.0,1.0,),),

_F(GROUP_MA='ALL_EXP',

REPERE='GLOBAL',

CARA='M_T_D_L',

VALE=(1.0,),),),);

ASSEMBLAGE( MODELE=MODEXP,

CARA_ELEM=CHCAREXP,

NUME_DDL=CO('NUMEXP'),

MATR_ASSE=(_F(MATRICE=CO('KASSEXP'),

OPTION='RIGI_MECA',),

_F(MATRICE=CO('MASSEXP'),

OPTION='MASS_MECA',),),);

MODMES=LIRE_RESU(TYPE_RESU='MODE_MECA',

FORMAT='IDEAS',

MODELE=MODEXP,

UNITE=32,

NOM_CHAM='DEPL',

MATR_RIGI =KASSEXP,

MATR_MASS =MASSEXP,

FORMAT_IDEAS=_F(NOM_CHAM='DEPL',

NUME_DATASET=55,

RECORD_6=(1,2,2,8,2,3),

POSI_ORDRE=(7,4,),

POSI_NUME_MODE=(7,4),

POSI_FREQ=(8,1,),

A few pieces of advice and pitfalls to be avoided:

- The order of the components (keyword NOM_CMP) in LIRE_RESU is not compulsory; it is possible to carry out a simple change of coordinate system (the same for all the nodes) by choosing judiciously the order of the components.
- Beware of the keyword RECORD_6; it can vary; this is in particular the case when the unv file has been created by *Code_Aster* itself. Indeed, it can happen that the data are printed on 6 columns, in the case where the user has printed the data on a DIS_TR modelling. The last 3 columns contain the rotational degrees of freedom. This is the case in the test case sdls112a. One can read back only the first three if the experimental model has only 3 degrees of freedom per node.
- It is possible to read data coming from strain gauges. In this case,

  - NOM_CHAM='EPSI_NOEU',
  - NOM_CMP=('EPXX','EPYY'...) to be chosen according to the coordinate system used.
  - In order to compare these data with numerical data, one will be able to use the macro-command OBSERVATION.

#### 2.2.2 Case of the orphan nodes

It is not advisable to use orphan nodes in the mesh, because the associated fields are difficult to visualise in Salomé. One can nevertheless read experimental data on these nodes, provided that one applies to them a specific modelling of point type (POI1).

The case is treated in the test case sdls112a.

MAYAEXP=CREA_MAILLAGE(MAILLAGE=MAYAtmp,

REPERE='GLOBAL',

VALE=(1.0,1.0,1.0,),),

_F(GROUP_MA='NOEU',

CARA='M_T_D_N',

VALE=(1.0,),),),);

## 3 Model validation by the MAC criterion

### 3.1 What is the MAC?

The MAC, Modal Assurance Criterion, is a criterion lying between 0 and 1 giving the collinearity between two modes with respect to a given norm.

${\mathit{MAC}}_{ij}=\frac{{({\Phi}_{i}^{H}W{\Phi}_{j})}^{2}}{({\Phi}_{i}^{H}W{\Phi}_{i})({\Phi}_{j}^{H}W{\Phi}_{j})}$

The use of the weighting matrices ($W$  in the formula) is optional. When one knows them, one can use the mass or stiffness matrices of the model. This is the case when one handles numerical data, because the matrices have been assembled on the model. It makes it possible to check the orthogonality of the eigenmodes with respect to the mass and stiffness matrices:

- ${\mathit{MAC}}_{ij}=1\mathit{si}i=j$
- ${\mathit{MAC}}_{ij}=0\mathit{sinon}$

But when one handles experimental data, one does not know the matrices condensed on this model. One can manufacture them by Guyan condensation from the numerical model, but, the latter not being updated, one risks making an error.

One can, more simply, compute the MAC without a weighting matrix, and look at the collinearity of the modes in the norm ${L}_{2}$ .

- If the objective is to check the orthogonality of the basis, one can consider, as a first approximation, that the MAC without a weighting matrix is fairly similar to the MAC weighted by the mass matrix,
- If the objective is to compare two bases of modes with each other, then the choice of this norm is equivalent to the others: the MAC will be equal to 1 if the modes are collinear (hence if they “look alike”) and 0 otherwise.

NB: the use of the MAC on experimental modes makes it possible in particular to check the capability of the sensors to separate the modes. Indeed, the more sensors one has, the more the modes “will look different” as seen from them. The MAC of two different modes correctly identified will therefore be close to 0. If one has a single sensor, then the MAC between two modes will always be equal to 1: the modes are not separable.

### 3.2 Projection of fields

#### 3.2.1 Projection of the numerical data onto the experimental model with PROJ_CHAMP

The modes are comparable only if they are defined on the same model. One therefore projects the numerical modal basis, computed with *Code_Aster* , onto the experimental model, with the command PROJ_CHAMP.

![Figure](/figures/u2.06.41/10000000000004220000031A8254940427DDB68B.png)

**Image** 3.2-1 **: projection of data.**

Notes:

- Important note: one must specify, in PROJ_CHAMP, the name of the NUME_DDL of the experimental model, so that the numberings of the experimental modes and of the projected numerical modes are the same.

  - If the NUME_DDL is not the same, one will not be able to compute a MAC criterion.
- In PROJ_CHAMP, it is necessary to specify the dimension onto which one projects: by default, one will associate the nodes of the experimental model with 3D elements of the numerical model.

  - If the numerical model is constituted of plate elements, one must specify it with CAS='2.5D',
  - If the numerical model is composed of 3D and 2D elements, then it is not possible to specify several types of projection. One solution proposed is to assign a plate modelling (DKT for example) to the skin elements which cover the 3D elements and to place oneself in the case '2.5D'.
- The operator OBSERVATION makes it possible to carry out the same operation, with additional options:

  - use of local coordinate systems sensor by sensor,
  - removal of the measured data from the result data structure (for the cases where the measurement had been made with uniaxial sensors),
  - creation of a mixed data structure comprising accelerometric and extensometric data, in order to reproduce an accelerometer + strain-gauge measurement,
  - simulation of a “virtual gauge”.
- The description of this operator is proposed in the following paragraph.

- on the experimental data, one filters the modes so as to eliminate the unmeasured data, keeping only one direction for the strain gauge and the accelerometer

## 4 Other validation methods

### 4.1 Validation by visual comparison of modal shapes

This mode of validation is the most direct. It can be done by printing the modal shapes in Salomé in the classical manner.

NB: in CALC_ESSAI, in the “Model expansion” tab, it is possible to select one or two bases (opposite “Result 1” and “Result 2”) and to visualise them in GMSH by clicking on “Shapes”. It is not currently possible to visualise the shapes in Salomé; this development is to be carried out in 2012 (by adding the possibility of superimposing the shapes).

### 4.2 Validation by comparison of FRFs

A procedure is proposed in CALC_ESSAI making it possible to compare an FRF coming from the measurement with an FRF simulated by hammer impact. This validation method is different, because the comparison is done at one measurement point at a time, but over an extended frequency band. It makes it possible to check the very validity of the modal model.

To this end, click on “FRF” in the “Model expansion” tab. The following window appears:

### 5.4 Script for the 3D representation of a MAC diagram

This script can be copied at the bottom of a command file, replacing the names $\mathit{B1}$ and $\mathit{B2}$ on the last line by the names of the two bases which one wishes to compare by MAC.

Warning: this script relies on the matplotlib library, which must be installed.

def mac_plot_lib(BASE1,BASE2):

""" computes the mac between two bases, extracts it and represents it in a 3d graph

matplotlib"""

__MAC=MAC_MODES(BASE_1=BASE1,

BASE_2=BASE2);

mactmp=__MAC.EXTR_TABLE()

mac = mactmp['NUME_MODE_1','NUME_MODE_2','MAC'].Croise()

mac_py = mac.values()

import numpy as np

from mpl_toolkits.mplot3d import axes3d

import matplotlib.pyplot as plt

freq_1 = BASE1.LIST_PARA()['FREQ']

freq_2 = BASE2.LIST_PARA()['FREQ']

nume_ordre_1 = BASE1.LIST_PARA()['NUME_ORDRE']

nume_ordre_2 = BASE2.LIST_PARA()['NUME_ORDRE']

nb_freq_1 = len(freq_1)

nb_freq_2 = len(freq_2)

matrice_mac = np.transpose(np.array([ mac_py[kk] for kk in nume_ordre_1]))

fig = plt.figure()

ax = axes3d.Axes3D(fig)

# Create regular mesh from coordinates

xpos,ypos = np.meshgrid(np.arange(nb_freq_1),range(nb_freq_2))

xpos = xpos + 0.5*(np.ones(matrice_mac.shape)-matrice_mac)

ypos = ypos + 0.5*(np.ones(matrice_mac.shape)-matrice_mac)

xpos = xpos.flatten()

ypos = ypos.flatten()

dx = matrice_mac.flatten()

dy = dx.copy()

dz = dx.copy()

zpos=np.zeros(nb_freq_1*nb_freq_2)

for kk in range(len(xpos)):

if dx[kk]<1.0E-6:

# to avoid crashes when the mac is too small

dx[kk]=dy[kk]=dz[kk]=1.0E-6

ax.bar3d(xpos[kk],ypos[kk],zpos[kk],

dx[kk],dy[kk],dz[kk],

color=mac2col(dz[kk]))

ax.set_xlabel(u'FREQ_I')

ax.set_ylabel(u'FREQ_J')

ax.set_zlabel(u'MAC')

plt.show()

def mac2col(value):

# gives the colour value corresponding to a MAC value

# lying between 0 and 1

import matplotlib.colors as colors

import matplotlib.cm as cm

value = 1-value

desc=cm.RdYlBu._segmentdata

segments=[desc['blue'][kk][0] for kk in range(len(desc['blue']))]

num_seg=0

for kk in segments:

if value > kk:

num_seg = num_seg+1

tri=(desc['red'][num_seg][1],

desc['green'][num_seg][1],

desc['blue'][num_seg][1])

return colors.rgb2hex(tri)

mac_plot_lib(B1,B2)
