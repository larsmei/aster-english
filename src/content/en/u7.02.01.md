# u7.02.01 Operator LIRE_RESU

## 1 Purpose

Read fields and store them in a data structure of type resultat.

The type of the format of the file read is: either the MED format, or the IDEAS universal format.

Produces a data structure of type resultat (evol_noli, evol_ther, ...).

### 3.1 Keyword RESULTAT

In the case where one wishes to enrich an existing result data structure, the keyword RESULTAT indicates that the object is enriched. It is a means, in particular, of modifying MODELE, EXCIT, COMPORTEMENT, CARA_ELEM and CHAM_MATER between several time instants.

Note: one imposes that the order numbers and/or the time instants be (strictly) increasing in the case where one enriches an already existing result data structure. If this is not the case, a fatal error will be emitted.

### 3.3 Operands if FORMAT = 'IDEAS'

One does not read *datasets*  58 (but only *datasets*  55, 57 and 2414)

#### 3.3.1 Keyword FORMAT_IDEAS

##### 3.3.1.1 Objective

The fields to be read in the universal file are written in the form of *datasets*. Each *dataset* is composed of a header "*identity card*" and of a set of values (results at the nodes or by element at the nodes). This identity card is composed of several records "record", composed of fields "*field*". The objective of this keyword is to make it possible for the user to define their own "identity card" by specifying their own search criteria.

**Notes:**

A certain number of "identity cards" are defined by default [§6]. One can "overload" them by using the keyword *FORMAT_IDEAS.*

*In certain particular cases (non-regression tests) the mesh associated with the model was not created by PRE_IDEAS. If one does not find in the mesh the node associated with the number that appears in dataset 55, then one recovers the name of the node in a comment in the universal file, while checking that the associated number does indeed correspond to the name recovered.*

```text

```

The character string 'XXX' is a wildcard making it possible to ignore the component when reading the values.

If the number of components to be read is greater than the number of components present in the .unv file, the extra components are ignored.

**Important note:**

*When one reads a* *cham_elem, it is dimensioned in accordance with the finite elements of the model (see keyword* *MODELE below). For example, if one reads a stress field on a 2D model, the components carried by the elements will be* *SIXX,* *SIYY, SIXY and* *SIZZ. If in the IDEAS file one finds the components:* *SIXX,* *SIZZ,* *SIXZ, the components* *SIXZ will be ignored. On the other hand, all the components not found in the file (SIYY and* *SIXY in our example) will be set to zero.*

**Note on the assignment of the field at the node in datasets 55:**

*In a universal-format file (Ideas), a node of the mesh is known by its number. In Aster, a node is known by its name. The transcription is done by assigning to the node a name that begins with* $\text{N}$ *followed by its Ideas number. When reading the field at the node in a dataset 55, one checks that the node exists in the Aster mesh. If this is not the case, then one considers the name given, usually, in a comment next to the node number in dataset 55.*

◊    NB_VARI

Number of internal variables for fields of type ' VARI'

◊    PROL_ZERO =

If PROL_ZERO = 'OUI': one sets to 0 the values of the components at the nodes where the field is not defined, and one emits information of the type: " Non-existent values of the field TEMP read on the given mesh are considered null."

If PROL_ZERO = 'NON': one keeps the field as it is.

This keyword is dedicated only to fields at the nodes, because for fields at the elements the field is extended by 0 by default.

#### 3.4.2 Keyword REDEFI_ORIENT

This optional factor keyword makes it possible, if need be, to redefine the sensitive direction of the sensor at certain measurement points. This redefinition is currently treated only for the NOM_CHAM =‘DEPL’, ‘VITE’ and ‘ACCE’. One redefines as many orientations as necessary. If this keyword is absent, one adopts the usual convention recalled in the following table:

| **Direction code** | **‘DEPL’, ‘VITE’, ‘ACCE’** | **‘SIEF_NOEU’** | **‘EPSI_NOEU’** |
| --- | --- | --- | --- |
| 1 | DX | SIXX | EPXX |
| 2 | DY | SIYY | EPYY |
| 3 | DZ | SIZZ | EPZZ |
| 4 |  | SIXY | EPXY |
| 5 |  | SIXZ | EPXZ |
| 6 |  | SIYZ | EPYZ |

##### 3.4.2.1 Operands

◊ CODE_DIR    =    /1,

> /2,
> /3,

Code describing the measurement direction, given in the header of dataset 58.

◊ DIRECTION =(dx, dy, dz)

Direction vector, expressed in the global coordinate system, indicating the sensitive direction to be associated with CODE_DIR

◊NOEUD =    l_no,

List of the nodes where CODE_DIR must be associated with the direction vector DIRECTION.

#### 3.4.3 Note: structure of the field created

Universal files in dataset 58 format contain "fields with holes": each dataset contains the data associated with a node and a direction. The field cannot be extended by null values, as is the case for files of type dataset 55, 57 or 2414. One creates a field whose components are, for each node:

  - $\mathrm{Di}$ , the number $i$ being associated with the direction code in the local coordinate system,
  - $\mathrm{DiX}$ , $\mathrm{DiY}$ and $\mathrm{DiZ}$ , giving the local direction in the global coordinate system.

Note: it is not possible to print and to visualise directly the field read in the standard formats (MED type). On the other hand, the field read can be used in computation–test correlation operators. The result field contains the standard components and can be printed.

### 3.5 Operands if FORMAT = ’MED’

In MED format it is possible to read data structures of the following type: DYNA_TRAN, DYNA_HARMO, MODE_MECA, MODE_MECA_C. However, it should be noted that this rereading does not make it possible to fill the parameters of the data structure. The analysis may stop if these parameters are necessary for the execution of a command.

#### 3.5.1 Operand NOM_CHAM

```text
♦ NOM_CHAM =    nomch,
```

Symbolic name of the field to be read. One can a priori read the fields at the nodes, the fields by elements at the nodes (ELNO), the constant fields (ELEM) and fields at the integration points (ELGA). See the keyword NOM_CHAM outside the factor keywords [§3.5.1]

#### 3.5.2 Operand NOM_CHAM_MED/NOM_RESU

```text
♦/     NOM_CHAM_MED = nommed,

/     NOM_RESU = nommed,
```

Makes it possible to define the name of the MED field, either explicitly or automatically:

- NOM_CHAM_MED: Name according to the MED convention of the field to be read in the file. It is a string of 32 characters,
- NOM_RESU: Prefix of the name of the MED field to be read in the file. It is the name of the result associated with the MED field. It is a string of at most 8 characters. It makes it possible to define the name of the MED field automatically with the data supplied to NOM_CHAM.

#### 3.5.3 Operands NOM_CMP/NOM_CMP_MED

```text
◊ NOM_CMP        =    lcmp,

◊ NOM_CMP_MED    =    lcmpmed,
```

These two lists must be of the same length. One reads in the MED file the components listed in lcmpmed, then one assigns them to the components in the *Code_Aster* sense, of the same rank in the list lcmp.

The names of the MED components are limited to 16 characters.

If these 2 lists are absent, one assumes that the names of the components are the same for MED and for Aster.

#### 3.5.4 Operand PROL_ZERO

When reading a field at the Gauss points in MED format, one checks the consistency between the Gauss points as they are defined in the MED file and in Aster.

If the number of "MED" Gauss points is different from the number of "Aster" Gauss points one simply emits an alarm and one does not fill the field on the elements concerned. One will therefore have undefined values (NaN) where the field is not defined. The keyword PROL_ZERO = 'OUI' makes it possible for the user to set null values if so wished.

### 3.7 Reading of the MODE_MECA

One can read eigenmodes stored in IDEAS format. ### 3.8 Reading of the MODE_EMPI

> ◊    NUME_PLAN    =    /0                                                [DEFAUT]

```text
/nume_plan,                                    [I]
```

The empirical modes on a thermal result may be defined on a section of the mesh (so-called "lineic" model) for the simulation of welding. The operand NUME_PLAN makes it possible to specify to which section the empirical modes read belong. If this parameter is equal to zero, then the empirical mode read is 3D (general case).

### 3.9 Reading of the EVOL_NOLI

#### 3.9.1 Operand COMPORTEMENT

The syntax of this keyword, common to several commands, is described in the document [U4.51.11](doc:u4.51.11). This keyword must be supplied in the case of non-linear mechanics because it is used on restart of an analysis in STAT_NON_LINE and DYNA_NON_LINE to check the compatibility of the behaviours (the number of internal variables in particular). If one does not supply it, the structure will be considered to have elastic behaviour (COMPORTEMENT='ELAS') in small strains (RELATION='PETIT').

The concept EVOL_THER is used for linear thermal analysis and for non-linear thermal analysis. In the latter case, the thermal behaviour (keyword COMP_THER_NL in THER_NON_LINE) is not available in LIRE_RES, which means that the concept EVOL_THER created by LIRE_RESU does not contain the thermal behaviour map (COMPORTHER) and is therefore not entirely consistent. However, this problem is not troublesome insofar as the behaviour map is created in THER_NON_LINE, including on restart, and the non-linear thermal behaviours have no internal variables; it is therefore not necessary to check the compatibility of the non-linear fields on restart; there is no risk of incorrect results.
It is the same for the concept EVOL_SECH used for the drying analyses.

#### 3.9.2 Operand VERI_VARI

> ◊    VERI_VARI    =    /'OUI'                                            [DEFAUT]

```text
/'NON'
```

This keyword is used to check the consistency between the size of the fields of type VARI_ELGA and the definition of the non-linear behaviour.

If there are differences, alarms are emitted.
