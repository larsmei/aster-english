# u4.92.01 Procedure TEST_RESU

## 1 Purpose

Compare a value extracted from a data structure with a reference value supplied by the user.

This command makes it possible to test a numerical value: integer, real or complex extracted from an already computed concept. Today, one can test a component of a cham_no or of a cham_elem, a component of a field extracted from a resultat, a parameter of a resultat, a 'global' value extracted from a field, or else the content of an arbitrary object of a user concept.

The procedure then writes a conventional message:

- "OK" (if it is good),
- "NOOK" (otherwise).

followed by the value found, the reference value and the percentage of error.

Systematically, one checks a non-regression value, and when this is possible, an analytical reference value, coming from an external source or from another analysis with Code_Aster.

The commands TEST_FONCTION [U4.92.02](doc:u4.92.02) and TEST_TABLE [U4.92.03](doc:u4.92.03) make it possible to test the values extracted from the functions and from the tables.

## 3 General points

This command makes it possible to test a scalar numerical value retrieved from a concept of type cham_no, cham_elem, carte or resultat, against a non-regression value and, when it is possible, against an analytical reference value, coming from an external source or from another analysis with Code_Aster.

Three types of numerical values can be tested:

- a component of a field (cham_no, cham_elem, carte or field that is part of a resultat),
- a parameter contained in a concept of type resultat,
- a global value of a field [§ 4.4 ].

To test a field component, one must choose a field [§ 4.1 ] then choose a component [§ 4.3 ].

To test a parameter, one must choose an order number [§ 4.1.4 ] and choose the name of the parameter.

The expected numerical value (real, complex or integer) is supplied in accordance with [§ 4.7 ].

**Note concerning the non-regression tests**

*One systematically performs a non-regression test against a previously computed value. The tolerance associated with this test (* TOLE_MACHINE *) must be very small and should not be greater than the default value. In particular, the value should be the same (to at least 8 decimal places) on all platforms. Moreover, this computed value must change only when the algorithm is modified or corrected. Any other variation must alert the developer to the reliability of the programming.*

**Notes concerning the tests in the "generalised" data structures:**

*One can test the generalised components (displacements, velocities or accelerations of a transient in the modal space). One should nevertheless be cautious with this type of test. Indeed the value of a generalised component depends entirely on the norm of the mode. Now this norm is determined in an arbitrary manner. Therefore, without prior normalisation of the norms, the value of a generalised quantity is arbitrary. Finally, there is no possibility in Code_Aster of fixing the direction of a mode. For a multiple mode, this means that, even once the modes have been normalised, a generalised quantity can take any value. In the case of a simple mode, it may be oriented in one direction or in the opposite direction. One then obtains a generalised value or its opposite.*

## 4 Operands

### 4.1 Selection of a field

In order to test a field that may be an isolated field (cham_no or cham_elem or carte), or a field extracted from a result, one will use the factor keywords: CHAM_NO, CHAM_ELEM, CARTE or RESU.

#### 4.1.1 “Isolated” fields

```text
♦    CHAM_GD= champ
```

Name of the cham_no, cham_elem or carte from which one wants to extract a value.

#### 4.1.2 Operand RESULTAT

```text
♦    RESULTAT= res
```

Name of the resultat concept processed.

#### 4.1.3 Operand NOM_CHAM

```text
♦    /    NOM_CHAM= nosymb
```

Symbolic name of the field to be selected.

#### 4.1.4 Selection of an order number

```text
♦    /    NUME_ORDRE= nuor,
```

Order number of the field (or of the parameter) sought.

```text
/    NUME_MODE = numo,
/    INST = inst,
/    FREQ = freq,
/    NOEUD_CMP = (noeud, cmp),
/    NOM_CAS = nocas,
/    ANGLE = :math:`\alpha`,
```

These keywords make it possible to identify an order number in a resultat [U4.71.00](doc:u4.71.00).

They are called "access variables".

They are not all valid for all types of resultat.

When the access is made by a real value (ANGLE, FREQ, INST) the value given must not be ambiguous (cf. [§ 4.7 ]).

### 4.2 Selection of a parameter in a result

To select a parameter in a result, one must specify the required order number [§ 4.1.4 ] and give the name of the parameter.

```text
♦    PARA= para
```

Name of the parameter sought. This name is attached to the type of the resultat concept processed.

### 4.3 Selection of a component of a field

Access to a quantity is made, for a cham_no, by:

- the name of a node group containing the node that carries this quantity (and that node alone).

Access to a quantity is made, for a cham_elem, by:

- the name of a mesh-cell group containing the mesh cell that supports the element (and that mesh cell alone),
- something that specifies:
- either the name of a group containing a node of this mesh cell for the cham_elem "at the nodes" (ELNO).
- or the number of the Gauss point for the cham_elem "at the Gauss points" (ELGA).

Access to a quantity is made, for a carte, by:

- the name of a mesh-cell group containing the mesh cell,

```text
♦    GROUP_MA     = gma1
```

Makes it possible to designate the mesh cell for which one wants to test the cham_elem or the carte.

The group must contain only one mesh cell.

```text
♦    GROUP_NO= grno
```

Name of the group containing the node of which one wants to check a component.

The group must be reduced to a single node.

```text
/    POINT= nupoint
```

The integer nupoint specifies the number of the Gauss point whose value one wants to test (case of the cham_elem "at the Gauss points").

◊    SOUS_POINT = nusp

The integer nusp specifies the number of the sub-point from which one wishes to obtain the value (case of the cham_elem with sub-points, used by the structural elements: beams, pipes, shells).

In the case of multi-layer plates and shells, the sub-point number corresponds to the level in the set of layers. Each layer is described by a lower, middle and upper skin. By convention, for $N$ layers, this number varies between $1$ and $\mathrm{3N}$ where the first point lies at the level of the lower skin of the first layer and the $\mathrm{3N}$ th point at the level of the upper skin of the last layer (cf. [R3.07.03](doc:r3.07.03) and [R3.07.04](doc:r3.07.04) for the numbering of the layers).

In the case of multi-fibre beams, this integer is the number of the fibre whose numbering is described in the documentation [U4.26.01](doc:u4.26.01) and [R3.08.08](doc:r3.08.08).

In the case of pipes, one must refer to the description given in the document [R3.08.06](doc:r3.08.06).

```text
/    NOM_CMP = ncmp
```

Name of the component that one wants to test [U2.01.04](doc:u2.01.04).

```text
/    NOM_VARI = nvari
```

For the fields of the internal variables (VARI_* ), one may give the name of the internal variable (see [U4.51.11](doc:u4.51.11) for the naming rules of the internal variables) instead of the name of the component (V1, ...).

### 4.4 Testing a field "globally"

Once a field has been selected [§ 4.1 ], one can test a quantity computed globally over the whole field. For this, NOM_CMP must not be supplied so that all the components of the field can be taken into account.

```text
/    TYPE_TEST= ‘SOMM_ABS’
```

The sum of the absolute values of the components of the field.

```text
/    TYPE_TEST= ‘SOMM’
```

The sum of the values of the components of the field.

```text
/    TYPE_TEST= ‘MAX’
```

The maximum of the values of the components of the field.

```text
/    TYPE_TEST= ‘MIN’
```

The minimum of the values of the components of the field.

### 4.5 Testing the content of a JEVEUX object

This functionality is reserved for the developers of the code. To use it, one must know the names of the JEVEUX objects that make up the user's concepts. It is intended to check the non-regression of data structures other than the RESULTAT, CHAMPS, TABLE and FONCTION.

#### 4.5.1 Operand NOM

```text
NOM= nomobj
```

Name of the JEVEUX object that one wants to test.

**Note:**

*The aim of this type of test (NOM+* *VALE_CALC/_I) is to test a whole vector globally. The "sum" that is tested is unfortunately a poor "checksum" of the object: a permutation within the vector does not change this sum. A more cautious test consists in printing the object to a file (IMPR_CO) and then testing the content of this file with a true "checksum" (TEST_FICHIER).*

#### 4.5.2 Operands CRITERE and PRECISON

See below [§ 4.7 ].

### 4.6 Factor keyword MAILLAGE.

This keyword makes it possible to validate the commands of the code that produce (or modify) meshes.

It makes it possible to test a few (integer) characteristics of the meshes: number of mesh cells, of nodes, of mesh-cell groups, of node groups, number of mesh cells in a mesh-cell group and number of nodes in a node group.

#### 4.6.1 Operand MAILLAGE

```text
MAILLAGE= mailla
```

Name of the mesh that one wants to test.

#### 4.6.2 Operand CARA

Makes it possible to choose the characteristic of the mesh to be tested: 'NB_MAILLE', 'NB_NOEUD', 'NB_GROUP_MA', 'NB_GROUP_NO', 'EXI_GROUP_MA' or 'EXI_GROUP_NO'.

#### 4.6.3 Operands NOM_GROUP_MA and NOM_GROUP_NO

These operands are to be used for CARA='EXI_GROUP_MA' (resp. CARA='EXI_GROUP_NO' ).

They make it possible to designate the group that one wants to test.

In this case, the tested value (VALE_CALC_I or VALE_REFE_I) must contain the number of mesh cells (or of nodes) of the group.

### 4.7 Definition of the non-regression value and of the reference value

One systematically performs a non-regression test against a previously computed value, with a very small tolerance: keywords VALE_CALC and TOLE_MACHINE.

As often as possible, one adds a test against a reference value with respect to an analytical solution, a value obtained from an external source or another modelling: keywords REFERENCE, VALE_REFE, PRECISION.

```text
♦    /    VALE_CALC= val
```

Real non-regression value. It is the value computed by Code_Aster.

When this value is zero (less than 1.e-16 in absolute value), the keyword ORDRE_GRANDEUR = ordgrd must be supplied. It is meaningful only in absolute terms.

One then checks that: $\left|\mathit{val}\right|\le \mathit{tole}\ast \mathit{ordgrd}$

If ORDRE_GRANDEUR is not supplied even though VALE_CALC is zero, the non-regression test is ignored (it appears with SKIP in the result file). Beware: in this case, a test with VALE_REFE is compulsory.

```text
/    VALE_CALC_C= val
```

Complex non-regression value.

```text
/    VALE_CALC_I= val
```

Integer non-regression value.

```text
/    VALE_CALC_K= val
```

Character string of non-regression. Only by TEST_FICHIER and TEST_TABLE.

```text
◊    TOLE_MACHINE = tole
```

Accuracy required (by default 1.D–6) in order to accept the computed value with respect to the non-regression value (VALE_CALC). See ORDRE_GRANDEUR above.

```text
◊    VALE_ABS
```

```text
= ‘NON’    la valeur de référence et la valeur calculée par Aster sont comparées telles quelles.

= ‘OUI’    la valeur de référence et la valeur calculée par Aster sont comparées en valeurs absolues.
```

```text
◊    CRITERE=
```

Type of test to be performed. It applies to the non-regression test and to the test against a reference value where applicable.

If v is the extracted value, the test will concern, for:

- 'RELATIF' on: $\mid \mathit{val}-v\mid \le \cdot \mid \mathit{val}\mid$
- 'ABSOLU' on: $\mid \mathit{val}-v\mid \le$

```text
◊    REFERENCE=
```

| / 'ANALYTIQUE': | the reference value supplied is 'analytical' |
| --- | --- |
| / 'SOURCE_EXTERNE': | the reference value supplied comes from a program other than Code_Aster, from a bibliographic reference, from a measurement, etc. |
| / 'AUTRE_ASTER': | the reference value supplied is that obtained by another analysis with Code_Aster (another command, another modelling, analysis option, ...) |

It is the presence of the keyword REFERENCE that indicates that one has an external reference and that conditions the presence of the keywords VALE_REFE[_I/_C] and PRECISION.

```text
♦    VALE_REFE, VALE_REFE_C, VALE_REFE_I, VALE_REFE_K
```

Similar to the keywords VALE_CALC above. They define the value obtained from the external source.

```text
◊    PRECISION=
```

Accuracy required (by default 1.D–3) in order to accept the computed value with respect to the reference value (VALE_REFE).

**Note:**

*When the definition of the order number of a* *RESULTAT is made by a real access variable (FREQ,* *INST,* *ANGLE), there must be no ambiguity about this order number. For this the user defines a small interval around the required value by means of the keywords* *CRITERE and* *TOLE_MACHINE.*

*In this case ("real" access) the keywords* *CRITERE and* *TOLE_MACHINE will therefore expect 2 values each: (crit1,* *crit2) and (prec1,* *prec2).*

*crit1 and* *prec1 concern the non-regression value.*

*crit2 and* *prec2 make it possible to choose the search interval of the order number.*

*The default values of* *crit1 and prec1 are* *'RELATIF' and* *1.D-6.*

*The default values of* *crit2 and* *prec2 are* *'RELATIF' and* *1.D-3.*

*One cannot define* *crit2 and* *prec2 explicitly without defining* *crit1 and* *prec1.*

**Note:**

*The non-regression tests (keywords* *VALE_CALC) are systematically ignored in the validation tests* *but they must still be supplied (with any value) because they are required by the catalogue of the command.* *The validation tests are identified as such by the presence of* *testlist validation in their* *.export file.*

*There is however an exception for the tests on character strings (VALE_CALC_K), which are not ignored because there is no tolerance/accuracy on these tests.*

### 4.8 Addition of a specific feature to the tested value

> ◊    LEGENDE =

> Character string of at most 16 characters describing the test performed.
> The user therefore has the possibility of commenting on the test.

### 4.9 Keyword TEST_NAN

```text
|    TEST_NAN =            /    ‘NON’    ,                            [DEFAUT]
/    ‘OUI’    ,
```

This keyword is used to validate the operation of the $\mathit{NaN}$ ( *Not-a-Number* ) of Code_Aster. This keyword is to be used only with a view to carrying out tests. Its use must cause a fatal error in $\mathit{FPE}$ ( *Floating Point Exception* ) in *debug* mode in TEST_RESU.
