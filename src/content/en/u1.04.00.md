# Methods for launching a code_aster run

> **Summary.**

This document presents the different ways of launching a study on code_aster, such as AsterStudy, astk, run_aster, run_ctest and run_sbatch.

All the methods are described in terms of their operating logic, their advantages and their disadvantages. More precisely, we describe their graphical interfaces or their command-line approaches, and we explain how the user can launch a study according to his or her needs.

Note: Note that some methods are already contained in other methods. For example, AsterStudy uses the command run_aster or run_sbatch. Likewise, astk uses the low-level command as_run to launch a run. It is not recommended to use as_run directly, which is why we shall not give any details of this command here.

## 1 General notions

Here are a few definitions and pieces of information which will be used in the following sections:

### 1.1 Server

There are two types of server used in the context of the execution of code_aster:

- Compute server: machine on which the services required for the execution of the analyses are installed. One can access it in order to launch analyses, consult the results and handle the files required for execution.

- File server: machine used only to store and access the files required for the analyses, with no possibility of direct execution on it.

In the remainder of this document, we shall distinguish two categories of server according to their location relative to the user:

- Local server: this is the machine on which the user works directly. By default, this machine can be used as a file server, because its connection information is already known. However, if one wishes to execute analyses on it (for example if a version of code_aster is installed there), it is necessary to declare it explicitly as a compute server.

- Remote server: any machine other than that of the user, accessible via the network, can be declared as a compute server or a file server, according to requirements.

### 1.2 salome_meca container

This is a self-contained software environment, containing the main program as well as its dependencies. It makes it possible to run an application without having to install it directly on the host system. The name of the container image is constructed in the following manner:

```
salome_meca-<edf|lgpl>-<version salome_meca>-<packaging>-<version prérequis>-<base>.sif
```

The latest images are built on the basis of salome_meca 2024. The reference image is: salome_meca-edf-2024.1.0-1-20240327-scibian-11 (see `historique_des_images`_ for more details.)

#### 1.2.0.1 How to install the container?

There are two ways:

1. Open the *Packages* application and search for `salome-meca` (see the figure opposite). Select the package *salome-meca* or *scibian11 container for salome-meca-2024*, tick the box and click on Apply the changes.

![Paquet d'installation de salome-meca (**EDF seulement**)](/figures/u1.04.00/installer_conteneur.png)

1. Download the image locally (often into the directory *${HOME}/containers/*) from a terminal. Enter the command line:

```bash
wget -c https://minio.retd.edf.fr/codeaster/sif/stable/salome_meca-edf-2024.1.0-1-20240327-scibian-11.sif
```

Then, launch the installation script:

```bash
singularity run --app install salome_meca-edf-2024.1.0-1-20240327-scibian-11.sif
```

For more information, please visit `Prise en main rapide`_.

#### 1.2.0.2 How to access the container?

There can be two cases, according to how the container was installed:

1. When the *Packages* application was used:

On a Scibian machine, the *Packages* application has installed various files, of which the most important are `/usr/bin/salome-meca-2024` and `/usr/bin/salome-meca-2024-container-shell`. The first allows us to access the salome_meca container, in which one will be able to use asterStudy and astk. The second allows us to access the bash of the container in order to execute the command lines run_aster/run_ctest and/or as_run.

1. When the container image was downloaded:

One goes into the directory containing the container and starts the execution of salome_meca with:

```bash
./salome_meca-edf-2024.1.0-1-20240327-scibian-11
```

One can add the installation path to the PATH by putting:

```
export PATH=${HOME}/containers:${PATH}
```

in the file *~/.bashrc*. One will then be able to execute salome_meca-edf-2024.1.0-1-20240327-scibian-11 directly from anywhere (and without ./ in front). One can simplify the execution further by creating a link in the terminal with:

```bash
ln -s ${HOME}/containers/salome_meca-edf-2024.1.0-1-20240327-scibian-11 ct
```

Then, one can launch the container by doing:

```bash
ct
```

In addition, here are a few launching options:

```bash
ct --shell # démarre bash (seul .bashrc est chargé).

ct --help # affiche l'aide d'utilisation du script de démarrage.

ct shell # démarre salome shell (charge l’environnement SALOME).

ct -- shell --help # affiche l’aide de salome shell (pas du script de lancement).
```

### 1.3 ASTK profile

A profile is a file (extension .astk) which contains all the information relating to a study: the location of the files of the study, as input data and as results, the type associated with each file, the parameters for submission of the run (memory, time, compute machine, batch/interactive, etc.).

As its name indicates, it is inherent to the astk interface. Consequently, it also contains parameters concerning the interface itself, so as to resume a study in exactly the same state in which it had been left. It is saved at the user's request and at each launching of a run.

### 1.4 EXPORT file

This file (extension .export) is a simplified representation of the astk profile: it contains only the information on the files and the parameters required for the run (and no information on the astk graphical interface). The syntax of this file is the same for all the tools which launch code_aster from the command line.

Note: Note that all the tools for launching code_aster need, in one way or another, the *.export* file (see documentation D1.02.05).

#### 1.4.0.1 Example of a .export file

Here is an extract:

```
P actions make_etude
P time_limit 60
P memory_limit 512
P ncpus 1
P mpi_nbcpu 1
P mpi_nbnoeud 1
P version stable

F comm fichier.comm D 1
F datg fichier.datg D 16
F mmed fichier.mmed D 20
F resu fichier.resu R 8
F mess fichier.mess R 6
```

This example illustrates the indispensable parameters to be defined:

- actions make_etude : in order to launch a run
- time_limit : time in seconds of the submitted job
- memory_limit : memory in MB for the run
- ncpus : number of processors for OpenMP parallelism
- mpi_nbcpu : total number of processors for MPI parallelism
- mpi_nbnoeud : number of nodes for MPI parallelism
- version: a version of code_aster: stable, dev, etc.

For more information and the other optional parameters, visit document D1.02.05.

Note that the data files required in order to run the test are described in the form:

```
F/R type chemin D/R/C numéro_unité_logique
```

Here, F/R means that the user has the possibility of declaring the nature of the object pointed to by the path: file (F) or directory (R).

In addition, the user also has the possibility of saying whether the object consists of input data (D), of results (R) or is compressed (C).

The logical unit number makes it possible to identify each of the files (it can be used in the command file to designate the input or output files).

#### 1.4.0.2 List of types for a study

| **TYPE** | **DESCRIPTION** | **LOGICAL UNIT** |
| --- | --- | --- |
| comm | code_aster command files (including the restart files) | 1 |
| mail | mesh file in code_aster format | 20 |
| mmed | mesh in MED format | 20 |
| mess | file of the messages of the execution | 6 |
| resu | result file (printout of the tests, printout in code_aster format) | 8 |
| rmed | result file in MED format | 80 |
| base | directory containing the database of the run | 0 |

#### 1.4.0.3 How to add Python files and/or directories?

We deal with the case in which the user has a Python file *.py* with functions which are called in the command file. First of all, it should be noted that performing this action is possible with as_run, run_aster and astk. Up to version 2024, AsterStudy does not include this functionality.

If the user uses the methods as_run, run_aster or astk, the following line should be added to the .export file:

```
F nom chemin_du_fichier D 0
```

If the user needs to add a folder with various files, the following line should be added:

```
R nom chemin_du_dossier D 0
# ou
R repe chemin_du_dossier D 0
```

However, when astk is used, there are a few notes to consider when calling the functions. For more information, please read Example of importing folders.

#### 1.4.0.4 How to add a development version?

There is the possibility of adding new versions of code_aster (for example a development version) in astk and asterStudy (based on as_run). To do this, one adds the following line to the file `$HOME/.astkrc/prefs`:

```
vers : DEV:$HOME/dev/codeaster/install/mpi/share/aster
```

On the remote servers of EDF R&D, the installation path is different:

```
vers : DEV:/scratch/users/$USER/dev/codeaster/install/mpi/share/aster
```

## 2 Use of the AsterStudy interface

### 2.1 How to access it?

One must first launch the salome_meca container, then click on `View/AsterStudy` or directly on the tool icon in the toolbar.

![Figure](/figures/u1.04.00/capture_ecran_salome_meca.png)

### 2.2 How to launch a run?

In a very simplified manner, one should first define the different *stages* to be carried out in the *CaseView* tab (via `Operations/Add stage`). There is also the possibility of importing a test case by clicking `Operations/Import Testcase`.

For more detailed information, visit the [code_aster - salome_meca training](https://code-aster.org/spip.php?article915).

Once this step has been completed, one goes to the History View tab in order to provide the simulation parameters. Finally, one selects the *CurrentCase* and one clicks on the *Run* button (see the figure below).

![Fenêtre de History View dans Asterstudy](/figures/u1.04.00/asterStudy.png)

Note: In AsterStudy we have the possibility of choosing the machine on which to execute (e.g. local, cronos, gaia) as well as the code_aster version available on each machine (e.g. stable, dev, etc.).

#### 2.2.0.1 Run properties

In the *Run properties* window of the History View tab, we can provide salome_meca with the launching parameters.

#### 2.2.1 Basic

- Memory: equivalent to memory_limit of the export file. Memory in MB for the aster run

- Time: equivalent to time_limit. Time of the submitted job

- Run servers: the local or remote server available

- Version of code_aster: the versions installed on the selected server

- Number of MPI CPU: equivalent to mpi_nbcpu. Total number of processors for MPI parallelism.

#### 2.2.2 Advanced

Among the most used options:

- Run mode: interactive or console

- Number of MPI nodes: equivalent to mpi_nbnoeud. Number of nodes for MPI parallelism

- Number of threads: Number of threads for OpenMP parallelism.

### 2.3 Retrieval of the results

#### 2.3.0.1 In the event of success

If the simulation finishes without a major problem, AsterStudy will copy the various result files from the */tmp* folder and paste them into the location given beforehand. In addition, it will create a folder named *<hdf file name>_Files* in which one will be able to find the logs, the messages, etc., of each RunCase.

#### 2.3.0.2 In the event of failure

When an error occurs during a run, it is possible to retrieve the computation files already created (.rmed, .txt, logs, etc.). On a local machine, this directory is normally found at the location `/tmp` (or `/local00/tmp/`). On the cronos and gaia servers, access to the directory is restricted.

By construction, even in the event of a fatal error, AsterStudy will copy the intermediate results into the directory specified by the user. If the user wishes to analyse the cause of the error, he or she can consult the logs which are located in the */logs* directory on the tree of the study that was launched, or in the */tmp* directory.

Note: The tmp file is located at `/local00/tmp/` because that is the default path. To modify it, one would need to change the file $HOME/.astkrc/config_servers.

## 3 Use of the Astk interface

Astk is the graphical interface which makes it possible to organise code_aster analyses: prepare the data, organise the files, access the pre- and post-processing tools, launch and follow the progress of the analyses. Astk also makes it possible to choose the version of code_aster to be used from among those available (stable, testing, etc.).

![Figure](/figures/u1.04.00/capture_ecran_astk_1.png)

### 3.1 How to access it?

There are two ways of opening Astk:

- In the salome_meca container, one must click on `Tools/Plugins/code_aster/Run astk`.

- From the command line, one must execute, in the salome terminal:

```bash
Astk
```

Note: For more information on access to the salome_meca terminal, consult General notions.

### 3.2 Configuration

The first time the user launches the interface, he or she has a default configuration which was defined at installation. The configuration is then stored in the directory $HOME/.astkrc.

If the user wants to return to the original configuration, he or she must delete this directory and relaunch Astk.

In the following paragraphs, only the Servers menu is detailed.

#### 3.2.0.1 Servers

One accesses the servers window by clicking on *Configuration/Servers*.

The first button makes it possible to switch from one server to another and to add a "New server". The fields are:

- Full name or IP address: this is the name of the server on the network; one can give its full name with the domain name (for example: linux.labo.univ.fr) or its IP address (for example: 156.98.254.36).

- The "local machine" box indicates that Astk must not use ssh to contact this machine.

- Server state: one can set to "off" a server which is temporarily inaccessible.

- Login: identifier with which one connects to the server.

- HOME directory: default directory when one browses on this machine.

- Services directory: directory where the services are installed on this server (give the installation path, for example: /opt/aster); leave empty for a file server.

- Configuration download mode: none (for a file server), manual (one must click on the "Download now" button in order to retrieve the Aster configuration of the server), automatic (Astk queries the server at start-up every 30 days).

- Last download: date of the last update of the configuration information.

- Terminal: command for opening a terminal on the server. This makes it possible to open a command window on the server when one uses the bsf.

- Editor: text editor (for example, nedit). The installation procedure chooses an editor from among (and in this order): nedit, gedit, xemacs, emacs, xedit, vi.

Note:

- Whenever one defines a command to be executed (terminal, editor, etc.), it is advisable to give the absolute path (from the root) so that the command is not left unfound if the `$PATH` variable is incorrect.

- For users who have access to the EDF R&D servers, the information in the *Configuration/Servers* tab will need to be updated by clicking on the *Refresh now* button.

### 3.3 How to get a run launched?

In this paragraph and the following ones, a general description is given of how to use Astk in order to carry out a study.

Suppose that one wants to launch the study of the test case *forma00a*, for which the items available are:

- The *Aster* command file: forma00a.comm

- The description of the geometry produced with Salomé: forma00a.datg

- The mesh built by Salomé: forma00a.mmed

- The file containing the execution messages: forma00a.mess

In the example, all the files are placed in the directory $HOME/.

The files of this example are available in the astest directory of your version of *code_aster*.

Note: In the case of a study with several command files, all the files must be of type "comm", associated with logical unit 1, and it is the order of appearance in the profile which determines the order of execution.

#### 3.3.0.1 Creation of the profile

One launches the interface, which opens onto a blank profile; or else, if Astk is already launched, one chooses *File/New* in the menu in order to create a new empty profile.

One goes to the STUDY tab.

#### 3.3.0.2 Selection of the files

- **Definition of a base path**

In the STUDY tab, one chooses a base path in order to simplify access to the files. One clicks on the icon ![icon](/figures/u1.04.00/100000000000001A0000001882D179FCFD36DD40.png), and one chooses the directory $HOME/.

- **Addition of existing files**

One adds the command file by clicking on ![icon](/figures/u1.04.00/1000000000000019000000166BF7E1B13C675ABD.png); the file selection opens directly in the base path which has just been defined. All that remains is to select the file so that it appears in the list.

- **Addition of files which do not yet exist**

Unless an execution has already taken place, the result files do not yet exist, so one cannot add them by browsing the tree.

- by inserting an empty line:

by clicking on the new-file button ![icon](/figures/u1.04.00/10000000000000170000001B34383F7B49A2DD5F.png), a line is added to the list. For example, one can choose the type "mess" in the list in order to print the messages during execution. Then, one indicates the path $HOME/forma00a.mess or forma00a.mess or ./forma00a.mess (since it is possible to indicate the name of the file in absolute form, or relative to the base path). Finally, one fills in the logical unit number (equal to 6 by default), one ticks the "R" box (result) and one unticks "D".

- with "Default value":

This function uses the name of the Astk profile in order to build the default values. The profile must therefore be saved, if this has not yet been done. One chooses *Save as* in the *File* menu, one goes with the browser into the reference directory, and in the *Selection* line one writes, for example, forma00a (the extension .astk is added automatically). One inserts an empty line and one chooses the file type "mess", then one right-clicks in the file-name box and one chooses "Default value": Astk builds a file name from the base path, the profile name (with the extension removed) and the type "mess", that is $HOME/forma00a.mess. The "R" box has been ticked, and the logical unit number has been set to 6.

- **Delete a file**

To delete a line from the list of files, it is enough to select it by clicking in the area where the name of the file is indicated, and to click on the icon ![icon](/figures/u1.04.00/100000000000001800000019E013CF25FF4E0FD1.png). It should be noted that only the reference to this file in the Astk profile is forgotten; the file itself is not deleted.

#### 3.3.0.3 Launching of the run

The data and result files having been selected, one adjusts the parameters of the run, and one clicks on the "Launch" button.

One takes care to tick the box which is located just next to STUDY, in order to indicate that one wishes to use the contents of this tab; otherwise the interface replies "Nothing to launch!".

If the profile has not yet been saved, the interface asks one to choose a location and a name for this profile.

Astk calls as_run in order to execute the run, and transmits to the job monitor (asjob) the job number (process number in interactive mode) and other information which will make it possible to follow the progress of the run. The initial state of the run is PEND (pending); when the run starts, it becomes RUN, then ENDED when it is finished (other states are possible in batch). The "Refresh" button calls the service which refreshes the state of the runs in progress.

When the run is finished, one can consult the result of the job by double-clicking on the job, or via *Edit/Output file*.

![Figure](/figures/u1.04.00/10000000000003520000019658AE3D360A401ABE.png)

Figure 5.3-1: Job monitoring window

#### 3.3.0.4 Consultation of the results

One can consult the result files simply by double-clicking on their name, which opens a text editor for the "mess" and "resu" files.

Note:

- The directory which is to receive a result file does not exist; it is created automatically if the permissions are sufficient.

- If the copying of result files fails (problem of permissions, of quota, of remote connection...), they are copied into a temporary directory on the execution machine. An alarm <A>_COPY_RESULTS indicates the path where one must go to fetch the results.

### 3.4 Retrieval of the results

#### 3.4.0.1 In the event of success

If the simulation finishes without a major problem, Astk will copy the various result files from the */tmp* folder and paste them into the location indicated previously.

#### 3.4.0.2 In the event of failure

In the same way as for AsterStudy, when an error occurs during a run, it is possible to retrieve the log files of the terminal, which will contain additional information (in order to analyse the cause of the error) according to the verbose option chosen.

In that case, there are two directories to be taken into account: the flasheur and the tmp. On a local machine, the flasheur directory is normally found at the location `$HOME/flasheur/`, whereas the temporary directory tmp is located at `/local00/tmp/`. On the cronos and gaia servers, users have access only to the `flasheur` directory (also located at `$HOME/flasheur/`), access to the tmp directory being restricted.

An important distinction to note: the files in flasheur and tmp can vary according to the number of nodes or of processors used. For example, if two nodes are involved in the run, the information in the tmp directory can be duplicated and less well structured, which can complicate their analysis.

Note: The tmp file is located at `/local00/tmp/` because that is the default path. To modify it, one would need to change the file $HOME/.astkrc/config_servers.

## 4 Use of the commands run_aster, run_sbatch and run_ctest

Unlike astk and as_run, which make it possible to address different versions of code_aster, run_aster and run_sbatch launch only their own version. There is therefore one run_aster script (and one run_sbatch) per version.

Using run_aster is the recommended method for launching a code_aster run on the local server, and run_sbatch is the best option on the remote servers.

### 4.1 How to launch a run?

#### 4.1.0.1 The run_aster command

#### 4.1.1 On the local server

Locally, only run_aster is accessible (run_sbatch is not available, because there is in general no batch manager).

In order to launch the executables on the local server, one must first place oneself in the terminal of the container. Once inside, in order to launch the study of a single run, one must execute:

```bash
run_aster [options] file[.export|.py]
```

Here, run_aster is an alias to `/opt/salome_meca/V<version>/tools/code_aster<version>/bin/run_aster`. It is enough to choose the run_aster script of the version which one wishes to execute.

For developers, the path of the executable will frequently be `$HOME/dev/codeaster/install/mpi/bin/run_aster`.

It is possible to retrieve the information from the terminal during compilation by doing:

```bash
run_aster [options] file[.export|.py] > path_to_output_file
```

If needed, it is possible to display the help for run_aster by doing:

```bash
run_aster --help
```

#### 4.1.2 On the remote servers

First of all, one must connect to the remote server via ssh:

```bash
ssh NNI@ssh.hpc.edf.fr
```

On the servers of EDF R&D, it is mandatory to launch the analyses on the compute nodes in batch (and therefore with run_sbatch) and not on the front-end.

Note: run_aster executes directly, so it must not be used on the front-end.

#### 4.1.2.1 The run_sbatch command

This command is used to execute code_aster on the remote server. The simplest way of doing so is the following:

```bash
run_sbatch --wckey=$SBATCH_WCKEY [options] file[.export|.py]
```

Here run_sbatch is an alias for the executable `<SIMUMECA_INSTALL_DIR>/aster/install/<version>/bin/run_sbatch`. It is enough to choose the run_sbatch script of the version which one wishes to execute.

In this context, the key *$SBATCH_WCKEY* is to be requested from your project manager.

To find out more about the other launching options, the command available is:

```bash
run_sbatch --help
```

A recommended option is "--dry-run", which makes it possible to create and to read the submission script. This allows users to validate the parameters of the run before launching it. Here is an extract of what one might read:

```
#!/bin/bash
#SBATCH --job-name=myfile

# number of nodes
#SBATCH --nodes=1

# number of MPI processes
#SBATCH --ntasks=1

# number of threads per MPI process
#SBATCH --cpus-per-task=1 --threads-per-core=1

# max walltime
#SBATCH --time="01:00:00"

# memory in MB
#SBATCH --mem=11596M

# add `--exclusive` if several nodes, define `--partition=...`
#SBATCH
```

#### 4.1.2.2 The run_ctest command

This command is used to launch one or more test cases.

#### 4.1.3 On the local server

One must execute:

```bash
run_ctest --testlist=file[.txt] --resutest=folder [options]
```

By similarity, here run_ctest is an alias for the executable `/opt/salome_meca/V<version>/tools/code_aster<version>/bin/run_ctest` (which can change according to the version installed).

For developers, the path of the executable will frequently be `$HOME/dev/codeaster/install/mpi/bin/run_ctest`.

Note: Locally, the command run_ctest executes in a linear manner the computation of the test cases whose name is in the file file.txt (one test case after another).

On a remote server, run_ctest executes the analyses in parallel (one job for each test case).

In this example, the file file.txt contains the names of the export files to be executed. For example:

```
sdls118a
sdls118b
sdls118c
sdls118d
sdls118e
sdnx100g
```

Finally, the resutest option makes it possible to change the directory of the results of the test cases.

For more details on the other options available, one must execute in the terminal:

```bash
run_ctest --help
```

#### 4.1.4 On the remote servers

In a manner very similar to the case of the local server, one executes run_ctest by means of this command line:

```bash
run_ctest --wckey=$SBATCH_WCKEY --testlist=file[.txt] --resutest=folder [options] --sbatch
```

where one indicates the WCKEY key and the sbatch option, in order to launch the different test cases in different jobs with slurm.

## 5 Example: Using Python modules in an export file

Suppose that the tree of our project is:

```
project
├── mesh_file.mmed
├── command_file.comm
├── export_file.export
├── src
│   ├── __init__.py
│   └── python_file.py
```

The export file, which contains the information for the execution of the study, has the form:

```
P actions make_etude
P time_limit 60
P memory_limit 512
P ncpus 1
P mpi_nbcpu 1
P mpi_nbnoeud 1
P version stable

F comm command_file.comm D 1
F mmed mesh_file.mmed    D 20
```

To this export file, a line should be added in order to indicate the path of the folder to be taken into account during the run. Depending on the case, this line may be:

- When run_aster is used:

```
R nom chemin_du_src D 0
```

- When astk is used:

```
R repe chemin_du_src D 0
```

The difference between these two cases is due to the fact that astk, up to version 17.2 of code_aster, restricts the type *nom* to files. The type to be used is then *repe*. As a result of this, one must also adapt the way of calling the functions in the files of the *src* folder of our example.

### 5.1 Calling functions with run_aster

The way of importing, into the file command_file.comm, the functions contained in python_file.py is the following:

```python
from src.python_file import my_function
```

Assuming that the file python_file.py contains:

```python
def my_function():
    pass
```

### 5.2 Calling functions with astk

It should be noted that when a folder is imported with *repe*, astk will copy the files of the folder into a folder named REPE_IN in the temporary directory. This operation means that the Python modules must no longer be imported from `src`, but from `REPE_IN`.

In the command file, the way of importing the functions becomes:

```python
from REPE_IN.python_file import my_function
```

Note: astk does not allow more than one *repe* folder. Whereas with run_aster, which is the recommended solution, it is possible to have several.
